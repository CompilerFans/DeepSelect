# C500 行式 radix TopK：16 位行的耗时归因（2026-09-12）

这份记录回答一个问题：`radix_topk_row_bf16_b` 的时间**去哪儿了**。
交接手册 §9 列了四个候选杠杆，但那条清单是基于推测排序的——"绑定在
per-CTA 的 MLP 上"是推断，不是测量。这份记录把它换成实测，并且**退掉了其中
两条**。

口径与账本一致：C500（xcore1000），独占，`kk.bench` 取 **kernel time**，L2 每轮
flush，每格固定种子，两侧二进制分别现构（md5 在文末）。除非注明，cell 一律是
`b4096-v16384-k512`（bf16、`indices_type=int32`、`sorted_value=False`、
`sorted_index=False`、`return_value=False`）。

---

## 1. 方法：增量消融，不做加法计时

这段内核没有 FLOP，纯访存 + 比较 + 共享原子，所以不能靠"哪个阶段占比大"来
归因——`clock64()` 埋点会改变寄存器分配和指令调度，测出来的是探针自己的开销。

这里用的是**增量消融**：造一个变体，**只删掉一样东西**，其余逐字节不变，然后
两个变体相减。共同开销（启动、行遍历骨架、`__syncthreads`、寄存器分配）在两
次测量里是同一份，相减就抵掉了（`P5` 除外，见 §4）。

所有变体只存在于 `/tmp/dsprobe`（主仓的一份拷贝），**主仓从未被改动**
（`git status --porcelain` 全绿在整轮里保持为空）。每个变体的 `.so` 在测完后
立即删除：它们**按构造就是错的**（见 §5 的纪律）。

### 分母

| 量 | µs | 怎么来的 |
|---|---|---|
| 逻辑单趟 DRAM 下界 | 116.7 | 同一张 128 MiB 张量上 `x.sum()`，实测 1,149.8 GB/s |
| 两趟 DRAM 下界 | 233.4 | 上面 ×2（内核每行读两趟） |
| 行集 | 128 MiB | 4096 × 16384 × 2 B，是 8 MiB L2 的 16 倍 |

注意这个 1,149.8 GB/s 与账本里那个 1,487 GB/s 的 8 GB 流式墙**不是一回事**：
前者是"这个形状上可达的持续读速率"，分母更紧、更不利，所以本记录里的
"占墙百分比"比账本更保守。

## 2. 归因表

| 变体 | 改了什么 | µs | 增量含义 |
|---|---|---|---|
| 满内核 | — | **619.6** | |
| `P6` | pass 2 的 emit/staging 之后直接返回（跳过整个 refine 块） | **564.5** | refine 块 = **55.1** |
| `P7` | 在 `P6` 基础上，pass 2 的 emit 原子 → 普通 store | **528.1** | pass 2 的 emit 原子 = **36.4**；`P7` 与 `P1` 之差 = pass 2 的 walk + staging = 274.8 |
| `P3` | 满内核里只把 emit 原子 → 普通 store | **583.9** | 与 `P7` 一致，交叉验证 emit 原子约 36 |
| `P4` | pass 1 相邻两个元素合并成 1 个原子（原子数 ÷4） | **657.6** | **+38，更慢** |
| `P1` | 只跑 pass 1（直方图 + 过半后返回） | **253.3** | pass 1 的整段成本 |
| `P2` | 在 `P1` 基础上，pass 1 的 8 个共享原子 → 寄存器累加 | **150.8** | pass 1 的共享原子 = **102.5** |
| `P8` | `P1` + pass 2 的 walk（比较 + 普通 store，无原子、无循环携带依赖） | **385.4** | pass 2 的 walk ≈ **132.1** |
| `P5` | 两趟遍历，pass 2 换成纯计数（**有循环携带依赖，作废**，见 §4） | 379.6 | 不用 |

### 三个更细的口径

- **refine 块 55.1 µs**（`P6`）。它包含细直方图、256 宽扫描、arena emit、以及
  它的两次 `__syncthreads`。**注意这不是纯净余**：早返回也消掉了后面的
  `__syncthreads()` 屏障**等待**——而 pass 2 把工作分给 512 个线程，短行块先
  到屏障，所以那部分等待本来就不小（细直方图的原子工作量只集中在约 203 个
  staging 成员上）。真实净余 ≤ 55.1，用"每元素 ns"去读它会高估。
- **pass 2 的 walk ≈ 132.1 µs**（`P8` − `P1`）。`P8` 用普通 store 替掉了原子，
  没有 `P5` 那条循环携带依赖，所以这个数可以直接读：第二趟 128 MiB 是
  132 µs（约 1,020 GB/s，对单趟可达 1,150 GB/s 的 89%）。**两趟读合起来
  283 µs，对两趟下界 233.4 = 已达 82%。**
- **pass 2 工作流 = 275 µs**（`P7` − `P1`）= walk 132 + staging 原子 106 +
  emit 36。**staging 那 106 µs 是同一族问题里唯一还没被证否的一块**：每行约
  155 个成员，每个一次 `atomicAdd(&s_num_input[0])`（对同一地址）**加**一次
  细直方图原子。

**两个独立的 walk 都已在单趟可达速率的 80%~89%**，所以交接手册 §9 第 1 条
（行趟展开、加大 MLP）在**两个遍历上**都没有多少剩余空间——这比 §3 原来的
结论更强。

### 一条否掉的方向（重要）

`__ballot_sync` 的 wave64 分组归并（我原本要实现的那版）**正是 `P4` 的加强版**：
它也用"减少冲突次数"来换收益，只是做得更彻底。`P4` 既然为负，它就不再值得写。
**这是先测后写的价值**——那一版代码本来要动的是内核里最关键的 emit 路径。

## 3. 两个 walk 都已接近上限

`P2`（pass 1 去掉原子，保留向量装载、bf16x8 重解释和全部 8 次 key 变换）
= 150.8 µs，对 116.7 µs 的单趟下界 = **80% 可达速率**。

`P8` − `P1` 给出 pass 2 的 walk ≈ **132.1 µs**，对同一个下界 = **89% 可达速率**。

两趟合起来 283 µs，对 233.4 µs 的两趟下界 = **82%**。所以交接手册 §9 第 1 条
（行趟展开、每线程 2~4 个独立 `uint4`）在**两个遍历上**都只剩很少空间：pass 1
约 34 µs，pass 2 约 16 µs，合起来不到 50 µs。它仍然值得做，但顺序排到第 3 位，
而且目标要写清楚是"这不到 50 µs"，不是原先估的"抬 28% → 100%"。

**这一条是本轮最重要的结论修正**：内核现在**不是**"读得不够快"，而是
**"除了读以外还要做别的事"**——原子发射（pass 1 的 102.5 + staging 的 106 +
emit 的 36）和设备侧刷新一趟两趟之外的工作。

---

## 4. `P5` 的可信度说明（已用 `P8` 取代）

`P5` 把 pass 2 换成了一个手写的计数循环（`acc += (bin > tb)`），它引入了一条
**循环携带依赖**（`acc` 跨元素串行累加），这在真实内核里不存在。所以 `P5` 会把
第二趟测大，它的 379.6 **不能**用来推"pass 2 的 walk 是多少"。

`P8` 是同一个实验的正确做法：比较后**普通 store 到固定槽位**（无原子、无携带
依赖，其余与真实 pass 2 同形），`P8` − `P1 = 132.1` 就是第二趟的 walk。
`P5` 的数字保留在表里只为留痕：`P5`(379.6) 与 `P8`(385.4) 只差 6 µs，说明
**原来的担心（携带依赖会显著测大）在这格上没有兑现**，但方法上 `P8` 才是对的，
结论也只从 `P8` 读。

## 5. 下一步（按实测排序，替换交接手册 §9）

1. **pass 1 的直方图原子（102.5 µs，内核的 16.5%），现在是唯一的大头。**
   比 emit 侧两个原子加起来还多。`P4` 证明合并**冲突**不划算（原子数 ÷4、
   多一倍比较，反而慢 38 µs），但没证明减少原子**次数**不划算。唯一有支撑的
   方向是 §5 第 2 条：
2. **pass 1 的寄存器直方图（102.5 µs 的原子发射成本是唯一有支撑的方向）。**
   `radix_core.cuh:239` 的 `hist_add_bf16_reg` + `hist_reg_to_smem` 已在文件里
   且**无人调用**——全仓只有定义。它把原子从 8/uint4 降到 4/线程，代价是 8 次
   `__shfl_sync`。
3. **屏障等待 + 细直方图原子（约 104 µs，尚未单独量过）。** 由 §5.2 的缺口
   交代出来：五项已量成本相加 515.2，距满内核 619.6 差 104。这一项此前完全
   没被算过，**先量再说**——它可能比第 1 条更容易动（屏障等待是调度问题，不是
   原子问题）。
4. **MLP（交接手册 §9 第 1 条）。** 剩余空间：两趟合计不到 50 µs（§3）。
5. **chunked 路径的 static-k 行**（`radix_topk_row_bf16_k`）。仍是 8 位粗层 +
   3514 槽 arena。本轮的 cell 都不走它，所以它一点没被覆盖。

**别做**（已被实验否决，别重复）：

- **staging 原子聚合（F1）**——见 §5.1，越界，且 `s_num_input[0]` 是隐式溢出
  哨兵；而且它想省的 106 µs 本身是错的（真值 35.7）。
- **`__ballot_sync` / `__match_any_sync` 的分组原子归并**。`P4`（相邻两元素
  合并成 1 个原子，原子数 ÷4）实测 **619.6 → 657.6 µs，更慢**：省下的冲突不是
  瓶颈，那 102.5 µs 是每个原子的**发射/吞吐**成本。另外 `__match_any_sync` 在
  MACA 上是 32 次逐位 `sicmp` 的**软件模拟**，不是硬件指令。
- 固定加大 arena（24 KB）换溢出：效果被 coarse12 覆盖，还要在 topk ≥ 2048 掉
  occupancy。
- 把 `kMaxTopK` 那套按最大 k 预留 smem 的写法请回来：occupancy 直接掉到 1。
- 在 C500 上为 FP8 做性能判断（C500/C600 的 FP8 是软件模拟，性能只在 C600U 上
  测）——本题不涉及，但同仓库别的活涉及。

### 5.1 尝试过的方向：staging 聚合（F1）——失败，暴露了 `s_num_input[0]` 的双重身份

方案：把每成员一次 `atomicAdd(&s_num_input[0], 1u)` 改成**按 wave 预留槽位**——
`__ballot_sync` 取本 wave 的成员掩码，`__popcll` 计数，lane 0 做**一次**原子拿
基址，成员用掩码内的 rank 定位槽位。64 个成员从 64 次原子降到 1 次。

实现只落在**向量对齐路径**上：只有它的循环行程是块内均匀的，全 wave 掩码才有
意义；奇长度与标量路径保持原来的逐成员原子（永远正确）。编译通过，**运行时
非法访存**：

```
xnack(0x8): kernel causes atu address translation error
topk_kernel_radix<__maca_bfloat16, i32, 512, ...>
```

**根因不在 ballot，而在 `s_num_input[0]` 同时是两样东西：**

1. 它是 arena 槽位的**单调计数器**，**故意允许超过 `SMEM_INPUT_SIZE`**——写入被
   `pos < SMEM_INPUT_SIZE` 夹住，而 `overflow = s_num_input[0] > SMEM_INPUT_SIZE`
   正是**溢出检测**（`radix_core.cuh:1154`）。
2. 但 refine 之后同一段代码拿它当**无夹紧的循环上界**读 arena：

```c
const auto num = s_num_input[0];
for (uint32_t i = tx; i < num; i += BLOCK_SIZE)
    auto idx = s_input_flat[i];        // 无夹紧
```

正常路径下两者相等（一个成员一次原子，`pos` 与计数同步）。聚合版**故意多预留**
（`base += popcll(mask)`，装不下的成员也占计数），于是
`s_num_input[0] > 实际写入槽位数` → 读未写入的 arena → 越界。报错里的
`Li512` = `kLongRowBlockSize` 是唯一实例化 1024 线程路径的类型，与该溢出门一致。

**纪律**：`s_num_input[0]` 是一个**隐式的溢出哨兵**。任何让"计数"与"实际暂存数"
不再相等的改动都会越界。真要做聚合，必须**另加一个有界计数器**（或把 arena 读
循环也夹紧）——改动面比"把原子合并"大，且要先定住溢出哨兵。本轮不做，F1 已
回退，主仓源码零改动。

### 5.2 staging 原子的真实成本（把屏障等待剥掉）

`P9`：在 `P7` 的结构上（pass 2 的 emit 之后提前返回），把 staging 的
`atomicAdd(&s_num_input[0], 1u)` 换成**线程私有的槽位**（`pos = tx`），其余
（循环、两次屏障、细直方图原子）逐字节不变。`P7` − `P9` 就是 staging 原子本身
的成本，不含屏障等待。

| | µs | md5 |
|---|---|---|
| `P6`（pass 2 emit 后提前返回） | 562.3 | `a6484301f158` |
| `P7`（`P6` + emit 原子 → 普通 store） | 525.5 | `6be38345fd02` |
| `P9`（`P7` + staging 原子 → 私有槽位） | 489.8 | `fd5b3e272885` |

于是两个 emit 侧原子各自独立地量出来了：

| 项 | µs | 怎么来的 |
|---|---|---|
| pass 1 整段 | 253.3 | `P1` |
| pass 1 的直方图原子 | **102.5** | `P1` − `P2` |
| pass 2 的 walk | 132.1 | `P8` − `P1` |
| emit 原子（`s_counter`） | **36.8** | `P6` − `P7` |
| staging 原子（`s_num_input[0]`） | **35.7** | `P7` − `P9` |
| refine 块（含屏障等待） | 57.3 | 满内核 − `P6` |

**这是一次结论修正**：§5 第 1 条原先写的"staging 106 µs"**是错的**。那个数来自
`P7` − `P1` 再减去 walk 与 emit，而 `P7` 与 `P1` 都**提前返回**，两者之差里
混着 pass 2 的**屏障等待**（pass 2 把工作铺给 512 线程，短行块先到
`__syncthreads()`）。`P9` 把这一项单独拉出来后，staging 原子本身只有 35.7 µs，
与 emit 原子的 36.8 µs 同一量级。

**所以 pass 1 的直方图原子（102.5 µs）重新成为唯一的大头**，比 emit 侧两个
原子加起来还多。这也把缺口交代清楚了：253.3 + 132.1 + 36.8 + 35.7 + 57.3 =
515.2，距满内核 619.6 还差约 **104 µs**，那是**屏障等待 + 细直方图的原子**——
一个此前完全没被算过的项，值得下一轮单独量。

## 6. MACA 原语事实（顺手查清，记下来省得下一个人再查）

查 `__clang_maca_device_functions.h` + 编译探针（`.cu` 真编过，不是看文档）：

| 原语 | 状态 | 说明 |
|---|---|---|
| `__ballot_sync(unsigned long long mask, int pred)` | **原生，1 条指令** | `__builtin_mxc_sicmp(pred,0,ICMP_NE) & mask`（`:2202`）。**只有 64 位重载** |
| `__match_any_sync(mask, value)` | **软件模拟** | 32 次逐位 `sicmp` 循环（`:1648`）。别用 |
| `__activemask()` | **原生，1 条指令** | `__builtin_mxc_read_xmsk()`（`:2206`），64 位。拿它当 mask 免费 |
| `__popc` | **不存在** | 用 `__popcll`（64 位） |
| `__ffsll` / `__lanemask64_lt` | 有 | MACA 自己的 64 lane 代码用这一组，见 `maca_coalesced_scan.h:104-118` |

**wave 宽度是 64**（`radix_core.cuh:187`，`kWarpSize`）。所以 mask 必须写
`0xFFFFFFFFFFFFFFFFULL` 或 `__activemask()`，**不能写 `0xFFFFFFFFu`**：32 位
mask 会把同一 wave 的另外 32 个 lane 悄悄截掉，直方图少数一半，**不报错、
top-k 只是错**。这一条是本轮差一点踩进去的坑，值得单独留档。
