# C500 行式 radix TopK：16 位行的耗时归因（2026-09-12）

这份记录回答一个问题：`radix_topk_row_bf16_b` 的时间**去哪儿了**。
交接手册 §9 列了四个候选杠杆，但那条清单是基于推测排序的——"绑定在
per-CTA 的 MLP 上"是推断，不是测量。这份记录把它换成实测，并且**退掉了其中
两条**。

口径与账本一致：C500（xcore1000），独占，`kk.bench` 取 **kernel time**，L2 每轮
flush，每格固定种子，两侧二进制分别现构（md5 在文末）。除非注明，cell 一律是
`b4096-v16384-k512`（bf16、`indices_type=int32`、`sorted_value=False`、
`sorted_index=False`、`return_value=False`）。

---

## 1. 方法：增量消融，不做加法计时

这段内核没有 FLOP，纯访存 + 比较 + 共享原子，所以不能靠"哪个阶段占比大"来
归因——`clock64()` 埋点会改变寄存器分配和指令调度，测出来的是探针自己的开销。

这里用的是**增量消融**：造一个变体，**只删掉一样东西**，其余逐字节不变，然后
两个变体相减。共同开销（启动、行遍历骨架、`__syncthreads`、寄存器分配）在两
次测量里是同一份，相减就抵掉了（`P5` 除外，见 §4）。

所有变体只存在于 `/tmp/dsprobe`（主仓的一份拷贝），**主仓从未被改动**
（`git status --porcelain` 全绿在整轮里保持为空）。每个变体的 `.so` 在测完后
立即删除：它们**按构造就是错的**（见 §5 的纪律）。

### 分母

| 量 | µs | 怎么来的 |
|---|---|---|
| 逻辑单趟 DRAM 下界 | 116.7 | 同一张 128 MiB 张量上 `x.sum()`，实测 1,149.8 GB/s |
| 两趟 DRAM 下界 | 233.4 | 上面 ×2（内核每行读两趟） |
| 行集 | 128 MiB | 4096 × 16384 × 2 B，是 8 MiB L2 的 16 倍 |

注意这个 1,149.8 GB/s 与账本里那个 1,487 GB/s 的 8 GB 流式墙**不是一回事**：
前者是"这个形状上可达的持续读速率"，分母更紧、更不利，所以本记录里的
"占墙百分比"比账本更保守。

## 2. 归因表

| 变体 | 改了什么 | µs | 增量含义 |
|---|---|---|---|
| 满内核 | — | **619.6** | |
| `P3` | pass 2 的 `output[atomicAdd(&s_counter,1)]` → 普通 store | **583.9** | emit 原子串行化 = **35.7** |
| `P4` | pass 1 相邻两个元素合并成 1 个原子（原子数 ÷4） | **657.6** | **+38，更慢** |
| `P1` | 只跑 pass 1（直方图 + 过半后返回） | **253.3** | pass 1 的整段成本 |
| `P2` | 在 `P1` 基础上，pass 1 的 8 个共享原子 → 寄存器累加 | **150.8** | pass 1 的共享原子 = **102.5** |
| `P5` | 两趟行遍历，但 pass 2 换成纯计数（无 emit、无原子、无 refine） | 379.6 | 见 §4 的可信度说明 |

### 三条稳健结论

1. **pass 1 的共享原子是 102.5 µs，占内核 16.5%。** `P1` 与 `P2` 只差那一条
   `atomicAdd`，其余逐字节相同，所以这个差是干净的。8 元素/uint4 的原子频率，
   在 16 KB 的 4096 桶上，每行 16384 个元素 = 16384 次原子。
2. **把原子数按冲突降下来，反而更慢（`P4`：619.6 → 657.6）。** 这一条否掉了
   一个**具体的实现方向**，而不只是否掉一个数字：冲突合并要引入比较、分支和
   额外的原子地址计算，而省下的冲突不是瓶颈。也就是说，这 102.5 µs 是
   **每个原子的发射/吞吐成本**，不是总线争用。
3. **emit 的串行化只有 35.7 µs（5.8%）。** 约 462 个"高于阈值"的元素/行 ×
   4096 行，每条一次对同一地址的读改写。真实存在，但小。

### 一条否掉的方向（重要）

`__ballot_sync` 的 wave64 分组归并（我原本要实现的那版）**正是 `P4` 的加强版**：
它也用"减少冲突次数"来换收益，只是做得更彻底。`P4` 既然为负，它就不再值得写。
**这是先测后写的价值**——那一版代码本来要动的是内核里最关键的 emit 路径。

---

## 3. pass 1 的 walk 已经接近上限

`P2`（pass 1 去掉原子，保留向量装载、bf16x8 重解释和全部 8 次 key 变换）
= 150.8 µs，对 116.7 µs 的单趟下界 = **80% 可达速率**。
所以 pass 1 里留给"提高 MLP"的空间只有 **34 µs**。

交接手册 §9 的第 1 条（行趟展开、每线程 2~4 个独立 `uint4`）在 pass 1 上
**没有多少剩余**。它仍然值得做，但目标不是"抬 pass 1 的带宽"，而是
**pass 2 的读趟**和 pass 1 的**原子发射**——见 §5。

---

## 4. `P5` 的可信度说明（不要把结论建在它上面）

`P5` 把 pass 2 换成了一个手写的计数循环（`acc += (bin > tb)`）。它有两个问题：

- 它引入了一条**循环携带依赖**（`acc` 跨元素串行累加），这在真实内核里不存在
  （真实路径的 `bin > tb` 分支是一次不参与关键路径的原子 store）。所以 `P5`
  会把第二趟的耗时**测大**。
- 它删掉了整段尾活（细直方图、refine、arena emit），编译器因而可能重新调度
  前两趟。

因此 `P5` 的 379.6 **不能**与 `P1` 相减去推"pass 2 的 walk 是 228.8"。
唯一可以说的是：`P5`（两趟、无尾活）明显低于满内核，尾活段不小；具体多大，
要用与 `P1`/`P2`/`P3` 同等严格度的增量变体去量（下一步）。

---

## 5. 下一步（按实测排序，替换交接手册 §9）

1. **归因 pass 2 的尾活段。** 满内核 619.6 − pass 1 253.3 = **366.3 µs** 在
   pass 2 及其后。其中已归因的只有 emit 原子 35.7。剩下约 330 µs 里含第二趟
   遍历、阈值桶的 staging 原子、细直方图、refine 扫描、arena emit。
   用同样的严格度逐项拆（每条只删一样），再决定动哪一块。**这是当前最大的
   未知块，也是最大的一块。**
2. **pass 1 的原子发射成本（102.5 µs）。** `P4` 证明合并冲突不划算，但没证明
   减少原子**次数**不划算——`P4` 是"少一半原子、多一倍比较"。真正该试的是
   **寄存器直方图**：`radix_core.cuh:239` 的 `hist_add_bf16_reg` +
   `hist_reg_to_smem`（每个 warp 在寄存器里持 256 桶，warp 内归约后每线程只做
   `kBinsPerThread` 次原子）已经在文件里，但**当前无人调用**——全仓只有它的
   定义。它把原子数从 8/uint4 降到 4/线程（64 lane，`kBinsPerThread = 4`），
   代价是 8 次 `__shfl_sync`。这是唯一有实测支撑的 pass-1 方向。
3. **pass 2 / pass 1 的 MLP（交接手册 §9 第 1 条）。** 剩余空间：pass 1 里
   约 34 µs（§3），pass 2 的要等第 1 项量出来才知道。放在第 3 位，因为它的
   可见上限比原先估的小。
4. **chunked 路径的 static-k 行**（`radix_topk_row_bf16_k`）。仍是 8 位粗层 +
   3514 槽 arena。本轮的 cell 都不走它，所以它一点没被覆盖。

**别做**（本轮实测否决）：

- `__ballot_sync` / `__match_any_sync` 的分组原子归并。`P4` 已证伪其原理
  （降冲突不划算），并且 `__match_any_sync` 在 MACA 上是**软件模拟**：
  `__clang_maca_device_functions.h:1648` 起是 32 次逐位 `__builtin_mxc_sicmp`
  的循环，不是硬件指令；`__ballot_sync`（同文件 `:2202`）才是原生的**一条**
  `sicmp`。代价差 32 倍。
- 加大 arena、按 `kMaxTopK` 预留 smem：账本 §6 已否决，本轮没有新证据。

## 6. MACA 原语事实（顺手查清，记下来省得下一个人再查）

查 `__clang_maca_device_functions.h` + 编译探针（`.cu` 真编过，不是看文档）：

| 原语 | 状态 | 说明 |
|---|---|---|
| `__ballot_sync(unsigned long long mask, int pred)` | **原生，1 条指令** | `__builtin_mxc_sicmp(pred,0,ICMP_NE) & mask`（`:2202`）。**只有 64 位重载** |
| `__match_any_sync(mask, value)` | **软件模拟** | 32 次逐位 `sicmp` 循环（`:1648`）。别用 |
| `__activemask()` | **原生，1 条指令** | `__builtin_mxc_read_xmsk()`（`:2206`），64 位。拿它当 mask 免费 |
| `__popc` | **不存在** | 用 `__popcll`（64 位） |
| `__ffsll` / `__lanemask64_lt` | 有 | MACA 自己的 64 lane 代码用这一组，见 `maca_coalesced_scan.h:104-118` |

**wave 宽度是 64**（`radix_core.cuh:187`，`kWarpSize`）。所以 mask 必须写
`0xFFFFFFFFFFFFFFFFULL` 或 `__activemask()`，**不能写 `0xFFFFFFFFu`**：32 位
mask 会把同一 wave 的另外 32 个 lane 悄悄截掉，直方图少数一半，**不报错、
top-k 只是错**。这一条是本轮差一点踩进去的坑，值得单独留档。

## 7. 复现

```bash
# 1) 建隔离探针树（主仓不碰）
P=/tmp/dsprobe
cp -r <repo>/{csrc,deep_select,setup.py,scripts,tests} $P/ && rm -f $P/deep_select/*.so
cd $P && python setup.py build_ext --inplace        # 基线，md5 应为 40a2c663…

# 2) 每个变体：改一处 -> 构建 -> 存 .so -> 恢复源码
#    变体只改 csrc/xcore1000/radix_core.cuh 的 radix_topk_row_bf16_b
# 3) 计时（单 cell，钉种子）
PYTHONPATH=$P python t1.py
```

到底是哪份源码"的凭据。
