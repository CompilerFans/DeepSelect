# C600-U 上为什么不用上游 DeepSelect 的一趟式算法，当前方案是什么（2026-10-20）

本文回答两个问题，结论都来自本机的实测，不是移植判断：

1. 上游 DeepSelect 的原始算法（scan → filter → compact，一趟全局读）为什么在
   MetaX C600-U 上不是最佳性能方案；
2. 本仓当前落地的是什么方案，它在 C600-U 上被什么限制。

证据等级在每处标注：**实测**是本机或本仓实验记录里的数字，**推导**是从实测
数字直接算出的量，**未测**明确标出。所有 C600-U 数字来自 28 AP、128 KiB/AP、
MACA 3.8.1.3 的那台机器；C500（104 AP、64 KiB/AP）的数字单独标注。

---

## 0. 一句话结论

上游算法优化的是两个量：**每个元素只从全局内存读一次**，以及**候选集只有
`O(k + B + B2)`**。在 C600-U 上，一趟式的瓶颈不在 walk（阈值预置时 930 GB/s，
实测）而在 **compact**：保守阈值停在 k-th 所在 bin 的桶底，桶底之上的人口
（23,462，实测）装不下候选 arena（8,960），于是 compact 反复枚举，每轮
~20K 次按索引回读 key，实测每行 6 轮 ≈ 144 µs，总账比现行两遍 radix
**慢 2.0–2.6 倍**。且 ADJ4 之后两遍的第一趟（块最大摘要行走）已实测
~1002–1034 GB/s，比一趟式的过滤行走（930）还快——即使 compact 免费，
一趟式也赢不了。（2026-10-21 勘误：本文曾把 23,462 − 4,046 = 19,416 误读为
"k-th 值上的并列组"；它是桶底之上 42 个相邻 bf16 值的总人口，精确并列组为
24–110。机制更正见 §2.4，结论方向不变，但理由从"分布性质"换成了"实测速率"。）

两遍 radix 的直方图对并列和桶人口都是**免费**的：只是同一个桶多计几次数。这正是
它在 C600-U 上胜出的结构性原因，而不是某个微优化。

## 1. 两个方案

### 1.1 上游（官方）算法：scan → filter → compact

`docs/DeepSelect-deep-dive.zh.md` 的伪代码：维护阈值 `T`（初值 −∞），按
**随机块序**每次扫描 `B` 个元素，`x[j] > T` 的进入 `topk_candidate`；候选
缓冲超过 `k + B2` 时，在 shared memory 里做 radix-select 把候选精确收敛回
前 k，并把 `T` 更新为其中最小值。

它的代价模型（同文档）：

```
L = k + B + B2,  m = ceil(N/B),  H_m = sum_{i=1..m} 1/i
E[W] <= (1 + k/B2) * L * H_m = (1 + k/B2) * L * (ln m + O(1))
```

`B, B2 = Θ(k)` 时，TopK 部分的额外计算量是 `O(k log(N/k))`。这个界依赖三个
前提：

- **元素互不相同**（文档第 55 行明确写了"不妨设所有元素互不相同"）；
- `k + B + B2` 能放进 shared memory；
- 块序随机化带来的读带宽损失可以接受（随机化的目的是抗最坏输入）。

### 1.2 当前方案：两遍 radix（本仓 `csrc/maca_kernels/common/`）

对本仓而言，"当前方案"不是一个内核，而是一组按形状路由的数据流，全部共享
同一个契约半（NaN 处置、索引偏移、越界填充、有序输出）：

| 路由 | 数据流 | 入口条件（摘要） |
| --- | --- | --- |
| bf16 行内核 | 两遍 radix：12 位 coarse 直方图 → 阈值精确 → 只收集阈值桶 → 4 位 fine refine（V/k ≥ 256 时先对块最大值建直方图，元素直方图只走保留下来的块） | 默认；带跳表时 pass 2 只走摘要命中的块 |
| bf16 split | 每行切成 `chunks` 个 CTA，stage 1 各自建直方图，stage 2 合并；**每元素全局只读一次** | `vocab >= 262144`、`batches <= 64` 且 `batches^2 * 6400 <= vocab`（C600U 实测交叉）；`topk=2048` 另加 128 KiB 族门控 |
| fp32 coarse12 | 抽出 deep_gemm 的 `topk_coarse12`：12 位 coarse + 16 KB arena（直方图与候选别名）；pass 1 顺带写 16 元素块的 max-bin 表，pass 2 只走 kept-block 列表（列表 ≤ 3/4 块时；`6b5928c`） | 实测阶梯：窄行 `batches*topk >= 9216`，宽行 `>= 49152`；`vocab >= 2048` |
| fp32 chunks | 一 CTA 一行，沿行走（deep_gemm 的 chunks 内核） | `batches <= 2`（深解码带） |
| fp32 split | 分块 + 合并 | 长行、行数不足以填机；work target = `sm_count * 5 / 2` |
| fp32 行内核 | 8 位 coarse 直方图；阈值桶超过 arena 时整行重扫（多轮） | 其余形状 |

共享的调优件：

- **bf16 跳表**：pass 1 记下每个 64 元素块的最大桶号（`row_block_max`），
  收集时把"最大值 ≥ 阈值"的块压成 `row_block_list`；pass 2 只走列表。
  条件：bf16 + `vocab >= 65536` + `vocab >= 128 * topk`。1M 行、k=512 时
  被保留的块约 3%（推导：`1-(1-1/2048)^64`），pass 2 的流量接近免费。
- **块最大直方图**（pass 1 的两段式，2026-10-21 落地 `095224c`）：先只数每
  64 元素块的最大值（每块一次原子）；块计数跨过 `topk` 的桶 `m` 满足
  `#blocks(max>=m) >= topk ⇒ #elements(key>=m) >= topk ⇒ T >= m`，于是候选
  全在列表内，第二次元素直方图只走列表里的块。门 `topk <= length / 256`
  （盈亏点 `V/k ≈ 142`，取两倍余量）；门以下、非对齐行、`kSkip=false`
  逐字节未变。b4096 V1M k1024 17.42 → 14.16 ms（1.23×），k512 1.30×
  （`docs/experiments/20261021_blockhist/`）。
- **OUT=2 成对装载**（L2，2026-10-19 落地）：pass 1 的 walk 每迭代装两个
  16 B 块，MLP 翻倍；bf16 摘要走法与 fp32 coarse12 都采用。
- **NaN 扫描融合**：所有生产路线把 bit-pattern 投票折进本来就要读的一趟；
  逐行投票由 dispatcher 独占的 `scan_flags` 表承载，契约半读取并清零
  （2026-10-20 落地，见 `docs/experiments/20261020_scan_flag_read_clear/`）。
- **每族编译期常量 + 运行时 `sm_count`**：smem 预算、AP 数按族编入产物；
  网格尺寸按调用时设备的 `sm_count` 计算。

## 2. 为什么官方算法在 C600-U 上不是最佳

### 2.1 先排除错误的理由：它不是被原子顶卡住的

C600-U 的 bf16 pass 1 元素走法（每元素一次直方图原子）被**共享原子发射率**
封在 780–880 GB/s（实测：8 atomics/uint4 走法 771–832，+OUT=2 后 832–881；
机制是 ~12.5 G/s/SM × 28 AP ≈ 350 G atomics/s，每元素 2 B ⇒ 700–880 GB/s
硬顶，约为读墙的 50%）。C500 有 104 AP，摊薄 3.7 倍，从未撞到这个顶。
（2026-10-21 起 V/k ≥ 256 的行改走块最大直方图，每块一次原子。V1M k1024
的相位实测给出 pass 1a ≈ **827 GB/s**（占该行周期 73%，× 14.22 ms 覆盖
8.59 GB，见 §3.3），与 walk2 微基准的 854.6 相差 3%；原子顶仍然约束门
以下的行和第二次元素 walk（后者逐字节是第一趟的 1.7–3.2 倍），下面这条
推理也不依赖它如今是否正好在跑。）

**但官方算法恰好不撞它**：它的原子只发生在候选上（约 `k·ln(L/B)` 条/行），
不发生在每个元素上。所以"原子顶"不能用来否决官方算法——探针也证实了这一点
（下节）。否决它的是 compact，不是 filter。

### 2.2 读墙与 walk：官方算法的 walk 其实是快的

本机实测（2026-10-19，`docs/experiments/20261019_c600u_pass1/README.md`）：

| 探针臂 | GB/s |
| --- | ---: |
| 裸读，56 CTA × 512 线程，OUT=2/4 | 1616–1695（本机读墙 ≈1650，规格 2 TB/s 的 82%） |
| 裸读，OUT=1，1 CTA/SM | 265 |
| 裸读，OUT=2，同 grid | 956 |
| bf16 直方图走法（每元素原子） | 771–832 |
| 当时的 pass-1 形态（全量原子 + 块摘要，OUT=1，2026-10-19 读数） | 556–599 |

一趟式探针（2026-10-19/20，`docs/experiments/20261020_onepass/README.md`，
4096 行 × 1M bf16，生产 walk 几何）：

| 臂 | GB/s | 说明 |
| --- | ---: | --- |
| 裸读，仿射块序 | 1176–1184 | 随机块序比顺序读（1650）慢 ~28% |
| 过滤 + 暂存，**阈值预置真值** | **930–932** | 每元素 xform + 比较 + 罕见原子 |
| 完整一趟（含 compact） | **492** | compact 是唯一的大头 |

也就是说：**官方算法的 filter 段比当时的 pass 1 快约 1.6×**。如果 compact 免费，
这条路线会赢。它没有赢，因为 compact 不免费。

**这个 1.6× 在 2026-10-21 收窄了，而且已经被相位读数钉住**：块最大直方图
（`095224c`）把 pass 1a 的走法换成 walk2 微基准量到的 854.6 GB/s 形态；
`095224c` 之后的相位探针直接量到 V1M k1024 的 hist1a 占该行周期 73%
（≈ **827 GB/s**），第二趟元素 walk 占 8%（k512 是 5%）、collect 11%、
list 7%。对 filter 段（930）第一趟只剩 ~1.12×，把整行成本算进去约
~1.2×。完整一趟仍是 492。结论方向不变、而且更硬——一趟式的领先优势现在
几乎只剩 compact 成本（`docs/experiments/20261021_blockhist` §9）。

### 2.3 原型实测：正确，但慢 2.0–2.6 倍

原型 v1（`prototype_v1.patch`）完整实现了官方数据流：running threshold +
smem arena + 两轮 8+8 精确 compact + 寄存器快照。正确性全过（8 个目标 cell +
升序/常数/NaN 对抗组），途中修掉三个只有就位形态才暴露的竞争。**性能：所有
目标 cell 慢 2.0–2.6 倍。**

成本归因（实测，目标 cell b4096×1M，k=512）：

| 位置 | 成本 | 说明 |
| --- | ---: | --- |
| walk（load + xform + 比较 + 罕见原子） | ~80–136 µs/行 | 与 930 GB/s 探针一致 |
| compact ×6 次 | **~144 µs/行** | 每轮 ~20K 次**按索引回读 key**（分散 2 B gather） |

探针的 "filter + stage 930 GB/s" 用了**预置的真值阈值**，没有计入 compact 的
真实 gather。原型把它摊开了：**瓶颈不在 walk，在 compact 每轮按索引回 gather
键值**——20K 个分散的 2 B 读，每次都把行重新随机触碰一遍。

### 2.4 结构性原因：阈值粒度，不是并列密度（2026-10-21 勘误）

**本节原论断"k-th 值上并列 ~1.9 万元素"是误读，2026-10-21 更正。** 实测数字
本身没有问题，问题在解读。

v3 在原型的最终形态上测了同一行的键分布（实测，行 0，V=1M，bf16
NormalFloat）：

```
count(key > 49152) = 23,462     # 49152 = 0xC000，紧凑阈值停下的桶底
count(key > 49194) =  4,046     # 49194 = 0xC02A
count(key > 49235) =    490     # 49235 = 0xC053，该行的 k-th key
```

旧解读把 23,462 − 4,046 = 19,416 当作"k-th 值上的并列组"。但这两个计数
的键不同：19,416 = (0xC000, 0xC02A] 这 **42 个相邻 bf16 值**的总人口
（整个桶底到 k-th 的跨度是 83 个值、22,972 个元素）。**精确并列组** =
`count(key >= kth) − count(key > kth)`：numpy 模拟（官方 randn 分布，
`20261021_reference_recon/sim_tie_bf16.py`，bf16 RNE 截断）测得同形状
**29–36**（V1M k512 中位 29）、V1M k1024 中位 53、全网格 bf16 形状
**24–110**、fp32 恒为 **1**。旧解读大了一个量级。

**什么仍然成立（实测）**：

- compact 的成本：每行 6 轮 × ~20K 次按索引回读 key（~144 µs/行），是原型
  慢 2.0–2.6× 的主因（§2.3）。
- arena 装不下"高于桶底的人口"：保守合并把阈值降到 k-th 所在 bin 的桶底
  （原型自己的决策 1），桶底到 k-th 之间的 ~19–23K 元素都至少被暂存过一次。
  这实质是**阈值粒度病**，与 coarse12 的 12 位阈值桶在 k=2048 时装
  1336–1702 个成员是同一类问题——不是并列病。直方图对两者都免费，
  这正是两遍 radix 存在的理由。

**什么因此改变**：

- bf16 排除一趟式的理由从"结构性不可能"退化为**行走速率算术**：过滤+暂存
  行走实测 930 GB/s（§2.3），ADJ4 之后两遍结构的摘要行走在核内实测
  ~1002–1034 GB/s（`20261021_blockhist`、`e191bd6`）——一趟式即使 compact
  免费，单趟也跑不过两遍的第一趟；compact 实测并不免费（完整一趟 492 GB/s
  端到端）。结论方向不变，但依赖实测速率，不再依赖分布性质；速率关系翻转
  才是重估条件。
- "阈值 + 候选集"并不必然装下 19K：带裕量的阈值（如采样阈值）把阈值放在
  k-th **之下**，候选期望 ≈ 1.4k，并列组 24–110 装起来毫无压力。这条路线对
  fp32 完全开放（并列组 = 1），可行性已在官方分布上模拟验证——见
  `docs/experiments/20261021_reference_recon/` §7。
- sidecar 想法（staging 时顺手写 16 位 key，把 compact 的回读变成 smem 查找，
  估算端到端 560–750 GB/s）仍未落地；它修的是回读，不修桶底人口的暂存量，
  且 560–750 GB/s 本来就低于现在的摘要行走。

### 2.5 旁证：移植版在 C600-U 上的实测（不代表算法上限）

`csrc/maca_kernels/legacy/` 是上游算法的移植，在同一台 C600-U 上实测比
现行共享内核慢 1.5–2.9×（4096×16384 k=512 bf16：4146.8 µs vs 1413.8 µs；
512×262144 k=512：2721.2 vs 1793.1），且 `check_result` 全败（移植版的
rescan 路径只在 128 KiB SM 上可达，在那里它会丢掉阈值处并列组的高成员，
并用组内低成员的 key 回写全部成员）。

**这条只作为旁证。** 移植版本身有移植缺陷（lane-width 遗留、上述 rescan
路径），它的数字不能当作"官方算法在 C600-U 上的可达性能"；2.3/2.4 的原型
是原生实现、正确性全过，那才是算法级的证据。

### 2.6 官方算法在什么条件下才会重新成为候选

- **fp32（2026-10-21 新增）**：fp32 的 k-th 并列组恒为 1，采样阈值一趟式在
  官方分布上模拟可行（E[count] ≈ 1.4k，欠收/溢出概率 ≈ 0），成本模型
  1.8–2.9× 于三个大 fp32 格——见 `docs/experiments/20261021_reference_recon/`
  §7。这是本节第一个有模拟证据支持的"重开"方向，上机顺序排在 coarse12
  相位探针之后。
- **并列稀疏的分布**（2026-10-21 起弱化：并列组实测 24–110，不是 19K）：
  fp8 e4m3 的 8 位键空间会让同一 k-th 桶**更挤**，方向相反；bf16 一趟式的
  重估条件从此改为**行走速率关系翻转**（过滤行走持续快于摘要行走），
  不再是分布并列度。
- **大 smem 部件**：H100 类 227 KiB/SM 能装下 `k+B+B2` 且留 staging 空间；
  C600-U 的 128 KiB 在 k=2048 时一轮 arena 就接近预算。
- **C500**：其 pass 1 已在 96% 墙（长行实测 94.9–97.9%），一趟式只省第二趟；
  且长行的 pass 2 已有跳表，第二趟本来就近免费。未测，不默认。

## 3. 当前方案在 C600-U 上的实测状态

### 3.1 为什么"两遍"不是浪费

- pass 1 是**精确**的：12 位 coarse 直方图给出阈值，不需要候选集去"试"；
  并列只增加桶计数。
- pass 2 有跳表时只读摘要命中的块（1M 行 k=512 约 3% 的块）和块列表
  （每 64 元素 4 B），流量接近免费；无跳表的形状（短行）本来就在低占用带。
- 计数是**桶的属性**，不是"装得下多少"：阈值桶的成员全部计数，只有写入
  arena 受容量限制；溢出走整行重扫（fp32）或精确补集（bf16）。

同 cell（b4096-v1048576-k512 bf16）两遍结构的逻辑带宽实测 **513 GB/s**，
而 pass 1 单独 556–599 GB/s——pass 2 只占约 10%。（`095224c` 之后同一格
**674 GB/s**：pass 1 变快后 pass 2 的份额相应上升，两遍结构的结论不变。）

### 3.2 网格时间分布（C600-U，官方 95 cell + 附加形状）

| 带 | 占网格时间 | 达到读墙 |
| --- | ---: | ---: |
| bf16 大 batch 长行（b≥256, V≥256K） | ~35% | 26–31% |
| fp32 coarse12 cell | ~19% | 21% |
| 解码 b1–b64 | <1% | — |

### 3.3 当前真正的三个顶（都实测）

1. **共享原子发射率**：bf16 pass 1 780–880 GB/s（墙的 ~50%）。已试否决：
   采样直方图（端到端 +17–68%，见 20261019 §3）、多路副本（与不复制逐拍
   相同）、寄存器预聚合（427 vs 678 GB/s）、减桶数（拥挤分布炸）。
   **2026-10-21 起，V ≥ 256k 的行已绕过这个顶**：先对每 64 元素块的
   *最大值*建直方图（每块 1 次原子），再用它给出的精确块切割建列表，
   元素直方图只走列表里的块（`095224c`；b4096 V1M k1024 17.42 → 14.16 ms）。
   **pass 1a 的速度已经是读数**：`095224c` 之后的 clock64 相位探针
   （`20261021_blockhist` §9）在 b4096 V1M k1024 上量到 hist1a 占该行
   总周期的 73%，即 8.59 GB ÷ (73% × 14.22 ms) ≈ **827 GB/s**（约读墙的
   一半），与 walk2 微基准的 854.6 相差 3%——此前的反解值（855–870）偏快
   3%。同一次实测里第二趟元素 walk 占 8%（k512 是 5%）、list 7%、
   collect 11%；门底格 V262144 k1024 上第二趟涨到 23%、collect 36%，
   两趟 walk 合计 54% ≈ 改动前单趟的 51.6%，正是该格只赢 1.01× 的原因。
   全网格（147 行 / 134 个 cell，`perf_data/MetaX_C600-U/20261021_032150`，
   产物 `518cc1b1`）对旧 baseline 的总账是 **−10.87%**：34 格改善（有量级
   的都是 V ≥ 256K，最大 −24.4%），16 格回退（+3.2…+5.7%，全部是 bf16 短行）。
   回退在同 session 配对 A/B 里复现，而门下的格运行时一步没变（§9 的
   hist1b = 156 周期），代价是第二趟 body 编进同一函数后的代码生成——
   与 `kSkip` 门下的 +4% 中位同类，按“一套实例”接受；试过按 batch 收紧
   密度门，只值 1–2%，已放弃（`20261021_blockhist` §10）。
   它不能给 fp32 用：fp32 行已在元素级
   按 8 位 coarse 建直方图，本来就不在原子上封顶。
2. **MLP**：单在途 `uint4` 把 walk 压在 47–60% 墙；OUT=2 落地后低占用
   cell 提升 2–4×，原子封顶的大 cell 只有 +6%。
3. **解码固定成本**：split 的两张表 memset（本次改为 read-and-clear 后
   只剩一张，且只在增长时清）、stage 2 单 CTA 合并（b1-k2048 的 47%）、
   stage 1 每 CTA 固定成本（疑似 3× 偏胖，待 phase probe）。

fp32 coarse12 的绑定因素未定（不是原子；F1 待 phase probe）。

### 3.4 诚实的边界

- 以上是**本仓实现**的实测，不是"所有实现的上限"。fp32 行内核在
  `deep_gemm` 能服务的 12 个形状上，核级对比其 `topk_coarse12`：
  **2026-09-16 的 C500 记录**（ledger §8、MACA 3.8.1）是慢约 2×（大
  batch）/ 4.5–5.5×（小 batch）；**这一句在 C600U 上已经不成立** ——
  `kThreads` 512（`6b01951`）+ 第二趟 kept-block 列表（`6b5928c`）之后，
  两条长行（V107520 / V131072）在 batch ≥ 132 已全部在前面（b4096
  **0.880×** / **0.879×**，b132/b256 0.91–0.97×）；仍落后的是 b1
  （V66551 1.37×、两条长行 2.1–2.4×；45–111 µs 的 launch 延迟带）和最密
  的 V66551 形状在 b132/b512（1.13× / 1.01×，与上文该 cell 是唯一回退
  同源）。两次记录之间
  `deep_gemm` 自身只动了 −2.1..−3.6%，差值来自本仓
  （`perf_data/MetaX_C600-U/20261022_175424`，
  `docs/experiments/20261022_f32_pass2_skip` 的 "On the official grid"）。
  算子级仍反过来的原因没有变：它的 NaN 检查是一次全量 `torch.isnan`
  （wall 17.1 ms vs 本仓融合的 4.76 ms，b4096 V131072 k2048）。
- 本文的"官方算法"指上游 DeepSelect 的 scan→filter→compact 数据流，
  不代表任何其它实现。

## 5. 如何复核本文的结论

1. **并列密度**（2026-10-21 更正预期）：任取一行，按 bf16 有序键统计
   `count(key >= kth) - count(key > kth)`，即精确并列组；官方分布下同形状
   为 24–110（`20261021_reference_recon/sim_tie_bf16.py`）。本节旧版
   "相差两个数量级"的预期是 2.4 误读的结果，不是可复现的事实。
2. **walk 上限**：用预置真值阈值的 filter+stage 探针（`onepass_probe.cu`）
   测 930 GB/s 级数字；再测完整一趟，差额即 compact 成本。
3. **端到端**：`tools/ab_snapshot.py` 两臂交替、同 session；一趟式原型补丁
   在 `docs/experiments/20261020_onepass/`，当前树是基线臂。
4. 若要重开这个方向，先证明线上分布 tie-sparse（1 的统计），否则结论不变。
