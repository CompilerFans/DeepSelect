========================================================================

Resolve the 16-bit row's coarse level at 12 bits, over the arena

A bf16 key is 16 bits and the coarse level kept 8 of them, so the threshold
byte could hold thousands of members -- 4,686 of a 16,384-element row on the
perf table's own generator -- all of them ties the refine had to rank through
the candidate arena.  This is deepgemm's coarse12 layout applied to a 16-bit
key: keep 12 bits coarse, which leaves 4, i.e. exactly the rest of the key, so
two levels decide a key completely and the refine never ranks past the fine
ties.  The measured effect on the table's data is that the widest threshold bin
falls from 4,686 members to 203, under the arena at every cell, so the overflow
path stops being taken at all.

  - pass 1 builds a 4,096-bin histogram over `key >> 4` instead of a 256-bin one
    over `key >> 8`.  The bins live in the arena's own 16 KB: the histogram is
    dead before the arena is written, so one region carries both (deepgemm
    aliases these two the same way).  The dynamic request at k=512 goes 16,104
    -> 18,432 B, i.e. static+dynamic 18,432 -> 20,760, still under the 32 KB a
    second CTA needs; at topk >= 4096 both are past it already, so no k loses
    occupancy.
  - the scan still walks 256 bins: the 4,096 fold down to one bin per high byte
    first, and thread 0 then narrows inside the byte the scan lands on.  The
    fold is a plain 16-way sum, so the existing 256-wide warp scan is reused
    unchanged for both levels.
  - pass 2 emits `key >> 4` above the threshold and stages `key >> 4` equal to
    it, counting the low 4 bits; the refine ranks those 16 fine bins, and the
    arena emit reads `key & 0xF`.

  One rule in the narrow is worth naming because getting it wrong is silent:
  the sub-bin is the one where `count(above it) + its own count` crosses
  `remain_topk` -- the window -- and NOT the remainder left after the byte above
  has been counted.  Testing the remainder fires a sub-bin early whenever the
  byte has slack, which leaves the window short; the refine then finds no bin to
  land on and reads whatever the shared variable held.  It cost a memory
  violation and 379 of 512 wrong slots on b1-v4096-k512 before the dump showed
  the kernel choosing bin 0xBFA where the truth was 0xBF9.  The landing state is
  now initialized as well, so an unlandable crossing leaves a defined bin.

Both currencies, per the standing rule.  GB/s is over the logical row set
(B x V x 2 B / time).  No compute roofline applies: the kernel's arithmetic is a
compare and a histogram increment per element, no FLOPs.  The bandwidth roofline
is C500's measured 1,487 GB/s streaming-read wall; with the row read twice, the
fastest moved cell sits at 206 x 2 = 413 GB/s, 28% of it, against 17% before.
So the cell is still not DRAM-bound, and what is left is per-CTA: 512 threads x
16 B is 8 KB in flight, and the row walks are dependent chains of load ->
transform -> compare -> shared atomic.  The counters are the other half of it --
the threshold bin's members each take a serialized `atomicAdd` on one staging
counter plus one on the fine histogram, and the 16x smaller bin is most of why
this commit moves the cells it does.
