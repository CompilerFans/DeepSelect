**口径**。原则来自仓库纪律：**只给 delta 不算记录**——必须同时给出受影响 cell
的前后**算力与带宽**（含 arch peak / memory floor 的百分比）与绑定 roofline。

## 1. 测量契约

| 维度 | 取值 |
|---|---|
| 设备 | C500（xcore1000），104 AP，独占（跑前 `pgrep -af python` 确认） |
| 计时 | `tests/kernelkit` 的 `kk.bench(fn, num_runs)`，取 **kernel time** |
| 用例 | `tests/lib.py` 的 `TestParam`，**每格固定种子**（官方表按全局计数器取种，A/B 必须自己钉） |
| L2 | 每轮 flush |
| 二进制 | 两侧都由待比对的**那棵树**现构，md5 留档。**md5 是"测的是哪一个产物"的收据，不是内容哈希**：同源码两次构建的 md5 **不同**（mxcc 给中间编译单元取随机后缀，实测 6 个字节，见仓库 CLAUDE.md 的 Build 一节）；要判定两版是不是同一份代码，用 `cmp -l` + `nm -S` 对，不要用 md5 |
| 数据类型 | bf16 输入，`indices_type=int32`，`sorted=False`（除非另行注明） |
| GB/s 口径 | **逻辑行长**：`B × V × 2 B ÷ kernel time`。行被读几趟见每格的"趟数" |

**roofline 分母**：C500 实测**流式只读 1,487 GB/s**（8 GB 张量实测；读写混合
1,344 GB/s）。这个数**不要**从内核反推。

**这些 cell 没有算力 roofline**：内核每个元素只做几次比较 + 一次直方图自增，
没有 FLOP。所以"双币种"落地为：**逻辑单趟 GB/s × 趟数 = 实际 DRAM 流量**
（对只读墙的百分比），加上 per-CTA 的受限因素。

**官方表的数据长什么样**（决定一切）：`NormalFloatDistribution`，**不是**
bit-pattern 均匀。同一行里大量元素挤在同一个高字节上——这是所有优化围绕的
事实。

## 2. 三个提交，逐格 before → after

七个代表格（全部 bf16、k=512 除注明）。**每一列的"before"都是上一列的
"after"**，即链式可比。

### 2.1 `ea8bcb0` — staging 缓冲按 `topk` 定尺

原理：`radix_smem_bytes` 把选中下标缓冲按 `kMaxTopK`(4096) 预留 16 KB，而它
只装 `topk` 个。k=512 时 `静态 2,328 + 动态 30,440 = 32,768 B` = 正好半个
64 KB SM ⇒ **occupancy 只有 1**；改成 `4*topk` 后 16,104 + 2,328 = 18,432 ⇒
**occ 2**。

| cell | before µs | after µs | 逻辑 GB/s | vs torch |
|---|---|---|---|---|
| b4096-v1024-k512 | 420.7 | 240.3 | 19.9 → 34.9 | 1.62x |
| b4096-v16384-k512 | 2535.8 | 1588.3 | 52.9 → 84.5 | 1.31x |
| b4096-v16384-k1024 | 2597.2 | 1641.6 | 51.7 → 81.8 | 1.28x |

中性（该格本来就不是这个约束）：`b4096-v65536-k512` 2874.8 → 2863.9、
`b512-v262144-k512` 2887.7 → 2884.3、`b256-v1048576-k512` 6546.7 → 6569.5、
`b4096-v262144-k512` 22817.4 → 22835.0。

对只读墙的占比：最大的一格 84.5 × 2 趟 = 169 GB/s = **11%**。⇒ 不是带宽受限，
翻倍并发度才是收益来源；绑定的是 **per-CTA 的 memory-level parallelism**
（512 线程 × 16 B = 8 KB 在飞）。

### 2.2 `4cd740a` — refine 排"整个桶"，不是"装得下的那部分"

原理：细直方图是**阈值桶的计数**，staging 才是**arena 的容量**。旧代码把两者
一起夹在 `pos < SMEM_INPUT_SIZE` 里 ⇒ 桶比 arena 宽时直方图只统计了一部分，
refine 排的是截断子集，必须再整行重扫一趟来修。解开这个夹逼后 rebuild 趟消失，
同时把 overflow 的 emit 趟向量化（`uint4`，一次 8 个元素）。

| cell | before µs | after µs | 逻辑 GB/s | speedup |
|---|---|---|---|---|
| b4096-v1024-k512 | 240.8 | 239.7 | 35.0 → 35.0 | 1.005x |
| b4096-v16384-k512 | 1587.5 | 1034.3 | 84.5 → 129.8 | 1.54x |
| b4096-v16384-k1024 | 1641.2 | 1089.6 | 81.8 → 123.2 | 1.51x |
| b4096-v65536-k512 | 2865.6 | 2863.7 | 187.3 → 187.5 | 1.001x |
| b512-v262144-k512 | 2886.1 | 1689.2 | 93.0 → 158.9 | 1.71x |
| b256-v1048576-k512 | 6568.1 | 3821.0 | 81.7 → 140.5 | 1.72x |
| b4096-v262144-k512 | 22840.3 | 13280.0 | 94.0 → 161.7 | 1.72x |

**中性那两格恰好是"不溢出的格"**，这是因果自洽的独立证据：改动只碰 overflow
路径。CPU 侧对官方生成器建模（算第 k 大所在粗桶的规模）给出了完美对应的图景：

| cell | 8 位粗桶规模（中位） | 超过 arena(3514) 的行 | 本提交的实测 |
|---|---|---|---|
| b4096-v1024-k512 | 13 | 0/4096 | 1.005x（不动） |
| b4096-v16384-k512 | 4686 | **4096/4096** | 1.54x |
| b4096-v65536-k512 | 1505 | 0/4096 | 1.001x（不动） |
| b512-v262144-k512 | 6016 | **512/512** | 1.71x |
| b256-v1048576-k512 | 24086 | **256/256** | 1.72x |

分相（同格，instrumented build，cycles/row）：总计 80,144 → 48,396；rebuild 趟
20,690 → 287；emit 趟 24,870 → 12,998；非溢出路径 548.6 µs 不变。

### 2.3 `3f8dfe7` — coarse12：粗层 8 位 → 12 位，直方图 alias 在 arena 上

原理：bf16 key 是 16 位，粗层只用 8 位 ⇒ 阈值字节可能装下几千个元素（上表：
4,686）。保留 12 位 ⇒ 剩 4 位，**正好是 key 的余下全部**，两级合起来把 key
定完，refine 永远不会排到细 tie 之外。实测阈值桶从 4,686 降到 203 —— **低于
每一格的 arena**，overflow 路径整条不再被走到。

代价：直方图 1 KB → 16 KB，**alias 在 arena 上**（两者时间上不重叠）。k=512 的
动态请求 16,104 → 18,432 B，静态+动态 20,760 < 32,768 ⇒ **occ 仍是 2**；
topk ≥ 4096 时两种写法都早已越过门槛，**没有任何 k 因它掉 occupancy**。

| cell | before µs | after µs | 逻辑 GB/s | speedup | vs torch |
|---|---|---|---|---|---|
| b4096-v1024-k512 | 239.7 | 229.3 | 35.0 → 36.6 | 1.05x | 1.67x |
| b4096-v16384-k512 | 1034.3 | 650.7 | 129.8 → 206.3 | 1.59x | 3.09x |
| b4096-v16384-k1024 | 1089.6 | 704.9 | 123.2 → 190.4 | 1.55x | 2.87x |
| b4096-v65536-k512 | 2863.7 | 2203.0 | 187.5 → 243.7 | 1.30x | 3.53x |
| b512-v262144-k512 | 1689.2 | 833.8 | 158.9 → 321.9 | 2.03x | 4.54x |
| b256-v1048576-k512 | 3821.0 | 1724.1 | 140.5 → 311.4 | 2.22x | 4.06x |
| b4096-v262144-k512 | 13280.0 | 6471.5 | 161.7 → 331.8 | 2.05x | 4.54x |

**注意这一提交连"不溢出"的格也动了**（v1024 1.05x、v65536 1.30x）：收益不再只
来自"不溢出"，而是 staged/refined 集合无论是否溢出都缩了 ~16x。

CPU 侧建模（12 位粗桶规模）：全部七格 **超过 arena 的行数 = 0**，最宽 516。

### 2.4 chunked scratch 跨调用复用（host 侧，2026-09-14）

**这一条不是内核改动**，与前三条性质不同，记在这里是因为它改变了同一条
e2e 曲线，且它的口径必须写清：**上面的表全是 kernel time，这一节全是 e2e**。

原理：`deep_select.topk` 每次调用都 `cudaMalloc`/`cudaFree` 候选 workspace
（`batches*kChunkedChunks*topk*6 + batches*topk*4 + batches*4` = 307,224 B
@ b6-v262144-k512）再一对长度表。本 runtime 的 `cudaMalloc` **代价非线性、
且随 size class 非单调**（`malloc_sweep.cu`，无 torch）：

| 大小 | 空闲 | 内核交错 |
|---|---|---|
| 307,224 B | 69.9 µs/对 | 100.3 µs/对 |
| 12,288 B | 30.2 µs/对 | 34.8 µs/对 |
| 12,582,912 B | 1.2 µs/对 | 16.1 µs/对 |

本内核的 workspace 正好落在最坏档。改成进程内**只增不减**的 `ChunkedScratch`
（`DEEP_SELECT_NO_SCRATCH_CACHE=1` 可退回旧行为）。

| cell（bf16，e2e） | before µs | after µs | 变化 | GB/s b → a | 对只读墙 a |
|---|---|---|---|---|---|
| b6-v262144-k512 | 272.2 | 161.9 | **-40.5%** | 11.6 → 19.4 | 1.3% |
| b6-v524288-k512 | 273.3 | 172.4 | **-36.9%** | 23.0 → 36.5 | 2.5% |
| b6-v262144-k1024 | 301.5 | 174.4 | **-42.2%** | 10.4 → 18.0 | 1.2% |
| b64-v262144-k512 | 500.9 | 455.5 | -9.1% | 67.0 → 73.7 | 5.0% |
| b64-v524288-k512 | 500.4 | 440.7 | -11.9% | 134.1 → 152.3 | 10.2% |
| b64-v1048576-k512 | 782.5 | 707.2 | -9.6% | 171.5 → 189.8 | 12.8% |

**roofline 判定：这些格不是带宽受限**（最宽的一格也只有只读墙的 12.8%），
绑定的是 **host 入队延迟 + 每 CTA 并行度**（6 行铺 104 个 AP）。所以一个纯
host 侧的改动能换 40%，而剩下的对 deep_gemm 的差距（b6 两格 72.5/106.0 µs）
仍然不是带宽故事。

**设备时间逐格不变**（96.8 / 101.3 / 113.0 µs），全部 delta 来自被删掉的那两对
malloc —— 这是一条 host 侧改动，没有动任何 kernel。

**门**：官方 200/200 抽样 pass；`--perf` All 95 passed（73 timed，min 1.26x /
median 4.11x / max 12.22x）；全表 4 shard `82170/82170`；
`scratch_stress.py` 六个格的交错复用 3 轮全过。

**一个记录在案的非发现**：tie 重的格上**下标集合**逐次不同，改前改后的二进制
都如此。这是**并列**不是竞争 —— `NormalFloatDistribution` 让 k 边界上有等值
元素，多个集合都对。用**无并列**构造（`2^e*(1+j/128)`，bf16 精确可表示，k 边界
严格落在互异区内）时下标集合逐次相同且等于 `torch.topk`；值的**多重集**在所有
格上都稳定。（据此，一个中间探针把"按索引排序后逐位置比 value"当成多重集比较
而报出的 `DIFFERENT-VALUES` 是**错的**，已作废。）

**已知代价：`ChunkedScratch` 带锁，多流并发会退。** `topk()` 在整个函数体里持有
`ScratchGuard`，所以两次 launch 都在锁内；官方 bench 是单线程、纯设备口径，**看不见
这一条**。实测（`conc2.py`/`conc3.py`，2 线程 / 2 条 `torch.cuda.Stream`，每线程 20
次调用，取最慢线程）：

| 被测 | 1 线程 | 2 线程/2 流 | 退化 |
|---|---|---|---|
| `deep_select.topk`（cache **ON**） | 114.9 µs | 1559.1 µs | **13.6×** |
| `deep_select.topk`（cache **OFF**，无锁） | 270.1 µs | 1926.9 µs | 7.1× |
| **对照：`torch.empty` + `fill_`（无 deep_select）** | 12.8 µs | 92.1 µs | **7.2×** |
| 对照：`torch.topk` | 293.3 µs | 475.2 µs | 1.6× |

**读法**：那个 7.2× 的对照最要紧 —— 两个纯 torch 算子、完全不碰 deep_select，在同样的
2 线程/2 流结构下就退 7.2×。所以**这个退化是这台机器的 Python/分配器/多线程派遣层
本身的**（GIL + caching allocator 锁），不是本扩展引入的。锁的边际贡献是
ON 的 13.6× 对 OFF 的 7.1×，即在基线之上再翻约 2×，出现在 host ~= 派遣受限的
形态上。（单次采样，不做精细解读。）官方 bench 单线程，所以任何臂都不受影响。

**要真修**，方向是不在锁内跨 launch：拿完指针就放锁再启动。但那要求缓冲区按流隔离或
带引用计数（否则释放别的流正在读的缓冲），改动面大于本条。**记录为已知限制，不隐藏。**

**架构边界**：只改 `csrc/xcore1000/`，xcore1600 逐字节不变，不欠 C600U 验证。

#### 补记：官方性能表**看不见**这一条（口径），以及三币种稳态表

`tests/test.py:140-144` 的规则是"匹配到恰好一个含 `topk` 的 kernel 名就用
kernel time，否则用 e2e 跨度"。**chunked 路径匹配到多个**，所以走后者 ——
那是**设备**跨度，不含任何 host 时间。于是官方表对这一条**必然零差异**
（实测：ON 与 OFF 的六格逐格相同到 0.1 µs）。这同时说明了一件事：
`deep_select.topk` 的 host 时间**完全被设备时间遮住**，官方表看不见它。

要量的是**稳态吞吐**，这才是服务循环里的读数。名字先定死：

- **管道 ON** = `ChunkedScratch` 生效（**现在的默认行为**），workspace 跨调用复用，
  热路径上不再 malloc。
- **管道 OFF** = `DEEP_SELECT_NO_SCRATCH_CACHE=1` 打开的**旧行为**（每次调用
  malloc/free），是这条改动的 A/B 对照臂。**OFF 不是"关掉缓存"的新功能，是改前
  的行为**。

"管道"指**连续背靠背调用、中间不 `synchronize`、设备从不停转**（`final_perf.py`
的 pipe 臂：100 次调用，壁钟/100）。对照的两个口径是：**call**（每次调用都从设备
空闲开始，用 cudaEvent 围住）与 **dev**（CUPTI 的 kernel 跨度）。三者回答三个不同
的问题——call 回答"单次延迟"，pipe 回答"稳态吞吐"，dev 回答"内核本身多快"。

| cell（bf16 除注明） | 设备 µs | 管道 OFF µs | 管道 ON µs | 吞吐 | GB/s OFF → ON | 只读墙 OFF → ON |
|---|---|---|---|---|---|---|
| b6-v262144-k512 | 96.9 | 262.4 | **107.3** | **2.45×** | 12.0 → 18.9 | 0.8% → **2.0%** |
| b6-v524288-k512 | 100.9 | 267.5 | **112.2** | **2.38×** | 23.5 → 36.3 | 1.6% → **3.8%** |
| b6-v1048576-k512 | 142.5 | 312.9 | **153.3** | **2.04×** | 40.2 → 56.3 | 2.7% → **5.5%** |
| b6-v262144-k1024 | 114.2 | 285.2 | **124.6** | **2.29×** | 11.0 → 17.3 | 0.7% → **1.7%** |
| b6-v524288-k1024 | 162.2 | 335.2 | **173.9** | **1.93×** | 18.8 → 27.2 | 1.3% → **2.4%** |
| b6-v1048576-k1024 | 169.5 | 340.4 | **180.2** | **1.89×** | 37.0 → 51.0 | 2.5% → **4.7%** |
| b32-v524288-k512 | 206.8 | 382.0 | **227.6** | **1.68×** | 87.8 → 102.5 | 5.9% → **9.9%** |
| b64-v524288-k512 | 351.9 | 492.3 | **374.7** | **1.31×** | 136.3 → 152.8 | 9.2% → **12.0%** |

路径上的 host 时间**：

| cell | 设备 µs | 管道 ON − 设备 | 管道 OFF − 设备 |
|---|---|---|---|
| b6-v262144-k512 | 96.9 | **+10.4** | +165.5 |

ON 臂的 host（约 65 µs）基本被设备遮住，只剩 ~10 µs 露在关键路径上；OFF 臂则
整条被 host 卡住（露出 140–170 µs）。

**107.3 > 96.9，不等号写反了**，据此编的那段"派发快过执行"解释也一并作废 ——
ON 臂的管道值在每一格上都**高于**设备时间，从来没有低于过。结论方向不变（ON 时
host 基本被遮住、OFF 被卡住），但支撑它的推理是错的，已改为上面的直接相减。）

`host_only.py`）：

`call − dev` 是**间接**估计：OFF 臂上 `call − dev` = 167.7 而直接量得的 host 是

再起表。单行报数一律用上面的直接测量。）

**两行 fp32 是这一节的对照组**：它们**不走 split**，所以从来没有过那对 malloc，
ON/OFF 两列相同（0.99×/1.00×）。这正是条目 ① 当时欠着的那部分——要让它们也吃到
同样的收益，必须给 fp32 接上 split 分支。**该分支已在 §2.5 落地**：此后 fp32 的
长行格走 split，`ChunkedScratch` 的那对 malloc 同样不再出现在热路径上。

**roofline 仍不在这条路径上**：ON 之后最好的格也只有只读墙的 12.0%，最差的
1.7%。这些格绑定的是**每 CTA 并行度**（6 行铺 104 个 AP）与设备内的 per-CTA
依赖链，**不是带宽**。带宽指标在这里的作用是**排除**带宽受限，不是描述瓶颈。

### 2.5 `2bfddbb` + `cd649a0` + `4baee61` — fp32 行：pass 2 向量化 + chunked split

三条改动在**同一族** cell 上链式生效（fp32，k∈{512,1024}，
`sorted_value=False`，种子钉死，`kk.bench(num_tests=10)` 取 **kernel time**，
`CUDA_VISIBLE_DEVICES=3`，C500）。每一列的 before 是上一列的 after。

**原理（三条各一句）：**

1. `2bfddbb` —— **pass 2 是延迟受限，不是带宽受限**。两条 walk（
   `remain_topk == 0` 的补集 emit 与暂存 walk）原本是逐元素 `__ldg`（4 B 宽，
   该宽度实测天花板 1,244 GB/s），改成 `float4`（16 B，天花板 1,650 GB/s）写在
   同一个 `stage_f32_lane` 里。**"4 B 访问每次载入的 stall 数是 16 B 的四倍"**
   是这条的机制，不是"少读字节"——字节数一个没变。
2. `cd649a0` —— **长行 + 小 batch 的问题不是带宽，是 CTA 数**。6 行铺 104 个 AP
   只有 6 个 CTA 在跑（只读墙的 0.65%）。给 fp32 接上 16 位那套 chunked split
   （stage 1 每 chunk 一个 CTA，stage 2 合并 `chunks*topk` 个候选），
   与 16 位 split 的唯一设计差异是 fp32 行核的 `output` 是**行内列号**，
   所以多了 `chunk_begin`（只在 emit 处加）与 stage 1 并记 `cols[]`。
3. `4baee61` —— **一个门槛不够**。split 的开销是 `batches` 个 CTA 的合并、
   收益是行核的每 CTA 时间，两相抵在 **b256 上会反号**（见下表），所以门槛分两级
   （小 batch 一档、大 batch 一档），而不是把小 batch 的阈值外推上去。

| cell（fp32） | `2bfddbb` 前 | pass 2 向量化后 | split 后（`4baee61`） | 累计 | 逻辑 GB/s | %1W（2 趟） | deep_gemm µs | 对 dg |

`DEEP_SELECT_F32_CHUNKS` 可覆盖（作 A/B 旋钮保留，默认值下不改变行为）。

**roofline 判定，分两族：**

- **小 batch 长行（split 族）**：**不是带宽受限，改前也不是**——改前 0.65%、

  所以这一族**不能用带宽口径评判**，带宽数在这里只用来**排除**带宽故事。
- **大 batch 族**：split **没碰**，仍绑在 `per-CTA 依赖链 + 共享原子发射率`
  （§4 的判定继续有效）。它们的 21–25% 只读墙是**这条改动之后**的数，

  天花板被这刀收回**。

**量级**：`2bfddbb` = 大 batch 族 **+28..+33%**、短行 +11..22%、V=1024 是噪声，
**无格回归**；`cd649a0` = 两个目标格 **+5.04× / +7.26×**、V=1024 处 +9..18%、
**其余全部在 ±1% 内**；`4baee61` = 新增 `b6-v129280`（Sampler 的形状，原来
低于旧门槛走行核 211.1 µs）**3.06×**，其余 ±1%。

**口径注记（两条，都必须随数字一起读）：**

1. **官方大表测不出 `cd649a0`/`4baee61` 的收益**。`tests/test.py:140-144` 的规则
   是"匹配到**恰好一个**含 `topk` 的 kernel 名就用 kernel time，否则用 e2e 跨度"。
   split 路径同时匹配 `topk_f32_chunk_stage1_kernel` / `…stage2_kernel` /
   `topk_kernel_radix` **三个**名字，所以走后者——而那是**设备**跨度，
   不含 host 时间，也看不出"6 个 CTA 的机器被填满"。官方表的零差异是
   口径的产物，不是改动的性质。
2. **split 的收益只在设备被填满时兑现**。它的全部意义是"把 6 个 CTA 的机器填满"；
   在**串行流**上这些 shape 本来就是设备受限、调用之间有设备空闲，
   所以把每次调用**单独**计时（`call` 口径）时，这个收益会被除回去。
   稳态读数要用 **`pipe` 口径**（背靠背、设备不停转），`call`（单次延迟）与
   `dev`（CUPTI 内核跨度）各自回答另一个问题——三者不是同一把尺子。
   本节所有 before → after 都是 **kernel time**（`dev`），它既不含 host、
   也不含调用间的空隙，因此对这三条改动是**中性的尺子**：split 的 96 个 CTA
   在设备上真的是 84 µs，而不是"和 6 个 CTA 的 425 µs 一样快只是被遮住了"。

**门**（`4baee61`，也就是本节末的二进制；最终 4 shard 全表见 §5）：

| 门 | 结果 |
|---|---|
| 官方 200/200 抽样（`--backend maca_c`） | **200/200 passed**，0 unsupported，0 failed |
| **全表 4 shard 串行** | **82170/82170 passed**，0 unsupported，0 failed（20543+20543+20542+20542，1,730–1,917 s/shard） |
| ABI | 0 `libtorch`/`libc10` DT_NEEDED，0 `c10`/`torch`/`at::` 符号，2 个 `__tvm_ffi_` 导出 |
| arange 冒烟（期望下标写死） | b2-v262144-k8、b6-v262144-k512、b6-v524288-k512、b6-v1048576-k512、b64-v262144-k512、b64-v1048576-k1024 的**选中集合**全部精确 |

**带出来两个无声缺陷（都记档，因第一个是本仓库 dispatch 撞过的同一类）：**

1. `launch_radix` 的 **preselected 臂带着 `if constexpr (bf16)` 守卫**，于是 fp32
   split **静默落到非 preselected 核**：merged 答案含 `-1` 的行被 `rerank` 兜回
   （掩盖一半），答案干净的行**直接从没初始化的共享 arena 发射**——
   `b6-v524288` 返回 `[0,0,0,…]`。**不报错、不 trap。** 守卫已删

2. `launch_topk_f32_chunked` 起初从调用方 workspace 的**基址**推 arena，而 split
   在它前面放了行长度表与逐行 NaN 标记，导致 stage 1 的列号整体偏移几百个元素。
   现在它接 arena 自己的起点（`ws.cols`）。

**架构边界**：三条都只在 `csrc/xcore1000/` 内（`radix_core.cuh` + `maca_topk.cu`），
xcore1600 逐字节不变，**不欠 C600U 验证**。本题不涉及 FP8。

### 2.6 `0fc74ae` + `1a72ea9` — chunk 数改成 batch 的函数，V 地板随之下沉

**§4 那条"批尺寸当网格用"的杠杆，这两条把它兑现了一半。** §4 的抽取实验说：
pass 1 的循环在 4,096 个 CTA 上跑 **1,646 GB/s（只读墙的 99.8%）**、104 个 CTA 上
只有 **921（55.8%）** —— **循环没病，病在 CTA 数，而 CTA 数 = batch**
（`launch_radix` 是 `<<<batches, BLOCK, smem>>>`）。两条改动各修一半：

**原理（各一句）：**

1. `0fc74ae` —— **大 batch 下 split 的价值不是并行度，是"chunk 小到能读得快"。**
   门槛原本只开到 `batches <= 256`，恰恰把 `b4096` 这一族（有富余 CTA 的那一族）
   关在门外；现在开到 `batches <= 4096`，同时 `f32_chunked_chunks(batches)`
   把 chunk 数从"恒定 16"改成 **>64 batch 恒为 2**。
2. `1a72ea9` —— **门槛的地板是拿"会随 `chunks` 缩放的成本"量的，chunk 数一变成常量，
   那个成本就不随门槛缩放了，地板于是可以下到小 batch 档的值。**
   两级门槛从"各自坐在自己拐点的赚的一侧"变成"坐在同一个拐点上"。

**chunk 数扫描（`0fc74ae`，为什么大 batch 取 2）：**

**一个方向：上面每一格都单调偏好更少的 chunk**，b6 在 16–32 之间平是唯一的例外
——6 行时机器是空的，chunk 是仅有的 CTA。所以这不是拟合曲线：小 batch 臂保留在
它身上量到的值，超过 split 自己的小 batch 上界（64）的一律取最小值。
`b512`/`b768` 上 1 与 2 相同，所以 2 是安全的下界。

### 2.7 中段 V（4K–64K）：一个**被否掉**的候选，和一条量出来的噪声纪律

**起因**：§8.2 的 deep_gemm 差距表把最大的缺口定位在 `V ∈ [4K, 64K]`
（2.3–2.7×），而 split 的 V 地板是 65536 —— 这一带恰好是地板够不着的地方。
于是按 §2.6 同一套办法（门槛下沉）去量。

**结论先说：没有落地。** 唯一被证据支持的改动是
`kF32ChunkedMinVocabLargeBatch` 65536 → 32768，它**把所有长行格都保持在
±1.0% 以内**，但同时把 `V=32768` 那一行的一批 b48/64/192 格推高
**+11…+23%**。§4 的纪律要求"验证受影响的形状族、排除回归"，这条过不了，
所以它作为**候选**记在这里，不进代码。

**一条必须记下来的测量纪律：分块（blocked）扫描在这个 box 上给出假结果。**
第一轮门槛扫描是"把 arm A 的 5 轮跑完、再跑 arm B 的 5 轮"，它在
`b6-v32768` 上给出 head 71.4 / cand 56.6 µs = **−20.6%**。
**而这个格在三个 arm 里走的都是行核**：`v(32768) < 65536`，两级门槛都判 false，
split 根本不进。**同一条路径不可能差 26%。** 那是 arm 之间的漂移。

改成**轮转**（每轮每个 arm 各跑一次、奇偶轮颠倒顺序）之后，同样的格子重测为：

| 格 | 分块 | 轮转 |
|---|---|---|
| b6-v32768 | −20.6% | **−20.4%** |
| b48-v32768 | +11.2% | **+11.0%** |
| b64-v32768 | +21.9% | **+22.0%** |

**结论要分开看，别一律当噪声扔掉**：b6-v32768 的 −20% 在轮转下**依然存在**，
所以它不是漂移，而是**探针内部**的效应（同一轮里 b6-v32768 是第 1 个格、
b6-v65536 是第 11 个格，而 b6-v65536 在两次测量里都是 66 µs 不变）——
两个 arm 都取行核，差的是**测量顺序**。**这一格在拿到解释之前不可引用**；
而 b48/b64 的 ±11…22% 在轮转下复现，是真的。

**两次扫下来的完整数据（轮转，5 轮，中位数，`ab_rr.py` / `ab_gate.py`）：**

| cell | chunks=16 时 δ | chunks=2 时 δ | V/batch |
|---|---|---|---|
| b64-v32768 | **+21.9%** | −13.7% | 512 |
| b48-v32768 | **+11.2%** | −15.6% | 683 |
| b64-v65536 | +0.6% | **−21.1%** | 1024 |
| b48-v65536 | +0.9% | **−15.4%** | 1365 |
| b33-v65536 | +1.0% | +1.6% | 1986 |
| b64-v262144 | +0.2% | −0.7% | 4096 |

| b33-v262144 | +0.6% | **+27.9%** | 7944 |
| b64-v524288 | +0.3% | **+14.3%** | 8192 |

（"δ" = 相对 head 的比值中位数，两列分别是在"chunk 边界 64"和"chunk 边界 32"
的二进制上测的；b96/b128/b256/b4096 在两列里都是 −8…−18%。其余格
—— b6/16/32-v32768、b6/16/32-v65536、b6/64-v16384、b6/256-v262144、
b4096-v262144 —— **每一格都在 ±1.0% 以内**。）

**所以：分档阈值 32 只能覆盖到 b≤32（它服务得好，−18%），b48–64 落在一个
floor 单独会使其退化的窗口里。** 在拿到区分二者机制的证据之前，
`V=32768` 这一带退回到"不做改动"。

**副产品（可独立引用）**：**`V ≥ 65536` 的每一格都已在当前默认值上**
（head 对候选全部 ±1.0%），所以把地板 65536→32768 对长行**中性**；
`kF32ChunksFewBatches` 的分档边界在 32 与 64 之间移动，对
`V ∈ [32768, 524288]` 的 b48–64 格**有 ±15…28% 的效应**——它是这一带真正
起作用的旋钮，不是地板。

**没有跑门的理由**：本条没有落地任何改动，`cands` 只存在于 `/tmp`；
交付的扩展与 HEAD 逐字节一致（`md5 = d230c6946537fcb5a47f329ef8852d90`）。

## 4. roofline 判定（每格绑定什么）

`b4096-v16384-k512`（最常被引用的那格）现在 650.7 µs：

- 逻辑单趟 206 GB/s，行读 **2 趟** ⇒ 实际 DRAM ~413 GB/s = 只读墙的 **28%**。
- 优化前是 17%。⇒ **仍然不是带宽受限**。
- 绑定的是 **per-CTA 的依赖链**：`load → key 变换 → 比较 → 共享原子`，512 线程
  × 16 B = 8 KB 在飞；再加**串行化的共享原子**（阈值桶每个成员一次
  `atomicAdd` 到同一个 staging 计数器，细直方图再压一次）。
- 12 位粗层把那个桶从 4,686 降到 ~203——这正是本提交收益的大头。

**下一步的杠杆**（按判断排序，都未做）：

1. **批尺寸当网格用：`launch_radix` 是 `<<<batches, BLOCK, smem>>>`。**
   这是**现在唯一有实测支撑的杠杆**，也解释了 pass 1 的缺口。
   把 pass 1 的循环**逐字**抠成独立核（`/tmp/dsab/mt_kernel.cu`，同样的
   `hist_add_f32`、同样的共享桶原子、同样 2,328 + 14,056 B、0 栈帧），
   **每次读满同样的 4.295 GB、只改 CTA 数**：

   | grid | 4096 | 1024 | 512 | 256 | 104 |
   |---|---|---|---|---|---|
   | GB/s | **1646.4** | 1599.4 | 1423.4 | 1519.1 | **921.3** |
   | 占 1650 | **99.8%** | 96.9% | 86.2% | 92.1% | **55.8%** |

   **循环本身没病**（99.8%），病在 CTA 数，而 CTA 数 = batch。
   `b512-v262144` 是 512 个 CTA、`b16-v16M` 是 16 个。见 plan §15.6。
   **修法已落地**：`0fc74ae` 把 fp32 chunked split 的门槛从 `batches <= 256`
   开到 `batches <= 4096`（`b4096` 正是这一族），并把大 batch 的 chunk 数
   定为常量 2；`1a72ea9` 随之把 V 地板从 262144 下到 65536。见 §2.6。
   **本条的下一半仍未做**：`b16-v16M` 这类 batch 更小、行更长的形状走的是
   16 位 split（`batches <= 64` 才开 split），以及 fp32 行的多轮 rescan。
   剩下的通用形态（"每行多 CTA"不依赖 dtype）也还是未做。
2. warp 聚合原子（ballot / match-any）把同地址原子从 32 次压成 1 次——先确认
   MACA 的原生面有没有 match-any。
   **更正：方向可能反。** §15.1 实测同一个核加不加 pass 1 的 4 次 `atomicAdd`
   只差 **0.5%**；`docs/C500-radix-profile.zh.md` §5 也记过一个把原子冲突降 4×
   的变体**慢 38 µs**。
   **2026-09-14 再更正**：§15.3 曾把这条重新立起来（"3 CTA/SM + 原子"），
   但 §15.6 的抽取实验把它**彻底否掉** —— 那个循环在 39 道波时带着原子跑满
   99.8%。**原子不是杠杆，删掉本条。**
3. fp32 行是另一套代码（多轮整行 rescan，最多 8 趟），同样的病、不同的解。
   **部分已解**：`2bfddbb` 向量化 pass 2、`cd649a0`+`4baee61` 给它接上 chunked
   split（§2.5）。rescan 那条路仍在，且它与 §15 的地址模式关系未测。
4. chunked 路径的 static-k 行仍是 8 位粗层，未享 coarse12。
   **2026-09-14 降级**：本条假设"8 位粗层要重扫"是瓶颈，而 §15.6 说明
   大 batch 长行的瓶颈是 CTA 数、与粗层宽度无关；小 batch 长行走 split。
   在拿到"重扫确实发生"的计数之前，保持"未测"。



**另外两条 2026-09-14 收回的判断**（过程见 plan §13/§14）：

- §4 原文把 `b4096-v16384-k512` 的绑定写成"per-CTA 依赖链 + 串行化共享原子，
  12 位粗层把桶从 4,686 降到 203 正是收益大头"。**后半句对，前半句的归因错**：
  消融 C/D 显示 refine 块与 pass 1 的原子都量不出来，桶缩小之所以有用，是因为
  它让**暂存/refine 的集合**缩了，而不是因为省了原子发射。
- **口径更正**：本节原先把该格的实际 DRAM 算成"逻辑单趟 206 × 2 趟"。
  两趟**不是同一份字节**（pass 2 只重读在阈值附近的那部分），所以那个乘积
  从根上不成立；逐相的实测见 §14.2。

## 6. 走过的弯路（别重复）

| 实验 | 结果 |
|---|---|
| 固定加大 arena 到 24 KB 消溢出 | 官方 1593.7 → 960.7 µs。**被 coarse12 取代**（同样效果、不动 smem 预算），且固定加大会在 topk ≥ 2048 掉 occ |
| 在 C500 上把 FP8 路径的性能当调优依据 | 无效：C500/C600 的 FP8 是软件模拟 |
| "官方表数据到不了 arena" | **错的**。已在 `4cd740a` 的 commit message 里更正；官方表自己的数据在 8 位粗层下每行都溢出 |
| 8 shard 并行跑官方大表 | 会让 CUB onesweep 把设备打挂并连坐整机。**4 shard 串行** |
| 降低 `needs_long_row_bf16` 的 `L` 门槛换 1024 线程块 | **更慢，不是更快。** 门槛 `L >= 60000` → `8192`（其余条件不变）实测：`b4096-v16384-k512` **0.78x**（765.7 → 978.9 µs）、`b4096-v32768-k512` **0.80–0.82x**、`b512-v16384-k512` **0.90x**、`b512-v32768-k512` **0.93x**；`b128-v32768`、`b256-v16384` 也各慢 ~6%。**唯一不受影响的是 `L >= 60000` 一侧**（`b4096-v65536-k512` 1.00x、`b8192…`/`b16384…` 均 ~1.00x）——但那几格两个变体本来就都走 1024，本就没被改到。 |
| 抬高 `needs_long_row_bf16` 的 `B` 门槛（4096 → 16384） | **中性**。`b8192-v16384-k512` 1.00x、`b16384-v16384-k512` 0.99x、`b8192-v65536-k512` 1.00x、`b16384-v16384-k1024` 1.00x。代价为零，收益也为零 —— 可留作 reshape，不值得单独立项。 |

**"512 线程首波只填 25%" 这条不能推出"该换 1024"。** 2026-09-14 的两个 A/B（同
session、同种子、每格 15 rep 取中位数、两侧都过契约检查）把这条否掉了，且方向是**反的**：
1024 线程块在 `L < 60000` 全域**慢 10–22%**，batch 抬到 16384 也没有出现"波形表预测的
收益"。说明短行区间绑定的不是"C 里并发不够"，而是每行的**依赖链长度**——用更宽的 CTA
去摊它，只是让同一行摊得更薄。`L >= 60000` 那道门槛是实测出来的，不是估的。

**不过要如实记一条边界**：同一次 A/B 里 `b4096-v65536-k512` 两种块宽都是 ~2310 µs，
而 §2.3 的账记该格 8 位层 → coarse12 是 **2865.6 → 2863.7（1.001x）**，两者对不上；
且同一格在两次会话间重现到 ±0.2%。所以 **`L >= 60000` 这一侧的二分点还没被独立量过**，
上面那句"门槛是实测出来的"只覆盖 `L < 60000` 一侧。要动这一侧，先复现 §2.3 的数。

（复现：`/tmp/dsab/ab.py`，两侧 `.so` 存 `/tmp/dsab/{base,candA,candB}.so`，
