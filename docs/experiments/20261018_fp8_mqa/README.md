# FP8 MQA(DSA indexer)在 C600-U 上的 top-K：分析与天花板测量

日期：2026-10-18。设备：MetaX C600-U(28 AP,sm89,family 1600)。树：`cae657e`(P6 之后)。
探针：`fp8_pass1_ceiling.cu`；原始输出：`probe_raw.txt`。

## 0. 问题

DSA indexer(DeepSeek V3.2 起为 FP8 MQA 形态）若把 **fp8(e4m3)logits 直接**交给
`deep_select.topk`，选择器需要一个 fp8 行路径。本文回答三个问题： naive 移植在这张卡上
跑多快、瓶颈在哪、收益点在哪。

**契约前置问题（gate）**：调用栈给选择器的是 fp8 logits 本身，还是已反量化到 bf16 的
logits？若是后者，本方向整体不需要。本文假设前者。

形状（decode 为主）：`B = 1..512` 行(= query token 数)，`V = 64K..131K+`(= 历史 token
数),`k = 2048`。基线快照（`perf_data/MetaX_C600-U/20261018_152134`）里这些 cell 的现状：

| cell | dtype | us | GB/s |
|---|---|---|---|
| b1-v131072-k2048 | bf16 | 75.8 | 3.6 |
| b1-v262144-k2048 | bf16 | 121.3 | 4.4 |
| b64-v131072-k2048 | bf16 | 124.4 | 139.1 |
| b128-v262144-k2048 | bf16 | 324.9 | 209.8 |
| b512-v262144-k512 | bf16 | 697.1 | 386.6 |

小批量是延迟/并行度受限（b1 = 28 个 AP 用 1 个 CTA，单行走私）；大批量才轮到吞吐问题。

## 1. 实测：pass 1 直方图的天花板

行核 pass 1 是"每元素一次共享原子自增的 256 桶直方图"(bf16 取键高 8 位；fp8 的
e4m3 保序编码后整个键就是 8 位——**同一结构，桶数不变，每 16B 加载的原子数从 8 涨到
16**)。探针在 256 MB 流式缓冲上、224 CTA × 512 线程下测得:

| 臂 | 数据 | 时间 | 带宽 | 换算 |
|---|---|---|---|---|
| A 只读(4 个在途 uint4) | — | 191.5 µs | **1401.5 GB/s** | 本探针的墙(仓库专用探针测得 1545) |
| C 8 atomics/16B(bf16 现状) | 均匀 | 393.3 µs | 682.6 GB/s | = 341 G atomics/s |
| B 16 atomics/16B(naive fp8) | 均匀 | 743.9 µs | **360.7 GB/s** | = 361 G atomics/s |
| D 选票聚合(ballot 循环) | 均匀 | 149 ms | 1.8 GB/s | **死** |
| E 每 warp 复制 8 份直方图 | 均匀 | 744.2 µs | 360.7 GB/s | **与 B 逐拍相同** |
| C 同上 | 拥挤(7/8 同一桶) | 2307.2 µs | 116.3 GB/s | |
| B 同上 | 拥挤 | 4603.6 µs | 58.3 GB/s | |
| D 同上 | 拥挤 | 23.6 ms | 11.4 GB/s | 仍然死 |
| E 同上 | 拥挤 | 4603.6 µs | 58.3 GB/s | **零收益** |

读出的规律（与 C500 上 P4 的"冲突减 4 倍反而慢 38 µs"一致）:

- **共享原子是每元素发射率问题，与争用无关。** 两个臂反解出同一个上限:
  ~12.2-12.9 G atomics/s/SM(28 AP 合计 ~350 G/s)。均匀数据直接撞上它。
- 同桶串行(拥挤)再砍到 ~2 G/SM/s;warp 复制救不了——每个 warp 内部仍是 64 车道打
  同一地址。
- 选票聚合的每轮固定成本(ballot + shuffle wrapper + popc + 循环链）远超它省下的原子。

**推论一(naive 移植不可做)**:fp8 每元素 1 B,吞吐天花板 = 原子发射率本身 ⇒
naive fp8 pass 1 封顶 361 GB/s(均匀)/ 58 GB/s(拥挤),即墙的 23% / 4%。在大 batch 上
这是**绝对时间的回退**——字节数减半，吞吐更低于减半:今天 bf16 在 b512-v262144 已跑
386 GB/s(逻辑),naive fp8 反而更慢。

**推论二(墙为什么远)**:C500(104 AP)上同样的直方图曾贴近墙(94.9-97.9%),因为
每 AP 只需 15.9 GB/s ⇒ 7.9 G atomics/s,低于发射上限;C600-U 每 AP 要 55 GB/s 才到墙,
bf16 需 27.6 G/SM/s、fp8 需 55 G/SM/s——**这张卡上连 bf16 的 pass 1 在裸探针里都只有
墙的 48%**,fp8 只是把这个既有缺口放大到 4 倍。

## 2. 结构红利：fp8 独有、今天就能拿的三件事

1. **单层直方图，没有 refine/重扫。** 8 位键 = 256 桶就是整个键空间。bf16 路径的
   coarse12(12+4 位)二级结构、arena 容量守卫、overflow 重扫全部不需要；pass 2 是
   纯收集。内核更小、寄存器更宽余。
2. **NaN 检查免费。** e4m3 的 NaN 经保序编码后落在键空间两端(0x00 / 0xFF);pass 1 的
   直方图桶非零即投票，不需要独立扫描趟——对照今天 fp32 cell 上 NaN 扫描占 20-30%
   的现状，这是结构性减法。
3. **字节减半直接利好延迟受限区。** b1-v131072:bf16 行 256 KB → fp8 行 128 KB;在
   单 CTA 串行读已占不满的 regime 里，时间近半。

## 3. 收益点排序(杠杆)

1. **chunked split 的 fp8 arm(decode 形状的真正收益点)。** b1..b128 × V≥64K 的形状
   死在并行度(一行一个 CTA,28 个 AP 闲着 27 个),与原子发射率无关。split 已存在
   (bf16/fp32 两臂),fp8 arm 是 dtype 机械移植：一行切成 chunks 个 CTA 的段、段内选、
   再归并。这一步把 b1 的 3.6-4.4 GB/s 往墙的十分之一以上推——**10x 量级在这里**,
   不在直方图。
2. **采样阈值(pass 1 只直方图 1/S 的行)。** 唯一能减少"每元素原子数"的结构手段:
   按 1/64 跨步采样做直方图定阈值,原子成本降 64 倍,主趟只剩收集;漏阈用有界二次
   收集修补(上游 DeepSelect 的 random-block + compact 就是它的严谨形态)。这是
   **大 batch 的 lever**,也是一次真正的数据流改造,不是调参。
3. **若仍要全量直方图**:在 4.4 倍原子削减之前,任何指令级手段(选票、复制、bsm)
   都已实测无效——别再投。

## 4. 落地形态(若做)

- 内核:`common/radix_row_fp8.cuh`(共享实现),`value_dtype` 加 2;pass 1 单层 256 桶 +
  pass 2 收集 + NaN 折叠;对齐要求按字节不变(1024 B stride = 1024 元素)。
- chunked split 的 fp8 stage 与 bf16 stage 同构(radix_chunked.cuh 的模板轴加 dtype)。
- 实例化表:经 P6 的生成器 `family_instantiations(family)` 进入三族的
  `xcore<N>/instantiations/`;若 128 KiB 家族能摆更宽的块宽/更大的 chunk 集,
  那就是家族分化的第一个真实用例——**先测量,再分化**。
- 验证:官方门禁 + 本仓库的 fp8 合同行(值回读、min(selected) ≥ max(unselected)、
  NaN 哨兵);fp8 的 tier 关系用 `min/max` 合同验,不与 torch 逐位比。

## 5. Go / no-go 清单

1. 调用方确认:logits 以 fp8 到达选择器(而不是反量化后的 bf16)?——否则本方向不需要。
2. 分布确认:线上 fp8 logits 的桶拥挤度(决定"拥挤"臂 58 GB/s 是否是现实)。
3. 若两者成立:先做 chunked fp8 arm(低风险、decode 形状直接收益),用
   `tools/ab_snapshot.py` 在本机对同板基线(20261018_152134)出数;
   采样阈值单独立项。

## 6. 增补:线程内预聚合的证伪(同日,同一探针)

"一次 16B 加载内的同桶元素先在寄存器合并再发原子"是唯一没被 §1 否掉的聚合机制。
补测(`probe_agg_raw.txt`,新增 NormalFloat 实物分布与 12 位粗桶两臂):

| 臂 | 均匀 | normal~27% | 拥挤 87.5% |
|---|---|---|---|
| C12 bf16 plain,**4096 桶(现行 coarse12)** | **678.1** | **677.4** | 116.3 |
| F12 bf16 线程内聚合,4096 桶 | 427.4 | 428.0 | 425.5 |
| C bf16 plain,256 桶 | 681.5 | 264.2 | 116.4 |
| F bf16 线程内聚合,256 桶 | 344.6 | 345.2 | 345.3 |
| B fp8 plain,256 桶 | 360.6 | 133.5 | 58.3 |
| G fp8 线程内聚合 | 78.2 | 78.1 | 78.2 |

两条结论:

- **对现行 bf16 内核:聚合已死。** 现行 pass 1 是 12 位 4096 桶;NormalFloat 的"拥挤一个
  高字节"摊开成 ~16 个子桶,同桶串行自行消解(C12 在 normal 与均匀同为 ~678)。聚合臂
  的固定三角比较(28 次 ALU/8 元素)把它钉死在 ~427 GB/s,在生产分布下**输给现状
  37%**。第一次 8 位桶版本里 F 在 normal 下 +31% 的"胜利"是桶宽拿错的人造物——先核对
  现役桶宽再动内核,这条纪律这次省了一笔无用功。
- **对 fp8:键就是 8 位,没有 12 位稀释空间**,naive 在 normal 下 133.5 GB/s。采样阈值
  (§3 杠杆 2)是唯一活口。
