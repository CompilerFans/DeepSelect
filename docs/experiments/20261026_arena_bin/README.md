## 0. 结论

1. **网格 87,249.9 → 82,761.5 µs(0.9486)。** 按块直方图闸门
   (`topk <= length / 128`)分组才对得上:**放行的 69 格 0.9422**,不放行的
   48 格 **1.0089**(只有代码体积税)。其中 batch ≥ 64 的 52 格是 **0.9414**。
2. **收益集中在 V/k = 128–256 的关键形状**,这些格子带宽只有墙的 17–41%,
   是延迟受限而不是带宽受限,所以消掉的延迟直接换成时间:
   `b4096 V65536 k512` **2030.4 → 1809.1 µs(0.8910)**,
   `b4096 V131072 k512` **2661.0 → 2406.0(0.9042)**,
   `b4096 V131072 k1024` **3493.1 → 3145.5(0.9005)**,
   `b4096 V262144 k1024` **4997.0 → 4483.8(0.8973)**,
   `b768 V262144 k1024` **993.6 → 889.0(0.8947)**。
3. **长行的收益小一个量级**(`b4096 V1048576 k512` 0.9887、k1024 0.9522):
   那里 walk 已经把带宽推到 847 GB/s(墙的 54.8%),行内是带宽受限的稳态,
   同样的固定延迟节省被带宽吸收。
4. **只有 staging walk 可以打包,这是这次改动唯一的坑。** B1 把计数 walk 也打包,
   于是 `collect_one` 要对整行每个元素付一次打包,给 48 个根本不执行 staged 代码的
   格子加了 **2.94%** 的税(最大 `b4096 V65536 k1024` **+10.05%**);把布局绑在
   `staged` 上之后,这些格子回到 **0.9984**。
5. 寄存器不变(**52 MT**),ST **62 → 66**,栈 **0 B**,共享内存 2604 B。

## 2. 机制:walk 之后有三趟"按竞技场顺序回读行"

staged 臂在 walk 里把"bin ≥ 块切点"的元素按下标放进 `s_input_flat`,
同时只把**高字节**计进 256 bin 的 `s_histogram`。之后还有三个阶段要知道
每个元素的更多位:

1. 落点字节的 16 个子 bin(`(key >> 8) == high`);
2. 阈值 bin 的 4 位 nibble 直方图(`(key >> 4) == threshold_bin`);
3. emit(`key > / == emit_key`,两处)。

三个循环都写成 `refine_bin(__ldg(input + s_input_flat[i]))`。**竞技场里的下标是
原子序,不是行序**,所以每一次都是一个 2 字节的随机读:一行 256 KB–2 MB,
每个 staged 元素一条 cache line,谁也帮不了谁。

可是这三段问的位 walk 早就知道 —— 那正是它把元素放进竞技场的原因。
12 位 bin 就是 `key >> 4`,于是:

- `bin >> 4 == key >> 8` — 第 1 段不再需要行;
- `bin & 15 == (key >> 4) & 15`,而 `bin > / == coarse_threshold` 与旧的
  `key > / == emit_key` 的高位判断等价(低位由 `nibble` 子句补上)— 第 3 段
  除了并列 bin 自己也不再需要行;
- 第 2 段仍是 bin 的成员,那是 bin 不携带的唯一字段:先比 bin,**只有**
  并列 bin 的成员回读。

所以每个 staged 元素的随机行读从 **3 次降到 0 次(并列 bin 的成员 2 次)**,
三个循环之间也不再有三趟共享读之间的依赖。

量化:`b4096 V131072 k512` 的行内固定项是 11.6 µs(`11.6 + 8.23 × V/131072`,
见 `20261025_row_walk`),这次省下 **1.74 AP-µs/行**,即固定项的 15%;
而该格的带宽只有墙的 28.9%,省下的时间不再被带宽吸收。到 V=1M,walk 占整行
69%,带宽 847 GB/s(墙的 54.8%),同样的固定项节省就只剩 1%。

## 3. 边界:下标字段 20 位,超出就退回裸下标

打包格式是 `(bin << 20) | idx` —— 12 位 bin 与 20 位下标正好用满一个
`uint32_t`。`length > 2^20` 的行(`fits_packed == false`)不打包,所有循环
回到"按裸下标回读行",与改动前的行为逐位相同。

这个边界是能走到真代码的:`s_input_flat` 只有 4096 项,而 vocab 的上限远大于
2^20,所以正确性必须在两侧都验。用 `tests/test.py` 的 `run_testcase`
(先校验后计时)在落地产物 `de449698` 上跑了六个点,每个点 3 轮:

| batch | vocab | topk | 路径 | 结果 |
| ---: | ---: | ---: | --- | --- |
| 2 | 1048576 | 512 | 打包(2^20 恰好在内) | True |
| 2 | 1048640 | 512 | 裸下标 | True |
| 2 | 1048576 | 1024 | 打包 | True |
| 2 | 1048640 | 1024 | 裸下标 | True |
| 4 | 1050624 | 512 | 裸下标 | True |
| 1 | 2097152 | 512 | 裸下标,2 倍字段宽 | True |

同一条闸门也覆盖了 staged 溢出:竞技场装不下时 `staged` 为假,计数 walk
自己填竞技场(写裸下标),`packed = staged && fits_packed` 让它对读者也是假,
读者回读行 —— 与改动前一致。

## 4. 被弃的中间版:布局属于 arm,不属于内核

B1 把 `packed` 直接取 `fits_packed`,于是**计数 walk 的 `collect_one` 也要
打包**:它对整行每个元素各算一次 bin(原来只算一次 nibble 掩码)、写一个
打包字,四个读者各多一次选择。后果按闸门分组一目了然:

| 分组 | B1/A | B/A |
| --- | ---: | ---: |
| 全部 117 格 | 0.9541 | 0.9486 |
| 放行闸门 | 0.9500 | 0.9458 |
| 不放行(48 格) | **1.0294** | **0.9984** |
| `b4096 V65536 k1024` | **1.1005** | 1.0233 |

放行的格子上 B 还更快(0.9458 对 0.9500),因为 staged 臂里本来就只有它需要
打包;不放行的格子被 `collect_one` 的每元素税吃掉了 3%。**改的是"哪些循环
可以免掉行读",那是 staging walk 的性质,所以布局跟着 arm 走**,而不是跟着
"下标放得下"这个全局事实走。

## 5. 代码体积:这一版没有把它压掉,只是压小了

A → B 产物 **+274,432 B**,48 个不执行这段代码的格子合计 **1.0089**
(`b4096 V65536 k1024` +2.3%)。这是这个内核的固定规律(见
`20261026_table_batch` §4):往 block-hist 体里加代码,会给根本不进那段代码的
格子加一笔体积税。和上一个提交叠加起来,这批格子现在累计约 +1.8%。

这笔税换到的是放行闸门的 69 格 **−5.8%**、关键形状 **−8~−11%**,按总账是
78.9 ms → 74.4 ms。
