# 组内 max 树与 block_max 存储:五个形状的否证,以及"存储的价钱与地址空间、缓存策略都无关"(2026-10-26)

设备:MetaX C600-U(28 AP,family 1600,MACA 3.0.1436.20261017,
torch 2.10.0+metax20261017.1120),设备 1。

本目录两个探针都是独立程序,不经 torch、不经本树的构建系统:

```bash
cucc -O3 -std=c++20 --offload-arch=xcore1600 walkprobeN.cu -o /tmp/p
CUDA_VISIBLE_DEVICES=1 /tmp/p
```

两者都是生产摘要 walk 的形状(ADJ4、BLOCK 1024、一行一 CTA、每线程每轮四个 `uint4`),
1120 行 × 1048576 元素 bf16 = 2.35 GB。本记录里的每个数字都是隔离 walk 的时间,不是整
算子的;核内的数字一律引自 `docs/experiments/20261026_stage_instead_of_collect/` 与
`docs/experiments/20261025_row_walk/`。

| 探针 | 问的问题 |
| --- | --- |
| `walkprobe2.cu` | 组内 max 树有没有更便宜的形状 |
| `walkprobe3.cu` | `block_max` 那 9 个点的价钱属于哪一层 |

## 0. 结论

1. **两个"更便宜的树"都被否证,而且是大幅否证**:两块 12-bit bin 打包进一个 shuffle
   字(每步一次 SWAR max 代替两次 select,shuffle 数减半)只有 **66.1%** 读墙;把映射
   改成"每 lane 覆盖半个块、一次 `row_shl:1` 收完"只有 **62.5%**。生产者形的 79.1–79.3%
   两个都够不着。
2. **探针第一次把"树"和"存储"分开计了价**:纯 key+max 98.3%,只加存储 89.7%(−8.6),
   只加树 79.3%(再 −10.4)。上一份记录里这两个是合在一起叫"树+存储"的。
3. **存储的价钱不属于内存系统**:同样的四条存储写共享内存 **86.0%(更慢)**,给表指针加
   `__restrict__` 89.5%(不动),非临时存储 `__stcs` 89.8%(不动),行读改流式 `__ldcs`
   98.7%(不动)。所以它是"四分之一 lane 上的四条谓词存储"这个**指令形状**的发行代价,
   换地址空间、换缓存策略、去掉别名假设都买不回来。
4. **更粗的表不是交易,是换债**:把表从每 64 元素一项改成每 256 元素一项,存储降到 1/4,
   但被保留的组每多读 4 倍行(候选计数不变、组宽变了),正好抵消 `bd8c3db` 刚拿到的
   那块。这是推算,没有测;记在这里是因为它是这条路上下一个会被人想到的形状。
5. **隔离探针对 walk 已经没有信息量了**。隔离上存储值 −8.6、树值 −10.4,可核内把四条
   2 B 存储合成一个 `uint2` 是 **0.9991×**(上一份记录),今天也没有任何一个形状能在隔离
   上把生产 body 的 79.3% 推上去而不破坏 16 B/lane 的读模式。**walk 的下一步必须是核内
   A/B(`tools/ab_snapshot.py`),不能再从隔离数字外推。**

## 1. 树的形状(`walkprobe2.cu`)

| 臂 | 形状 | ms | GB/s | 占 1545 读墙 |
| --- | --- | ---: | ---: | ---: |
| a0 | 只读 | 1.669 | 1407.4 | 91.1% |
| a1 | + 有序 key 变换与 lane 内 max | 1.558 | 1507.8 | 97.6% |
| a2 | + 生产树(每块三次链式 `mov_shfl`)+ lane 0 四条存储 | 1.921 | 1222.7 | 79.1% |
| a3 | a2 + 走完 walk 之后的块计数循环 = **生产 body**(窄行) | 1.994 | 1177.9 | 76.2% |
| a4 | 两块打包进一个 shuffle 字,每步一次 SWAR max | 2.300 | 1021.2 | 66.1% |
| a5 | 每 lane 半块,一次 `row_shl:1` 收块 | 2.431 | 966.2 | 62.5% |
| a6 | a1 + 只存储(存 lane 自己的 max,不存块 max) | 1.716 | 1369.0 | 88.6% |

a4 输在 SWAR max 本身:`vmaxu2_swar` 是 9 条整数指令(两次与、一次减、一次移位、
一次乘、两次与、一次或),而它替下的是两次 select;省下的 6 次 shuffle 不够付这 6 条
多出来的 ALU。`__vmaxu2` 在这套工具链里也是软件模拟
(`__clang_maca_simd_functions.h:631`,两次解包 + 两次比较选择 + 合位),不是视频指令,
所以打包这一路没有硬件可借。

a5 输在读模式:一个 lane 一次读 64 B,wave 内相邻 lane 的地址间距就是 64 B,即本仓库
已经记过的 `tx * 4 + q` 反模式。**一个块 128 B、一个组 8 lane,意味着每个 lane 每次
指令只能拿 16 B;任何"每个 lane 多拿一点、少几个 lane 参与"的重排都会把指令的扇区数
翻倍。** 这条约束把树的形状空间基本关死了。

## 2. 存储的价钱(`walkprobe3.cu`)

| 臂 | 形状 | ms | GB/s | 占 1545 读墙 |
| --- | --- | ---: | ---: | ---: |
| b0 | 只读 | 1.682 | 1396.5 | 90.4% |
| b1 | + key 变换与 lane 内 max | 1.544 | 1521.3 | 98.5% |
| b2 | + lane 0 四条 `uint16` 存储到全局 | 1.694 | 1386.4 | 89.7% |
| b3 | b2,表指针 `__restrict__` | 1.698 | 1383.4 | 89.5% |
| b4 | b2,存进共享内存 | 1.765 | 1330.7 | 86.1% |
| b5 | b2 + 生产树 | 1.917 | 1225.0 | 79.3% |
| b6 | b4 + 生产树 | 2.011 | 1167.9 | 75.6% |
| b7 | b1,行读用 `__ldcs` 流式 | 1.541 | 1524.3 | 98.7% |
| b8 | b2,存储用 `__stcs` 非临时 | 1.693 | 1387.6 | 89.8% |
| b9 | b5,存储用 `__stcs` | 1.918 | 1224.5 | 79.3% |
| b10 | b5,行读 `__ldcs` + 存储 `__stcs` | 1.918 | 1224.3 | 79.2% |

**共享内存更慢,不是笔误。** 表在共享里省掉的是全局写,但在 1024 线程的行上表和
`s_wide`(16 KB)抢同一份每 AP 共享,而且实际核里 `block_max` 是每行一张、跨相位读
(计数循环、建表),搬到共享要么缩小占用要么改动跨相位契约。b4/b6 说明即使不看这些,
**光是"lane 0 四条谓词存储"在共享上就更贵**,所以"把表搬进共享"这条路连收益上限都
不成立。

`__stcs` 在这套工具链上是真的(`__builtin_metaxgpul2rp_nontemporal_store`,
`__clang_maca_device_functions.h:3575`),`__stw t` 则只是普通存储的别名(同文件 3742),
所以这里只测了 `__stcs`。它一分钱没省,和 b3、b4 一起把"存储贵在内存系统"这个假设
三个方向都排除了。

## 3. 两件从数字里读出来的事

- **只读比"只读 + key 变换"慢**(b0 90.4% vs b1 98.5%,两份记录各测一次:上一份
  91.8/99.2)。这不是笔误:纯读臂的累加链极短,而 key 变换给每个 lane 一串互不相关的
  整数活,反而把更多 load 留在途上。也就是说**这台机器上 walk 的读是延迟受限、不是
  带宽受限**,任何"少算一点"的方向都要先过这一关。
- **测量间波动 ≤0.5 个百分点**,跨两次独立构建(`b0` 91.1/90.4,`b2` 89.7/89.7,
  `b5` 79.3/79.3),足以分辨今天这几个差值,但不足以分辨核内 1% 级别的改动 —— 这也是
  结论 5 的另一半理由。
