## 0. 结论

1. **块直方图臂的块计数不该在 walk 里做。** walk 每个块首 lane 打 4 个共享
   原子,那些原子打断的是 load 循环的流水;把计数挪到"walk 写出的摘要表上
   的独立循环"后,窄行(512 线程)的长行格全线变快(交付版 `3bbe39ec3116`
   对 base `883fcf249b74`):`b4096 V1048576 k512`
   **11113.0 → 10395.0 µs(−6.5%,772.96 → 826.35 GB/s)**,
   `b512 V1048576 k512` −5.3%,`b256 V1048576 k512` −4.5%,
   `b256 V131072 k512` −1.0%,`b4096 V131072 k512` −0.6%。
2. **同一个改动在宽行(1024 线程)上是净损失,幅度 17–38%**(`b128
   V1048576 k1024` 1.3785、`b64 V131072 k512` 1.2882)。原因不是数据流,
   是寄存器:模板体的第二份拷贝把宽行 kernel 从 60 MT 推到 68 MT,跨过
   **每线程 64 MT** —— 1024 线程 CTA 两个每 AP 的那条线(131072/2048)——
   于是 b64/b128 的格子从 2 CTA/AP 掉到 1。
3. **所以交付版把表计数限定在窄行**(`BLOCK_SIZE == kBlockSize`),宽行
   保留原来的 in-walk 计数,并且**保留它原来调用的那个 walk**
   (`kHist=false`)。交付版在 23 格切片上逐格中位数 **1.0000**(工具汇总行
   0.9994),1024 线程的每一格 0.999–1.003(即完全不动),512 线程且闸门
   触发的格 0.9354–0.9945。
4. **walk 与计数循环之间必须有 `__syncthreads()`**,见 §3.1:计数循环读的是
   别的线程写的表项,去掉屏障的版本在 512 线程行实例化上进
   `Memory Violation(0x4)`,而且它不走 suite 的 `crash` 通道,直接
   `std::terminate` 带走整个进程。屏障不改变读数(§4,与无屏障版逐格同值)。
5. **不触发的短行没有回归**(`b4096 V1024/4096/16384/65536` 0.998–1.002),
   因为闸门是密度(`topk <= length/256`)。
6. 闸门后的宽行读数是 **60/52 MT**,与 base 逐字节相同;窄行 62 MT,
   与改前相同(§3 表)。

## 1. 机制

pass 1 在块直方图臂上写的是一张**块摘要表**:每个 64 元素块的 max bin
(`block_max`)。改前,写表的那个 lane 顺手对同一个 bin 打一个共享原子,所以
walk 的 load 循环每块被 4 个 `atomicAdd` 打断(一次 4 个块,由 8-lane 组覆盖)。
改后 walk 只写表,计数由 walk 之后的独立循环做:

```cpp
for (uint32_t b = tx; b < nb; b += BLOCK_SIZE)
    atomicAdd(&s_wide[block_max[b]], 1u);
```

这第二趟读的是刚写出来的表,量是 `nb` 项(行长/64),不是行;表在 L2 里。
计数直方图的定义没有变 —— 它仍然是"每块的 max bin 计一次" —— 变的只是取数
的位置。

## 3. 闸门:寄存器预算决定 block 宽度

`mxcc --resource-usage`(本仓库的编译参数,`xcore1600`):

| TU | base | ungated | wrong-gate | gated |
| --- | --- | --- | --- | --- |
| `block_1024 si0_rv0_sv0_pre0` | **60** MT / 64 ST | **68** / 64 | 39 / 64 | **60** / 64 |
| `block_1024 si0_rv0_sv0_pre1` | 52 / 62 | 60 / 62 | 38 / 62 | 52 / 62 |
| `block_512 si0_rv0_sv0_pre0` | 62 / 64 | 62 / 64 | 62 / 64 | 62 / 64 |
| `block_512 si0_rv0_sv0_pre1` | 58 / 60 | 52 / 60 | — | — |

栈帧全部 0 B(48 B 地板以下),没有 spill。

算术:1024 线程的 CTA、每 AP 2048 线程、131072 寄存器/AP —— 两个 CTA 要求
**每线程 ≤ 64**。base 60 在线内,ungated 68 在线外,于是宽行的 b64/b128 格
(64/128 行铺在 28 个 AP 上,2 CTA/AP 时是 1.15/2.3 波,1 CTA/AP 时是
2.3/4.6 波)正好是这条线的受害者。窄行 512 线程、每 AP 4 个 CTA,62 MT
远在线内,所以它对第二份体没有感觉 —— 全网格里 512 线程也没有一格回归。

因此交付版的门是 block 宽度,不是 batch 或密度:只有 `BLOCK_SIZE ==
kBlockSize` 的实例化走表计数,宽行保留 walk 内计数。

**这一步的陷阱,记下来免得重犯**:第一版闸门把宽行的 block-hist 臂落进了
`summary_walk<kHist=true>`(元素直方图,每块 128 个原子),而不是它本来
该走的 `kHist=false`。读数是 39 MT —— 看起来"比 base 还轻" —— 但触发格
1.17–1.35×,因为那根本不是同一个数据流。闸门要恢复的不是寄存器数,是宽行
**原来那条路径**,所以判断标准只能是:宽行实例化的 MT/ST 与 base 逐项相同
(60/64 与 52/62),且有读数的格 0.997–1.004。

### 3.1 交付前修的竞态:计数循环前必须有屏障

`block_max` 是 walk 写的,读它的是 walk **之后**、由 `tx` 步进的独立循环;
第 `b` 项由哪个 8-lane 组写、由哪个线程读,两者没有任何对应关系,而 walk
对表的写在组与组之间没有任何顺序保证。第一版闸门版没有 `__syncthreads()`,
设备上的表现是:

```
trapping: kernelName: _ZN11deep_select17topk_kernel_radixINS_15TopkRadixConfig
  I15__maca_bfloat16iLi512ELb0ELb0ELb0ELb0EEEEEvNS_9RowParamsE
  ,commandIndex: 17562 ,trapType: Memory Violation(0x4)
terminate called after throwing an instance of 'c10::AcceleratorError'
```

即 512 线程行实例化的共享/全局越界访问。它在 suite 里的形态要单独记:
`c10::AcceleratorError` 不是 `torch.cuda.OutOfMemoryError`,从状态循环的
`except Exception` 里逃出去之后直接 `std::terminate` —— 也就是这个故障
**不会**被记成 `crash`,进程连同状态表一起死,读起来像"进程被杀"
(handover §4 的进程级死亡那一类)。所以这条路径上的"suite 提前结束"
要先怀疑计数循环的屏障,而不是先怀疑环境。

屏障是规则:walk 写 `block_max[b]`,循环读全部 `b < nb`,中间必须有 CTA 级
同步。交付版 `3bbe39ec3116` 就是闸门版 + 这一行。

## 6. 没有声称的东西

- **只测了 xcore1600。** `common/` 进每个 family 的产物,所以 xcore1000 /
  xcore1500 的 512 线程行实例化同样换代码,没有测;宽行实例化与 base
  同源同读数(§3),这是唯一能替其它 family 说的话。
- **没有路由变化。** 所有格两边都是 `row`;fp32 行、chunked split、
  coarse12 臂都不经过这个 walk。
- **23 格切片是刻意选的矩阵**(2 个 block 宽度 × 触发/不触发 × 3 个 V ×
  2 个 topk),不是 122 格的全部;全网格的读数在 §2,用的是未交付的
  ungated 产物,只用于说明代价在哪里。
- **没有动第二趟 walk、arena 和阈值逻辑**;`bd8c3db`(staged walk)的
  结论与这个改动正交。

## 7. 一个未解释的读数,不在这个改动的路径上

闸门版(带屏障之前)的一次 seeded suite 在**第 1 格**报了 `topk condition`
不一致:121 行里 15 行。这一格是 `b121 V682965 k1`,bf16、
`UniformUInt(0, 0x1000)`、带 `end` 与 `output_idx_offset`、`sorted_index`。

它不经过这个改动:121 行 < `kC600UNarrowRowBatches`(256),所以走 **1024
线程**实例化,而闸门把表计数只放进 512 线程实例化 —— 两个 1024 TU 的读数
与 base 逐项相同(60/52 MT,§3)。

排除的读数:同一格(seed 0,与 suite `_counter` 的首格同数据)在两臂上各跑
**48 次**(8 seed × 2 轮 + 16 seed × 2 轮,设备 0,`/root/hunt2.py`)全部
pass;带屏障的交付版上 seeded suite 第二、三遍与 sample gate 一遍全绿。所以
按现有证据这是一次**罕见的、不可复现的**读数,没有定位到原因;记在这里,
不当作已解决,也不当作这个改动的证据。
