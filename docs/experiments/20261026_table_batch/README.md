# 块表读的批量化:长行 −1.5%,短行按代码体积加税(2026-10-26)

设备:MetaX C600-U(28 AP,family 1600,MACA 3.0.1436.20261017,
torch 2.10.0+metax20261017.1120),设备 1。同一 pod 同一时段,两次构建只差
`radix_row_bf16.cuh` 里那两个读 `block_max` 的循环:

| 产物 | 源码 | md5 | 大小 |
| --- | --- | --- | --- |
| A(改动前) | `6d6298e`(`3613249` 只加文档) | `e45d9c2c0ae2` | 20,143,512 B |
| B(改动后) | 同上 + 批量化 | `654d4f7c2f2af0` | 20,368,792 B |
| A2(对照) | 与 A 同源,独立重建 | `49c4f01de876` | — |

两次都用 `CUCC_TARGETS=xcore1600 ./develop.sh`(`rm -rf build` 之后),然后
`python tests/test.py --perf-only -nc --dtype bf16`(117 格,每格先校验后计时,
每个产物两轮;五次运行全部 117/117 通过)。

## 0. 结论

1. **改动只在 `nb` 大的格子上生效,并且在那里的确是净收益。** `V >= 65536` 的 79 格
   合计 **0.9899**;`b4096 V1048576 k512` **10,408.9 → 10,251.8 µs**
   (825.2 → 837.9 GB/s),`b4096 V524288 k512` 0.9878,`b4096 V262144 k512` 0.9861,
   `b768 V1048576 k512` 0.9834,`b256 V1048576 k1024` 0.9760。
2. **它在根本不执行这段代码的格子上反而变慢,而且不是噪声。**
   `V < 65536` 的 38 格合计 **1.0096**,其中 `b6 V4096 k512` **+7.2%**、
   `b6 V16384 k512` **+4.8%**。这些格子的 `summary_wanted` 为假
   (`vocab_size < kSkipMinVocab`),宿主根本不分配 `block_max`/`block_list`,
   两个循环一次都不进 —— 变的只有产物体积(+225,280 B)与内核里多出来的那段代码。
3. **对照构建证明这不是"两次构建本来就有这么大差别"。** 同源独立重建 A2 对 A1:
   117 格合计 **1.0021**、中位数 **1.0000**、p10/p90 **0.9954/1.0050**,
   与同产物两轮的自噪声(A `0.9991`、B `1.0003`,p10/p90 各约 0.994/1.004)同量级;
   而在 B 退化的那些格子上 A2/A1 全是 0.987–1.010。所以退化是这次源码改动带出来的,
   不是构建抖动。
4. **两个循环真正的成本是原子,不是读。** 孤立探针里(`nb=16384`,1120 行,512 线程)
   把共享原子拿掉是 `0.301 → 0.087 µs/行`(3.5×),而把读批量化只是
   `0.410 → 0.333`(1.23×);把单一计数器拆成 8 个 per-wave 计数器只到 `0.323`,
   说明瓶颈是**每次原子的发射率**,不是同一个地址上的竞争。再往下只剩
   "少发原子"这一条路,而块数是 `nb` 定的,所以这一版能拿到的就是这 1.2–1.5%。

## 2. 这张表为什么值得动:阶段划分

`clock64()` 在现行内核上打点(一行一 CTA,512 线程,`radix_topk_row_bf16_b<512,true,true>`,
1120 行;探针程序在 `docs/experiments/20261025_row_walk/` 的注入器基础上改锚点)。
两格各自占整行的比例:

| 阶段 | V=1048576 k512 | V=131072 k512 |
| --- | ---: | ---: |
| pass 1 摘要 walk | 69.0% | 31.4% |
| **保留块列表构建** | **8.1%** | **6.4%** |
| **从表里数块直方图** | **7.5%** | **3.4%** |
| pass 2 walk | 6.7% | 32.2% |
| refine/emit | 2.2% | 6.5% |
| 清零直方图 | 1.9% | — |
| scan #2 | 1.6% | 6.6% |
| collect | 1.2% | 4.4% |
| scan #1 | 1.1% | 5.4% |
| pass 2 尾 | — | 2.1% |

两个读表的循环在 V=1M 上一共 15.6%,是 walk 之外最大的一块,所以先动它们。
注意这两段的比例**高估了循环体本身**:孤立探针里同样 `nb` 的循环只要
0.3–0.4 µs/行,而内核里这两段合计 43+40 k cycles/行 —— 差的那部分是与别的
CTA 共享 AP、以及段与段之间没有访存可以重叠的串行时间。

## 3. 孤立分解:为什么"批量化"就是这里能拿的全部

`nb = 16384`,1120 行,512 线程,同一个循环的五种写法(µs/行,5 轮取最小):

| 写法 | nb=16384 | nb=2048 |
| --- | ---: | ---: |
| 标量 + 原子(改动前) | 0.410 | 0.082 |
| 批 4 + 原子 | 0.333 | 0.072 |
| 批 8 + 原子 | 0.301 | 0.085 |
| 批 8,不写(只数) | 0.087 | 0.053 |
| 纯读(标量) | 0.174 | 0.047 |
| 批 4 + 每 wave 一个计数器 | 0.323 | — |

读数:去掉原子 3.5×,批量化 1.23×,拆计数器只多 3%。所以内核里那 1.5% 基本就是
这个形状能给的全部,再往下必须减少原子**次数**,而不是让原子更便宜。

块直方图那一半也验过同一条:`nb=16384` 上把块最大值换成真实行会产生的那种分布
(64 个正态的最大值,只落在 256 个高字节中的 2 个、最密的那个占 77.6%),
对比均匀铺满 4096 个 bin,只慢 **11%**(0.424 → 0.470 µs/行)。所以连
"热点 bin 上的原子冲突"都不是主项 —— 就是 16,384 次共享原子的发射率,
而次数等于块数。要用更少的原子只能减少块数(块变宽),那是 pass 2 要付的账,
`20261026_density_floor` 已经量过它在这个形状上是负的。

## 4. 短行的账:代码体积是这个内核的一等成本

`b6 V4096 k512` 11.3 → 12.1 µs,读 49 KB,4.1 GB/s —— 与带宽无关,整格由
内核启动和定长前导决定。这类格子对内核的代码体积敏感:同一份源码重建两次
(A vs A2)不动它(1.0000),而多出 225 KB 产物就动它 7%。

也就是说,往这个内核的 block-hist 体里加代码,会给 38 个根本不执行那段代码的
格子加一笔固定税。**要加,就得换回足够大的收益**;1.5% 的长行收益配 7% 的短行
代价是这笔账里最有争议的一笔,记录在此以便下一次按同一把尺子衡量。

## 5. 寄存器与栈

`mxcc --resource-usage` 对两版编译
`value_bf16_outidx_i32_block_512_si1_rv0_sv0_pre1.cu`,读数完全相同:

```
Used  52 MTregisters, 62 STregisters, 2604 bytes shared mem
 0 bytes stack frame
```

所以短行的退化不是寄存器或占用率,只能是代码布局/指令缓存。
