# C500 — DSA decode 的相位拆分（Phase 0）

**问题**：C500 的 DeepSelect 离 1,650 GB/s 读墙差得远（官方网格中位 15.3%）。
ledger §4 已把病灶定位到 **CTA 数**（把 pass 1 循环抠成独立核，只改 CTA 数：
4096 → 1646.4 GB/s，104 → 921.3 GB/s）。本战役的目标 regime 是 DSA decode：
`bs × head` 行、长上下文、`b` 很小。本目录是它的**相位拆分**——每个内核各占多少，
以及不属于任何内核的那部分有多大。

**设备**：MetaX C500，`CUDA_VISIBLE_DEVICES=2`，`sm_count=104`，
MACA 3.7.0.36。跑之前 `pgrep -af python` 为空、四张卡 Available（独占）。
**被测产物**：`825e6a8` 重建的 `deep_select_maca_xcore1000.so`（`develop.sh`
三族全建，`BUILD_RC=0`）。
**形状**：`825e6a8` 新补进官方网格的 27 个 DSA 格
（`b ∈ {1,64,128}` × `topk ∈ {512,1024,2048}` × `V ∈ {131072,262144,1048576}`）。
**复现**：

```bash
CUDA_VISIBLE_DEVICES=2 PYTHONPATH=$PWD:$PWD/tests \
  python3 docs/experiments/20261009_c500_dsa_decode/probe.py \
  > phase_split_raw.txt 2>&1
```

原始输出：`phase_split_raw.txt`（每格每个命中的内核名与时间都在里面，未聚合）。

## 方法 —— 两个钟，以及三个必须排掉的坑

- **逐内核**：`kernelkit.bench` 的 `BenchResult.time_ranges`（`bench.py:170`），
  与官方跑的是同一个调用（`tests/test.py:128`）。
- **e2e**：`scripts/perf_snapshot.py:118` 的 `wall_clock_time`。

三个坑，每个都由一个可核对的事实守：

1. **单位是秒，不是毫秒。** `_bench_kineto` 存的是 `time_range/1e6`，
   而 torch 的 `time_range` 是微秒 ⇒ **秒**。判据取同一条 trace 里的 8 GB
   冷 L2 `zero_()`：它必须落在 **~5,360 µs**（`bench.py:132`）。第一次跑我按毫秒
   读，所有内核小了 1000×，而那个 memset 读作 `5.37`——数字自己报的案。
2. **`nan_scan_kernel` 的名字里没有 `topk`。** 官方钟按 `"topk" in name.lower()`
   过滤（`tests/test.py:129`），于是 split 路径的 NaN 扫描**不在官方钟里**，
   而行路径的扫描是融进 pass 1 的（`c36222a`）。只按 `topk` 过滤会同时
   漏掉 11–21% 的时间、并把两条路径放在不同口径上比。本探针把
   `nan_scan` 也算作算子内核，并把官方钟单独打印出来对照。
3. **`wall_clock_time` 的两次调用之间不 flush**，`kk.bench` 每轮 flush。
   两者是不同的 cache 状态。所以判定用 `span`（`kk.bench` 自己 regime 下
   首尾算子内核的跨度），`wall` 只作参考列打印。

## 结果

27 格里 **只有 6 格走了 split** —— 门 `chunked_bf16_applies`
= `batches ≤ 64 && vocab ≥ 262144 && topk ∈ {512,1024}`
（`maca_topk.cu:717-721`）逐条卡住：`V=131072` 全走行核，`k=2048` 全走行核
（连 `V=1048576` 也是），`b=128` 全走行核。

## 判据（Phase 0 开工前写死，不许事后挪）

| 预登记判据 | 实测 | 结论 |
|---|---|---|
| `stage2 / Σ算子 ≥ 0.5` → 走 A | 最大 33.9%，b64 上 5.5–11.8% | **A 不成立** |
| `batches × chunks < 2 × sm_count` 且 stage1 占比大 → 走 B | b1: 1×16=16 < 208 ✓；b64: 64×16=1024 ✗ | **B 只在 b1 成立** |
| 没进 split 且是表上最差 → 走 C | b1 全族最差（0.1–0.2% 墙） | **C 成立** |
| `gap / e2e ≥ 0.5` → 停下来报告 | 行核 0.0%，split 1.2–8.7% | **不成立，继续** |

**A（并行 stage2）被实测否掉。** fp32 上 stage2 占 61–84%（ledger §8.5），
bf16 上不成立——**不要把这个结论跨 dtype 搬**。

## 本表新暴露出来的两件事

### 1. `b ≤ 104` 时，时间由**一行自己的串行链**决定，与行数几乎无关

行核在 `V=1048576, k=2048` 上（该 k 全是行核，是干净的单翼对照）：

| b | 1 | 64 | 128 |
|---|---|---|---|
| span µs | **699.29** | **775.65** | 1012.86 |

**1 行 699 µs，64 行 776 µs。** 加 63 倍的行几乎不花时间，因为 64 个 CTA 全在
并行，而每个 CTA 自己要做完 `load → key transform → compare → shared atomic`
这条链（ledger 的 roofline 判定就是"per-CTA dependency chain"）。
**所以"再加 CTA"对小 batch 不是把行铺开——行已经全铺开了；是把一行切开。**

### 2. split 在这个 regime 上**可能是负收益**，但本表无法直接判定

`b64 V262144 k512`：split 353.36 µs。同行核路径的等价格不存在（门挡住了），
只能外推，而**外推正是 ledger §9.2 记录过的那类错误**（"a controlled microbench
does not transfer"）。两个方向的外推给出相反答案：

- 按 `b64 V131072 k512 row = 82.92` 与行核的 V-伸缩（b128 上 V×2 → 1.72×）
  推 `b64 V262144 row ≈ 143 µs` ⇒ **split 慢 2.5×**。
- 按 `b1 V1048576 k2048 row = 699` 推 `b1 V1048576 k512 row ≈ 453 µs`
  ⇒ **split（127 µs）快 3.6×**。

**两个外推不可同时为真，说明外推本身不可用。** 判定必须直接测：把
`chunked_bf16_applies` 在**一份拷贝**里改成 `return false`，两臂同 session 交替跑
（`tools/ab_snapshot.py`）——这就是下一节的 A/B，也是 Phase 1 的第一个动作。

## Phase 1 —— 直接测，不外推

Phase 0 留下的问题（split 在这个 regime 上到底是正是负）不能用外推断定，只能直接测。
臂按《对比实验纪律》做**拷贝+指向**，生产树全程没被改过：

- 控制臂 `/tmp/ds_ab/rowonly`：`chunked_bf16_applies` 改成 `return false`
  （单变量，`diff -rq` 确认 csrc 下只有这一处，`setup.py` 逐字节相同）。
- 工具：`tools/ab_snapshot.py`，两臂**同 session 交替**、每臂每轮一进程，
  臂的 `.so` md5 由子进程自己打印（`lib=` 行）。

### 结果：split 的符号随 batch 翻转

`rowonly vs prod` 配对中位数（>1 = split 更快）：

| 格 | prod(split) µs | rowonly(row) µs | 比 | 判定 |
|---|---|---|---|---|
| b1 V262144 k512 | 87.45 | 128.72 | **1.472** | split 胜 |
| b1 V1048576 k512 | 125.85 | 446.80 | **3.550** | split 胜 |
| b1 V1048576 k1024 | 151.53 | 456.27 | **3.011** | split 胜 |
| b6 V1048576 k512 | 142.46 | 463.54 | **3.254** | split 胜 |
| b6 V524288 k512 | 102.48 | 244.12 | **2.382** | split 胜 |
| b6 V262144 k512 | 97.61 | 131.71 | **1.349** | split 胜 |
| b64 V262144 k512 | 352.84 | 140.80 | **0.399** | row 胜 |
| b64 V262144 k1024 | 383.46 | 149.35 | **0.389** | row 胜 |
| b64 V1048576 k512 | 609.25 | 481.61 | 0.790 | row 胜 |
| b64 V1048576 k1024 | 657.69 | 491.37 | 0.747 | row 胜 |

**对照是干净的**：两臂路由相同的 117 格，比值落在 **[0.973, 1.014]**、中位
**0.9997** —— 这就是这次测量的噪声底，±3% 以内。

### 交叉点随行长移动

把交叉点夹出来（同法配对，>1 = split 更快）：

| vocab | k=512 交叉 | k=1024 交叉 |
|---|---|---|
| 262144 | b∈(12,16)：12→1.131、16→0.909 | b∈(12,16)：12→1.048、16→0.852 |
| 524288 | b∈(32,40)：32→1.199 | b∈(12,16)：16→0.973 |
| 1048576 | b∈(40,48)：40→1.105、48→0.981 | b∈(40,48)：40→1.032、48→0.922 |

**机制**在行核那一列里直接看得见：**行核的时间对 batch 几乎是平的**
（V=262144：b=8 → 133.32，b=64 → 140.65；V=1048576：b=8 → 464.28，
b=48 → 478.36）——它是一波。而 split 的成本随 batch 涨（stage1 是 `b × chunks`
个 CTA）。两者相交，交叉点随行长右移。

### 落地的改动

`chunked_bf16_applies` 加一条按行长的 batch 上限：

```cpp
constexpr uint32_t kChunkedVocabPerRow = 20000;
...
return batches <= params.vocab_size / kChunkedVocabPerRow;
```

边界落在 b ≤ 13 / 26 / 52（V = 262144 / 524288 / 1048576）——
第一个夹在测到的 (12,16) 里，后两个在保守侧。20000 这个数是**从上面那张
交叉表读出来的**，不是拟合出来的定律；数据只支持"交叉点随 V 右移"这个方向。

**官方网格不受影响**：那里能进 split 的只有 b=6（V ≥ 262144），
6 ≤ 13/26/52 恒成立。改的只有 DSA decode 那一族。

## 验证（改动后）

- **配对 A/B**（新 gate vs HEAD 的 gate，147 格，3 轮）：
  **只有 4 格换路由，全部是 split → row，全部变快**：

  | 格 | new(row) µs | old(split) µs | 提速 |
  |---|---|---|---|
  | b64 V262144 k512 | 140.65 | 353.36 | **2.51×** |
  | b64 V262144 k1024 | 149.17 | 384.46 | **2.58×** |
  | b64 V1048576 k512 | 481.89 | 609.54 | 1.27× |
  | b64 V1048576 k1024 | 491.42 | 657.33 | 1.34× |

  未换路由的 **117 格**：比值区间 **[0.973, 1.014]**、中位 0.9997 —— **无回退**。
- **功能门**：`./run_test.sh --test` → **All 340 cases passed**（rc=0）。
  （`skip` 里那些 OOM 是共享卡上 `b=4096` × 大 vocab 的 16–32 GiB 分配，
  本仓成例，与本次改动无关。）
- **性能门 + 基线**：`run_bench.sh --set-baseline`
  （`20261009_140904` → `20261009_144529`）。
  官方门 `All 147 cases passed!` + fp32 `All 30 cases passed!`。
  `compare_result.txt` 对 `maca_c` 的判定是 **3 regressed / 6 improved / 125 noise**，
  全套件 −0.31%。
  **那 3 个 regressed 不是本改动造成的**，三条证据：

  1. **路由不同**。它们的 V 都是 256（低于 `kChunkedMinVocab`），或 b > 64，
     改动前后走的是同一个内核。本次改动能触及的格共 4 个，与这 3 个**不相交**
     （已经程序化核对：路由改变集合 ∩ 回退集合 = ∅）。
  2. **量级在噪声内**。3.4 / 5.5 / 8.8 µs 的格，+3.2% ~ +7.4%。
     本仓成例：`compare_snapshots.py` 的 ±3% 容差是按 >100 µs 的格标定的，
     3–34 µs 上 `maca_c` 自己的复跑散布就到 3–5%（§12.18.6）。
     同一批未换路由的小格里，反方向的"改进"也在（−3.3% / −3.5%），
     双向都有 = 噪声不是信号。
  3. **控制后端复现了同一格**。`torch`（裸 `torch.topk`，改动原理上碰不到）
     在 `b256-v1024-k1024` 上同样报 +4.2%。
