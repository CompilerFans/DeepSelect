# C500 — DSA decode 的相位拆分（Phase 0）

**问题**：C500 的 DeepSelect 离 1,650 GB/s 读墙差得远（官方网格中位 15.3%）。
ledger §4 已把病灶定位到 **CTA 数**（把 pass 1 循环抠成独立核，只改 CTA 数：
4096 → 1646.4 GB/s，104 → 921.3 GB/s）。本战役的目标 regime 是 DSA decode：
`bs × head` 行、长上下文、`b` 很小。本目录是它的**相位拆分**——每个内核各占多少，
以及不属于任何内核的那部分有多大。

**设备**：MetaX C500，`CUDA_VISIBLE_DEVICES=2`，`sm_count=104`，
MACA 3.7.0.36。跑之前 `pgrep -af python` 为空、四张卡 Available（独占）。
**被测产物**：`825e6a8` 重建的 `deep_select_maca_xcore1000.so`（`develop.sh`
三族全建，`BUILD_RC=0`）。
**形状**：`825e6a8` 新补进官方网格的 27 个 DSA 格
（`b ∈ {1,64,128}` × `topk ∈ {512,1024,2048}` × `V ∈ {131072,262144,1048576}`）。
**复现**：

```bash
CUDA_VISIBLE_DEVICES=2 PYTHONPATH=$PWD:$PWD/tests \
  python3 docs/experiments/20261009_c500_dsa_decode/probe.py \
  > phase_split_raw.txt 2>&1
```

原始输出：`phase_split_raw.txt`（每格每个命中的内核名与时间都在里面，未聚合）。

## 方法 —— 两个钟，以及三个必须排掉的坑

- **逐内核**：`kernelkit.bench` 的 `BenchResult.time_ranges`（`bench.py:170`），
  与官方跑的是同一个调用（`tests/test.py:128`）。
- **e2e**：`scripts/perf_snapshot.py:118` 的 `wall_clock_time`。

三个坑，每个都由一个可核对的事实守：

1. **单位是秒，不是毫秒。** `_bench_kineto` 存的是 `time_range/1e6`，
   而 torch 的 `time_range` 是微秒 ⇒ **秒**。判据取同一条 trace 里的 8 GB
   冷 L2 `zero_()`：它必须落在 **~5,360 µs**（`bench.py:132`）。第一次跑我按毫秒
   读，所有内核小了 1000×，而那个 memset 读作 `5.37`——数字自己报的案。
2. **`nan_scan_kernel` 的名字里没有 `topk`。** 官方钟按 `"topk" in name.lower()`
   过滤（`tests/test.py:129`），于是 split 路径的 NaN 扫描**不在官方钟里**，
   而行路径的扫描是融进 pass 1 的（`c36222a`）。只按 `topk` 过滤会同时
   漏掉 11–21% 的时间、并把两条路径放在不同口径上比。本探针把
   `nan_scan` 也算作算子内核，并把官方钟单独打印出来对照。
3. **`wall_clock_time` 的两次调用之间不 flush**，`kk.bench` 每轮 flush。
   两者是不同的 cache 状态。所以判定用 `span`（`kk.bench` 自己 regime 下
   首尾算子内核的跨度），`wall` 只作参考列打印。

## 判据（Phase 0 开工前写死，不许事后挪）

| 预登记判据 | 实测 | 结论 |
|---|---|---|
| `stage2 / Σ算子 ≥ 0.5` → 走 A | 最大 33.9%，b64 上 5.5–11.8% | **A 不成立** |
| `batches × chunks < 2 × sm_count` 且 stage1 占比大 → 走 B | b1: 1×16=16 < 208 ✓；b64: 64×16=1024 ✗ | **B 只在 b1 成立** |
| 没进 split 且是表上最差 → 走 C | b1 全族最差（0.1–0.2% 墙） | **C 成立** |
| `gap / e2e ≥ 0.5` → 停下来报告 | 行核 0.0%，split 1.2–8.7% | **不成立，继续** |

**A（并行 stage2）被实测否掉。** fp32 上 stage2 占 61–84%（ledger §8.5），
bf16 上不成立——**不要把这个结论跨 dtype 搬**。

## 本表新暴露出来的两件事

### 1. `b ≤ 104` 时，时间由**一行自己的串行链**决定，与行数几乎无关

行核在 `V=1048576, k=2048` 上（该 k 全是行核，是干净的单翼对照）：

| b | 1 | 64 | 128 |
|---|---|---|---|
| span µs | **699.29** | **775.65** | 1012.86 |

**1 行 699 µs，64 行 776 µs。** 加 63 倍的行几乎不花时间，因为 64 个 CTA 全在
并行，而每个 CTA 自己要做完 `load → key transform → compare → shared atomic`
这条链（ledger 的 roofline 判定就是"per-CTA dependency chain"）。
**所以"再加 CTA"对小 batch 不是把行铺开——行已经全铺开了；是把一行切开。**

### 2. split 在这个 regime 上**可能是负收益**，但本表无法直接判定

`b64 V262144 k512`：split 353.36 µs。同行核路径的等价格不存在（门挡住了），
只能外推，而**外推正是 ledger §9.2 记录过的那类错误**（"a controlled microbench
does not transfer"）。两个方向的外推给出相反答案：

- 按 `b64 V131072 k512 row = 82.92` 与行核的 V-伸缩（b128 上 V×2 → 1.72×）
  推 `b64 V262144 row ≈ 143 µs` ⇒ **split 慢 2.5×**。
- 按 `b1 V1048576 k2048 row = 699` 推 `b1 V1048576 k512 row ≈ 453 µs`
  ⇒ **split（127 µs）快 3.6×**。

**两个外推不可同时为真，说明外推本身不可用。** 判定必须直接测：把
`chunked_bf16_applies` 在**一份拷贝**里改成 `return false`，两臂同 session 交替跑
（`tools/ab_snapshot.py`）——这就是下一节的 A/B，也是 Phase 1 的第一个动作。

## Phase 1 —— 直接测，不外推

Phase 0 留下的问题（split 在这个 regime 上到底是正是负）不能用外推断定，只能直接测。
臂按《对比实验纪律》做**拷贝+指向**，生产树全程没被改过：

- 控制臂 `/tmp/ds_ab/rowonly`：`chunked_bf16_applies` 改成 `return false`
  （单变量，`diff -rq` 确认 csrc 下只有这一处，`setup.py` 逐字节相同）。
- 工具：`tools/ab_snapshot.py`，两臂**同 session 交替**、每臂每轮一进程，
  臂的 `.so` md5 由子进程自己打印（`lib=` 行）。

| b1 V1048576 k512 | 125.85 | 446.80 | **3.550** | split 胜 |
| b1 V1048576 k1024 | 151.53 | 456.27 | **3.011** | split 胜 |
| b6 V1048576 k512 | 142.46 | 463.54 | **3.254** | split 胜 |

### 交叉点随行长移动

把交叉点夹出来（同法配对，>1 = split 更快）：

| vocab | k=512 交叉 | k=1024 交叉 |
|---|---|---|
| 262144 | b∈(12,16)：12→1.131、16→0.909 | b∈(12,16)：12→1.048、16→0.852 |
| 524288 | b∈(32,40)：32→1.199 | b∈(12,16)：16→0.973 |
| 1048576 | b∈(40,48)：40→1.105、48→0.981 | b∈(40,48)：40→1.032、48→0.922 |

**机制**在行核那一列里直接看得见：**行核的时间对 batch 几乎是平的**
（V=262144：b=8 → 133.32，b=64 → 140.65；V=1048576：b=8 → 464.28，
b=48 → 478.36）——它是一波。而 split 的成本随 batch 涨（stage1 是 `b × chunks`
个 CTA）。两者相交，交叉点随行长右移。

### 落地的改动

`chunked_bf16_applies` 加一条按行长的 batch 上限：

```cpp
constexpr uint32_t kChunkedVocabPerRow = 20000;
...
return batches <= params.vocab_size / kChunkedVocabPerRow;
```

边界落在 b ≤ 13 / 26 / 52（V = 262144 / 524288 / 1048576）——
第一个夹在测到的 (12,16) 里，后两个在保守侧。20000 这个数是**从上面那张
交叉表读出来的**，不是拟合出来的定律；数据只支持"交叉点随 V 右移"这个方向。

**官方网格不受影响**：那里能进 split 的只有 b=6（V ≥ 262144），
6 ≤ 13/26/52 恒成立。改的只有 DSA decode 那一族。

## Phase 2 —— 8 位粗层溢出吗？不溢出（但顺带否掉了一个方向，并量出一条隐藏的悬崖）

**问题。** Phase 0 表里有一组之前没被点名的数字：b64 V1048576 k512 上
`nan_scan_kernel` 110.36 µs、`stage1` 459.67 µs，读**同一份 134.2 MB**、用
**同一个 grid**（`B × chunks` = 1024 CTA）。CTA 数相同 ⇒ 这 4.2× 不是 CTA 饥饿，
只能是 CTA 形态或**读取趟数**。

**读到源码里的嫌疑。** `stage1` 调的是 `radix_topk_row_bf16_k`（static-k 行），
它在阈值高位组的成员数超过 arena 时**多走两趟**整行：

| 趟 | 位置 | 条件 |
|---|---|---|
| 1 | 直方图 | 恒有 |
| 2 | collect（`>threshold` 出、`==threshold` 进 arena） | 恒有 |
| 3 | overflow rescan：整行、只统计 `(key>>8)==high_threshold_bin` | 仅溢出 |
| 4 | overflow emit：整行、同过滤、写回 | 仅溢出 |

而 `radix_topk_row_bf16_b`（生产行核）是 coarse12：12 粗 + 4 细 = 整个 bf16 key，
**refine 不可能溢出**，恒定两趟。源码里记着这条病史（`radix_core.cuh:345`：
"The 8-bit level made the threshold bin wider than the arena on ordinary rows, so
every one of them paid a third row walk"）——`_k` 就是没吃到这个修复的调用者。

### 判据：把 kernel 逐字节钉住，只换数据

`probe_stage1_passes.py`。arena 容量 `kSmemInputSize × 2 = 7028`（compact 索引），
一个 chunk 是 `V/chunks` 个元素，所以溢出是关于**某一个高位字节的成员数**的陈述：

- **crowded** —— 官方网格自己的数据（`lib.generate_testcase`），行内元素堆在少数几个高位字节里；
- **bituniform** —— 16 位空间上逐位模式均匀，256 个高位字节各占 ~1/256，**溢出在算术上不可能**。

**结果：不溢出。** 直接按 `radix_core.cuh:173` 的序保序编码复算每个 chunk 的阈值桶：

| 形状 | 粗层 | crowded 阈值桶 | bituniform 阈值桶 | 容量 | 溢出行 |
|---|---|---|---|---|---|
| b64 V1048576（行核 `_b`） | 12 位 | 412 | 301 | 4096 | **0/64** |
| b6 V1048576（chunk = 65536） | 8 位 | 1542 | 286 | 7028 | **0/6** |
| 同上，**最大**桶 | 8 位 | **18868** | 857 | 7028 | — |

三个 cell、两种数据、两个数据流，**没有一趟 overflow walk 被走到**。所以
"给 `_k` 补 coarse12 以消除重扫"这个方向**买不到任何东西**，在动手前被否掉——
这正是它值得先测的理由。

### 但数据确实在起作用，而且方向相反

同一个 cell、同一个 CTA 数、同一份字节数，只换数据（kernel 逐字节相同）：

| kernel | 粗层 | crowded µs | bituniform µs | 比 | crowded 实读 GB/s（%墙） |
|---|---|---|---|---|---|
| `_b` 行核 b64 V1M | **12 位** | **482.76** | **775.32** | **0.62×** | 556.0（2 趟） **33.7%** |
| `_k` stage1 b6 V1M | 8 位 | 65.54 | 44.65 | 1.47× | 384.0（2 趟） 23.3% |
| `_k` stage1 b6 V262144 | 8 位 | 41.50 | 19.53 | 2.12× | 151.6（2 趟） 9.2% |
| `_k` stage1 b1 V1M | 8 位 | 60.31 | 40.01 | 1.51× | 69.5（2 趟） 4.2% |
| `nan_scan` b6 V1M | — | 38.55 | 37.63 | 1.02× | 326.4（1 趟） 19.8% |

**`_b` 与 `_k` 对同一扰动的响应符号相反**：12 位粗层的行核在 crowded 数据上
**快 1.6×**，8 位粗层的 stage1 慢 1.5–2.1×；而两者都读同一份字节。`nan_scan`
（1.02×）说明这不是"数据难读"——它就是这两个数据流自己的差别。
**这条差别的成因本轮没有定论**，不许当成已知结论引用；它是下一轮的输入。

### 顺手量到的一条隐藏悬崖（本轮最有价值的副产品）

`_k` 的阈值桶 1542 / 容量 7028 = 0.22×，看着很宽裕。但同一批数据里**最大的**那个
8 位桶是 **18868 = 容量的 2.7×**。阈值落在哪个桶由每行的 rank-512 决定，不由桶的
大小决定——**只要某行的 top-512 恰好落进那个拥挤的桶，它立刻走 overflow 的两趟重扫**。

这就是 coarse12 当初被引入 `_b` 的理由在 `_k` 上依然成立的地方：**余量不是设计出来的，
是数据分布恰好给的**。官方网格上它不触发（本轮实测），所以这不是一个现在要修的缺陷，
但它是一个**会随输入分布迁移的悬崖**，记在这里。

### 3.2 机器在这块 size 上的读速率（`probe_read_scaling.py`）

不用新内核：`nan_scan_kernel` 就是**单趟纯读**，在产线上，grid = `B × 16`。
扫 b 即同时扫字节数与 CTA 数（每行 16 CTA / 2.10 MB）：

| b | CTA | 字节 | µs | GB/s | %墙 |
|---|---|---|---|---|---|
| 1 | 16 | 2.10 MB | 26.78 | 78.3 | 4.7% |
| 6 | 96 | 12.58 MB | 38.84 | 324.0 | 19.6% |

所以"某内核只有 X% 墙"必须先说清是在哪个 size 上——ledger §4 那条曲线读的是
**4.295 GB**，把它当成小规模的标尺会得出错误结论。

### 3.3 行核的两趟各占多少（`pass1_arm_ab`）

**臂**：`/tmp/ds_p1`，把 `radix_topk_row_bf16_b` 的 collect 整块短路（在 narrow 之后
`output[i] = s_wide_above; return;`），生产树逐字节未动。`tools/ab_snapshot.py`，
两臂同 session 交替，`126e9969`（prod）vs `5539f1c8`（臂）。

**对照是干净的**：另两条路由各自不动 —— `c12`（`dg_coarse12.cuh` 那条独立条目）
1.0009×、`split`（`preselected` 尾核）0.9981×。

| 格（4096 行） | prod µs | pass 1 µs | collect µs | pass1 占比 | pass1 GB/s | pass1 %墙 | collect GB/s | collect %墙 |
|---|---|---|---|---|---|---|---|---|
| ×1048576 k512 | 19320.3 | 8640.2 | 10680.1 | 44.7% | **994** | **60.3%** | **804** | **48.7%** |
| ×524288 k512 | 10075.1 | 4471.9 | 5603.2 | 44.4% | 960 | 58.2% | 766 | 46.4% |
| ×262144 k512 | 5457.0 | 2397.4 | 3059.6 | 43.9% | 896 | 54.3% | 702 | 42.5% |

1. **collect（第二趟）是较大的那一半，55–60%。** 想大幅提速就得少走一趟；

不是对 pass 1 的独立测量。

## Phase 4 —— 行核里还有第三趟，和一处只从调用方守着的越界读

### 4.1 `_b` 的 overflow 分支是**整行第三趟**，本 shape 不触发

`radix_topk_row_bf16_b` 在 collect 之后还有一段（`radix_core.cuh:1420-1472`）：

```cpp
const bool overflow = s_num_input[0] > SMEM_INPUT_SIZE;
if (overflow) {
    for (uint32_t idx = tx * 8; idx < vec_len; idx += BLOCK_SIZE * 8) {   // 整行第三趟
        uint4 v = __ldg(...);
        for (int i = 0; i < 8; i++)
            overflow_emit_member(idx + i, ...);
    }
    ...;  __syncthreads(); return;
}
```

coarse12 移植时 `SMEM_INPUT_SIZE` 被改指 `kCoarse12ArenaEntries`（4096），所以这条门的
判据现在是 **12 位阈值桶的成员数 vs 4096**——正是 `probe_arena_fill.py` 量到的量
（k=512 时 387、k=1024 时 847），**本 shape 不触发**。但注意余量只有 5–10×：
这条趟的开关是"阈值桶恰好装不下"，而阈值落在哪个桶由每行 rank-topk 决定。
和 Phase 2 那条悬崖是同一个性质。

### 4.2 失败的消融暴露的一处隐患：`s_high_threshold_bin_id` 没有初值

为了给 pass 1 的共享原子定价，做了第三臂 `/tmp/ds_p2`（在 pass-1-only 臂上只把
`hist_add_bf16_wide` 的 `atomicAdd` 换成寄存器累加）。它**崩了**——
`CUDA error: an illegal memory access`。查因不是臂写错，是它踩到了内核里一处
只由**调用方**守着的路径：

```cpp
if (tx < RADIX) {
    ...
} else if (tx == RADIX) {
    s_histogram[RADIX] = 0;
    // The refine's landing state, initialized here so that a crossing the
    // scan cannot find leaves a defined bin behind rather than whatever the
    // previous launch on this SM left in shared memory.
    s_threshold_bin_id = 0;
    s_last_remain = 0;
}
```

这段注释写得**正是**这个隐患，也**正是**为它防了 `s_threshold_bin_id` 与
`s_last_remain` ——但**同一处的第三个变量 `s_high_threshold_bin_id` 没有初值**。
它只由扫描写：

```cpp
if (tx < RADIX && inclusive_suffix > remain_topk && exclusive_suffix <= remain_topk) {
    s_high_threshold_bin_id = tx; s_num_input[0] = 0; s_counter = 0;
}
```

直方图全零时该条件恒不成立，变量保留上一次启动在同一 SM 上留下的值，随后被当作
高位字节索引进 4096 槽的 `s_wide`：

```cpp
const uint32_t high = s_high_threshold_bin_id;
... s_wide[(high << kCoarse12Shift) + s]     // (high<<4)+s 越界
```

**在生产路径上不可达**：调用方都先挡了 `length > topk`（`length <= topk` 走捷径，
`stage1` 也有 `if (chunk_len <= topk) return`），所以直方图总数恒 > topk，扫描必命中。
它记在这里是因为**守的位置不对**：同处的另两个变量是从内核内部守的，注释也写明了
理由，只有这一个依赖外部守卫——一旦哪个调用方放松了那条前置条件，失败形式是
越界共享读，不是错答案。

这条臂因此**作废，没有读数**；共享原子的定价仍未取得。

读，10053 µs）**。抠出来的两趟只要 6.2 ms。

循环体（指令级相同）、共享原子、占用率、CTA 数、数据拥挤度、NaN 融合、
collect 的分支形状与写出条数、两条第三次走的分支。剩下的候选是内核里
**walk 之外**的共享内存串行段与它们之间的屏障，以及**整核调度**本身。

下一步只有一条干净的路：在 `/tmp/ds_probe` 那类拷贝上，把 pass 1 的循环体

### 7.2 三条被实证否掉、不要重走的假设

- **不是代码尺寸**：E 是单一 body、**3122** 条指令，和 B 的 2951 几乎一样大，
  却跑 10067（和 5951 条的 A 一样慢）。四个臂的指令数/时间不单调。
- **不是 `uint4` 跨原子循环的存活期**：J 关掉 NaN 语义、只留一个对 `v` 的
  死用（比较永不成立），= 6019，与 B 的 6016 无差。
- **不是循环结构**：F 把测试融进原子循环，= 10063.7，与 A/E 无差。

**也不是谓词的算术**：D 把每 uint4 的谓词从 ~40 op 砍到 13，只拿回 6.8%；
K 再把累积从掩码域（汇编里是 `sand_b64`/`sor_b64`，与 `__ballot_sync` 同一单元）
挪回通用寄存器，也只到 8.0%。**40% 不在谓词的成本里。**

### 7.3 真正的话：成本是不可加的

把 P1 系与全核放在一起：

- pass 1 单独跑，NaN 开 3863.9 → NaN 关 2809.7，**NaN 值 1054 µs**；
- 全核 NaN 开 10072.3 → NaN 关 6016.4，**NaN 值 4056 µs**。

**同一个检查，在 pass 1 里值 1.05 ms，在整个核里值 4.06 ms。** 差额 3000 µs
落在 pass 1 之外——collect 那一趟没有 NaN 代码，却跟着一起变快。

这正是 Phase 5.4 那个"部件之和 ≠ 整体"的第二个实例，而且这次它是**可触发的**：
改一个与 collect 无关的开关，collect 的时间跟着动。⇒ 两条走 walk 的结论要按
这句读：**生产行核的两个 pass 共享同一个 SM 上的资源，单独量任何一趟都不构成
对整体的预测。**

### 7.4 顺带确定、可以单独记账的两条

- **BLOCK 1024→512 值 −11.0%**（A），但在 NaN 关掉之后**反过来贵 4.5%**（C 对 B）。
  所以 `needs_long_row_bf16` 选 1024 不是免费的，也不是无条件该改的——
  两者有交互，按当前生产配置（NaN 开）512 更快。
- **pass 1 在 blk512 / NaN 关时到 92.7% 墙**（P1c，4.295 GB / 2809.7 µs = 1529 GB/s）。
  这同时说明 Phase 5.4 里"两趟 walk 达 90.5% 墙"的微基准模型是对的——
  单独榨一趟是能做到的。

### 7.5 对两张图的意义

bf16 图 18 根柱子里 12 根走行核。这 12 根按当前配置各带一份 40% 的 NaN 税，
而**这份税不随谓词的写法变**。可选的只有两件事，都要单独决定：

1. `check_nan=False`（已存在的公开开关，本仓 ledger §8.4 在 fp32 上量到 22–32%，
   这里 bf16 量到 40%）——这是**契约**决定，不是调优。
2. 把 NaN 扫描从 pass 1 里拿出来做成独立的一趟（split 路径已经这么做）。
   代价是一趟纯读：4.295 GB 按 P1c 的 1529 GB/s ≈ 2.8 ms，而它现在值 4.06 ms。
   账面上能赚约 12%，但要加一次发射，且**必须按 7.3 的教训整体量，不能按趟相加**。

### 7.6 四条"保住检查、换写法/换位置"的路，全部走完

| 臂 | 做法 | µs | vs 控制 |
|---|---|---:|---:|
| D | 谓词改 SWAR（每 uint4 40→13 op） | 9391.6 | −6.8% |
| K | SWAR + 累积不落掩码域 | 9269.0 | −8.0% |
| M | 扫描搭 **collect** 那一趟（零额外读，复用已加载的 `uint4`） | 9452.9 | −6.2% |
| L | 扫描独立成趟（纯读、零共享内存、零原子） | 11304.6 | **+12.2%** |
| B | **不做检查** | **6016.4** | **−40.3%** |

**没有一条接近 −40%。** 三条改法挤在 −6~−8%，插一趟反而贵 12%。

L 值得单独记一笔：那第三趟是**纯读**，微基准里同几何纯读是 **95.4% 墙**（`real_data`），
放进这个核里只跑到 **49% 墙**（4.295 GB ÷ 5288 µs）。**这是"每一趟都只跑到微基准一半"
的第三个实例**，而且这次趟里什么都没有——没有原子、没有共享内存、没有屏障。

### 7.7 结论：40% 是"做这个检查"的价钱，不是这个检查怎么写

把 7.2、7.6 合起来，40% 既不是谓词的算术、不是累积落在哪个寄存器域、不是它在哪一趟、
也不是多出来的那趟本身。剩下的解释只有一个方向：**在这个内核里，任何附加的、必须
按元素做的工作都按"整核尺度"计费，而不是按"局部尺度"计费。** 同一个检查：

- 在 pass 1 单独跑时值 **1054 µs**（3863.9 → 2809.7，blk512）；
- 在整个核里值 **4056 µs**（10072.3 → 6016.4）。

差额 3000 µs 落在 pass 1 之外，而 collect 那一趟一行 NaN 代码都没有。

⇒ **不要把"40% 的 NaN 税"当成一个待修的缺陷**——它修不出来。它是探针：这个核里
"多做一点按元素的工作"的边际价格约为微基准确认值的 **3~4 倍**，探它最灵敏的旋钮
就是 NaN 的开/关。下一步该问的是**这个倍数从哪来**，而不是怎么把谓词写短。

## Phase 8 —— 40% 不是一笔税，是两个占用率工作点（2026-10-09）

7.7 那个"3~4 倍的边际价格从哪来"有答案了，而且它不在谓词里，也不在趟数里——
在**静态共享内存**里。

### 8.1 先把问题摆正

7.1 的 −40.3% 是**重编译**量到的（B 臂：把 NaN 实例化从内核里摘掉）。
而 `check_nan=False` 这个**运行时**开关只拿回 **−9.6%**（10071 → 9098 µs，
见 8.2 的 A 臂）。同一个开关差四倍。这一段追的就是这四倍。

`radix_select_row`（`maca_topk.cu:316`）在**运行时** `bool` 上分支，在两个
`radix_topk_row_bf16_b<BLOCK, kNan>` 之间选。所以生产内核里**同时躺着两份完整的
数据流**——7.2 记的 5951 条指令 vs B 的 2951 条，逐项都是 2×（`ldg_b128` 6:3、
`sm_add_u32` 40:20、`barrier` 44:21）。

### 8.2 臂（同一台机器、同一天、交替两轮；同一个 `.so` 内只有被列出的那一处改动）

| 臂 | 改动 | API `check_nan` | 实测 µs（两轮） |
|---|---|---:|---|
| **A** | 生产原样 | True | **10065.4 / 10064.1** |
| **A** | 生产原样 | False | **9103.3 / 9101.2** |
| **B** | `fold_nan = false` 字面量（单 body） | 任意 | **6021.5 / 6017.4** |
| **C** | 同上，但写 `params.topk == 0xFFFFFFFFu`（以为不透明） | 任意 | 6020 / 6022 |
| **C′** | 同上，改 `volatile bool`（以为不透明） | 任意 | 6020.5 / 6021.2 |
| **E** | `(… ) && (length == 0xFFFFFFFFu)`：不透明取 false（形态混合，见下） | True | **9101.9 / 9106.5** |

两件必须先说的事，都是这次实测推翻的：

- **C 和 C′ 都没能做成"双 body"**。C 被编译器看出 `topk` 有范围证明（内核里有
  `topk` 的上界检查），`C′` 的 `volatile` 局部量被常量折叠：两臂在**同一个
  mangled 符号**下都只有 **2950 / 2951 条指令**（`ldg_b128=3`、`sm_add_u32=20`、
  `barrier=21`），与 B 逐项相同。
  **"我加了个不透明条件"只能用逐符号汇编证，不能靠意图，也不能靠 `.so` 尺寸**：
  C′ 与 B 都是单 body，`.so` 却分别是 **4,534,336 / 4,145,216 B**（C 才是与 B
  同尺寸的那个）。判据是 `.s` 里那个符号的指令数，不是文件大小。
- **E 也不是"两份 body"**：它 4,257 条指令、`ldg_b128` 仍是 **3**（一份循环的
  载入量），但 `barrier=44`、静态 smem 4,924 B、寄存器 37/48 —— 都和 A 一样。
  它测到 **9,102 µs**，与 A/False 的 9,098 相同。所以 E 把"真 body + 不透明的
  假条件"编译成了一份循环 + 两套屏障的混合形态；**它支持占用率解释，但不构成
  单变量证明**（它的指令数也和 B 不同）。单变量的那一格是 8.6 的 T 臂。
- **`params` 探针**（arm D：在生产内核里打印 `blockIdx.x==0` 的整份 `RowParams`）
  显示两次调用**只差 `cn` 一个字段**——`end_ptr`/`idx_offset_ptr`/`preselected`/
  `nan_flags`/`scan_flags`/`coarse12_cols`/`chunks_workspace` 全为 0，`topk`、
  `sm_count`、`vocab`、`stride`、`length` 相同。**运行路径的差别只有那个 bool。**

### 8.3 机制：绑的是 **MT 寄存器**，不是共享内存（本节原稿引的 smem 表不是这一格的仪器）

**驱动自己的答案**（`/tmp/ds_nan_ab/occ_probe.py`：把臂按它自己的包装进来，对
本格真正跑的 `topk_kernel_radix<__maca_bfloat16, int, 1024, false,false,false,false>`
调 `mcOccupancyMaxActiveBlocksPerMultiprocessor(func, 1024, 18432)` —— 真实的
block 宽度与动态 smem）：

| 臂 | MT / ST regs | 静态 smem | 驱动给的 **blocks/SM** | 实测 µs |
|---|---|---:|---:|---:|
| **B**（单 body） | 27 / 40 | 2,336 B | **2** | 6,021 |
| **T** = B 的代码 + 2,588 B **动态** smem | 27 / 40 | 2,336 B | **2** | **6,020.8** |
| **S1**（B + 活着的投票 + 独立扫描核） | 42 / 50 | 2,336 B | **1** | 9,104 |
| **A**（生产，两份 body） | 43 / 70 | 4,924 B | **1** | 10,071 / 9,098 |

设备给的预算：`regs_per_multiprocessor = 131072`、
`max_threads_per_multi_processor = 2048` ⇒ 两个 1024 线程的 CTA 同时驻留时，
每线程 **32** 个寄存器。27 在 32 以内，37~43 不在。

**T 臂直接否掉共享内存这条**：它与 B 同一份代码、同一个静态 smem，只把**动态**
请求 +2,588 B —— 合计正好是 A 的 23,356 B —— 驱动仍给 **2 blocks/SM**，实测
**6,020.8 µs**，就是 B 的速度。**footprint 不是那个变量。**

**寄存器能定位到一个基本块**：A 的 447 个块里只有**一个**用到 r≥28 —— pass 1 那条
**把 NaN 位测试内联进去**的直方图循环（124 条指令，最高 r42，看着就是
`and 0x7f80` / `cmp 0x7f80` / `and 0x7f` / `cmp 0` 那一串）；A 的其余块全部 ≤27，
B 的同一条循环是 70 条、最高 r26。**43 是那个测试的账。**

时间指纹（9098 ÷ 6020 = **1.511**）与之相容：完全重叠的延迟隐藏该是 2.0、完全串行
该是 1.0，1.51 是部分重叠。但它只是佐证 —— **判据是驱动那一列**。本节原稿引的
CLAUDE.md smem 分档表在这格上给出的档位（A=2、B=3）与驱动不符，不要再引它。

### 8.4 更正 7.7 与原稿：生产只有**一个**工作点，"两个效应抵消"撤回

原稿把 3 CTA/SM 与 2 CTA/SM 摆成两个工作点、说两笔账反向抵消。**档位是错的**
（8.3），而且**第二个工作点在这份内核里不可达**：四种"保住检查、只换写法"的形态
（W / X1 / X2 / Y1，8.7）全部落在 **37 MT / 52 ST ⇒ 1 CTA/SM**。所以"某个工作点上
扫描只要 973 µs"那种说法没有工作点可指。

单变量、可直接量的只有一条：

| 内核（同一份 `.so`、同一占用率 1 CTA/SM、只差运行时那个 bool） | µs | 差 |
|---|---:|---:|
| A，`check_nan=False`（两趟纯读） | 9,098 | — |
| A，`check_nan=True`（两趟 + 扫描） | 10,071 | **+973（+9.7%）** |

⇒ **在生产实际运行的那个工作点上，这笔税是 973 µs（9.7%）。**
`8489b2c` 的标题（"40% 不是重写或搬移能偿还的"）在**结论上**成立，但理由按本节改：
那 40%（4,050 µs）里 **3,077 µs 买的是"把活着的那份投票一起删掉"**，
而那不是任何调用者能到达的配置（B 的 epilogue 被编译器证明恒假、整块删掉，8.2）。
剩下的 973 µs 才是这个检查的价钱 —— 而 8.7 给出的是：这 973 µs 里能拿回绝大部分，
靠的**不是删检查，是把一直在跑的那份 body 写短**。

### 8.5 对文档的更正

CLAUDE.md 的资源审计那一节记着"bf16 wide path, topk=512 : 16384 + 2048 + **2596**
= 21,028 B → 75%，limiter=shared_memory"。**2,596 是另一个实例化的数**（那份
`--resource-usage` 里 `Lb1E…` 那几个组合是 2,596，本格跑的 `Lb0ELb0ELb0ELb0` 是
2,336）。生产实例化是**双 body**，静态 4,924 B，合计 23,356 B。而它的占用率按 8.3 的
驱动实测是 **1 CTA/SM**（不是 3，也不是原稿改成的 2）—— 这一条影响所有以
"bf16 行核 3 CTA/SM"或"2 CTA/SM"为前提的推理。


## Phase 8 续 —— 独立扫描臂、T 臂、以及能拿的那一半（2026-10-09）

### 8.6 零成本的那一支不存在：独立扫描臂实测比生产贵 17%

问题原样是"NaN 检查现在融在一个 kernel 里，换成独立 kernel 会不会更好"。
**不会，而且差得不近。** 五个臂同一 session、交替、官方口径
（`/tmp/ds_nan_ab/ab_final.log`）：

| 臂 | 行核 µs | `nan_scan_kernel` µs | 合计 |
|---|---:|---:|---:|
| **A**（生产：融在 pass 1） | 10,073.2 / 10,074.0 | — | **10,073** |
| **S1**（B 的代码 + 独立扫描核，扫描 grid = batches×1） | 9,104.4 | 2,648.1 | 11,803.2 |
| **S2**（同上，扫描 grid = batches×16） | 9,107.0 | 2,574.4 | 11,738.1 |

三条理由，各自都是实测量出来的：

1. **独立那一趟已经在墙上**：4.295 GB 输入读 2,648 µs = **1,622 GB/s = 墙的 98%**
   （C500 实测只读墙 1,650）。一趟独占的扫描**没有可赢的东西**。
   S1→S2 只改扫描的 grid（×1 → ×16），扫描时间只动 2.8% —— 它不受并行度限制，
   受的是墙，这条正是上面那个结论的交叉验证。
2. **融合的边际成本是 973 µs**（8.4），比独立那一趟便宜 **2.7×** —— 因为它搭的是
   pass 1 已经在读的字节。
3. **独立方案连 B 的工作点都拿不回来**：它的行核仍然必须背着一个活着的投票
   （读 flag 表 + epilogue），落在 **42 MT ⇒ 1 CTA/SM ⇒ 9,104 µs**，与 A/False 的
   9,098 相同。**它付了整趟的钱，工作点还留在原地。**

两个记账陷阱，都要防：

- **`bench_topk` 按名字里含 `topk` 过滤，而 `nan_scan_kernel` 不含** ——
  独立方案会被记成"只有行核的时间"。`measure_sum.py` 因此逐核打印并额外给
  "所有算子核之和"一列；上表两列都给了。
- **B 臂的 −40% 不是"删掉扫描"**：B 的 epilogue 被编译器证明恒假、整块删掉
  （`nan_local` 初值 false 且无人写），那是**任何调用者都到不了的配置**。
  它买的是 8.4 说的那 3,077 µs。

### 8.7 能拿的那一半：把**一直在跑的那份 body** 写成 SWAR（已落在生产树）

8.4 说这 973 µs 是"做这个检查"的价钱；这一节是它的**可偿还部分**：
不删检查、不动占用率，只把 pass 1 那份一直在跑的 body 的**指令数**压下去。

改动（`radix_core.cuh` 的 `hist_add_bf16_wide`）：把 32 位字**两个 bf16 一起**处理，
排序键与 NaN 测试各一个 SWAR 式：

- 键翻转 `bf16_to_uint16` 是逐半的掩码（非负 `0x8000`、负 `0xffff`，即
  `0x8000 + 0x7fff*sign`）。打包形式：`(w>>15) & 0x00010001` 把两半的符号分别放到
  第 0、16 位，**一次乘 `0x7fff`** 就得到两半的掩码（`0x7fff + 0x7fff0000 =
  0x7fff7fff`，两半之间不进位）。
- NaN：`(h & 0x7fff) > 0x7f80` 与 `is_nan_bits16` 等价，且可两半同时做 ——
  `((w & 0x7fff7fff) | 0x80008000) - 0x7f817f81` 的**每半最高位**即为结果，
  低半不会向高半借位（`0x8000 - 0x7f81 = 0x7f ≥ 0`）。
- 两个恒等式都在 Python 上对**全部 65,536 个半字模式**逐条验过。

实测（同 session、交替、官方口径，b4096 V524288 k512 bf16）：

| 臂 | µs | Δ |
|---|---|---:|
| **A**（生产） | 10071.0 / 10071.8 / 10074.5 | — |
| **W**（只把 NaN 测试 SWAR 化） | 9390.5 / 9391.0 | −6.8% |
| **Y1**（测试 + 键翻转都 SWAR 化） | 9307.5 / 9309.4 / 9307.9 | **−7.6%** |

**双币种**（该格 = 趟输入 4,295 MB + 索引 8.4 MB；墙 1,650 GB/s）：
A 逻辑口径 427 GB/s（墙的 25.9%）、实际流量口径（内核读两趟）854 GB/s（51.7%）；
Y1 462 GB/s（28.0%）/ 924 GB/s（56.0%）。
**roofline 判定：这一格不是带宽受限** —— 1 CTA/SM 上它绑的是每 CTA 的依赖链，
所以 pass 1 的指令数在关键路径上，这正是不动占用率也能拿 7.6% 的原因。
循环本身 125 → 89 条指令。

**它买不到的是占用率档**，这一点四个形态一起证明：W（SWAR 测试）、X1
（键域区间测试 `(uint16)(key-0x7f) > 0xff01`）、X2（X1 + `#pragma unroll 4`）、
Y1（测试 + 键翻转）**全部恰好落在 37 MT / 52 ST**，驱动一律 1 CTA/SM。
再看 Z1 臂（同一个 fold，把 `__syncthreads_or` 换成逐线程值 —— 诊断用、语义
不对）：**还是 37**，只少了 256 B 静态 smem。⇒ **相对 B 那 +10 个寄存器，是
"这个 fold 存在"本身的账**（一个要活过 pass 1 的逐线程投票），不是它的算术，
也不是投票的机制。**改写法跨不过这道档。**

工具链事实（都实测过，省下一次重走）：

- **`__launch_bounds__(BLOCK, 2)` 被 mxcc 静默忽略**：A.s 与 U2 臂（只多这一个
  参数）的 `.s` **逐字节相同**，也没有 `.maxntid` 一类的元数据。
- **工具链没有寄存器上限开关**：`cucc --help` / `mxcc --help` / `--help-hidden`
  都没有 `-maxrregcount` 一类。⇒ 寄存器只能从源码里省。
- **`mcFuncGetAttribute` 拿错 id 会 core dump**（不是返回错误）：`attr_probe.py`
  盲探 1..11 时就崩了一次。要问就问确定的 id。

**正确性**：两个恒等式在 Python 上穷举验过；设备侧 A 与 Y1 的 NaN 契约一致 ——
NaN 行 slot 0 得 `0x3F3F3F3F`、±inf 行不得、`check_nan=False` 时 NaN 当一个值参与
排序。**逐元素比对在这里不可用**：bf16 行在第 k 名处成堆并列，`sorted=False` 下
选中集合逐次运行就会变（同一份二进制两次运行也是如此，CLAUDE.md 有记）。

**门**：改动树上 `./run_test.sh --test` = **340 cases passed**（含套件常规的 OOM
skip）。家族级 A/B（`tools/ab_snapshot.py`，2 臂 × 3 轮 × 10 iters、同一 session
