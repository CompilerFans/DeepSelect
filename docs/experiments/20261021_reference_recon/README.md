# C600U 参照系清查:mcDeepGEMM / 官方 CUDA / NPU / CUB,以及 fp32 采样阈值一遍(2026-10-21,离线)

状态:**纯离线分析,无设备**。四个参照系逐一过完了,结论是三条:大格上我们和
deep_gemm 同点、官方与 NPU 与 CUB 都没有可移植的机制剩下、fp32 的下一个大杠杆
是**采样阈值一遍**(本文给出在官方分布上模拟的可行性表)。另带一条勘误:仓库里
"k-th 值并列 ~19K" 的论断是误读,实际并列组是 24–110,bf16 排除一遍的理由因此
从"结构性不可能"退化为"行走速率算术"。

本文的出处:DG 内核对照来自对 `ref/deep_gemm/xcore1000_fp32_topk.cu` 与
`csrc/maca_kernels/common/topk_coarse12.cuh` 的归一化逐行 diff;官方 CUDA 与 mcCUB
对照来自对 upstream/main 与 `/opt/maca/include/cub/` 的通读;NPU 一节出自
mcDeepGEMM 仓的 `docs/20261020_dsa_topk_four_implementations.md`;模拟脚本
`sim_sample_np.py` / `sim_tie_bf16.py` 在本目录,纯 numpy,官方分布
(`NormalFloatDistribution` = `randn`)。

## 2. 对照 mcDeepGEMM 的 deep_gemm:同点,无可挖机制

**逐格(`relative_pct_vs_maca_c` = maca_c/dg×100,>100 我们快):**

| 格 | maca_c µs | dg µs | 比值 |
| --- | ---: | ---: | ---: |
| (4096,131072,2048) | 5,562.8 | 5,519.9 | 100.78 |
| (4096,107520,2048) | 4,678.8 | 4,679.4 | 99.99 |
| 小 batch k2048 各格 | — | — | 101.79–110.09(我们领先) |
| (16,66551,2048) | — | — | 115.69 |
| (1,131072,2048) | 111.2 | 36.5 | 304.77(DG 领先 3.0×) |
| (1,107520,2048) | 102.9 | 39.7 | 259.06 |
| (1,66551,2048) | 57.9 | 35.1 | 164.96 |

DG 在全部 V=129280 k=512 fp32 格上 `unsupported`(其 selector 限定 full-row)。
b1 三格 DG 领先 2.6–3.0×,但合计 272.0 µs = fp32 的 0.7%。

**内核体对照(归一化 diff,`xcore1000_fp32_topk.cu:476-691` vs `topk_coarse12.cuh:177-466`)**:
移植体**就是** DG 的 coarse12。常量、位移、桶数、容量、暂存、原子、早退、溢出循环、
乒乓 arena 全部相同;差异只有四处:我们的融合 NaN 谓词 + `__syncthreads_or`;
`if constexpr (ARCH_REGS_PER_AP >= 131072)` 的两 float4 在飞臂(两遍各一,DG 恒一);
`return true`(死代码差异);类型/格式。DG 全文**没有**任何块级/warp 级直方图归约,
两遍都是逐元素一次共享原子。结论:**在旗舰 fp32 格上,DG 的 coarse12 没有任何我们
缺的机制;47% 墙的运行点是算法/部件的,不是移植缺陷。**

DG 里我们 C600U 可达路径没有的东西,按价值排:

1. **n_rows ≤ 32 的 chunks 内核**。DG 从不把 coarse12 路由到 32 行以下。C500 台账实测
   DG chunks 在 b1/b2 V66551 k2048 为 53.0/54.1 µs vs 我们 split 90.8/93.4 µs = **0.58×**
   (`docs/C500-radix-perf-ledger.zh.md:2901-2912`;b≥4 反过来慢 3.8–4.2×,所以这是
   b≤2 专用杠杆)。我们的 `topk_chunks.cuh` 在树里但 **C600U 不可达**:
   `f32_chunks_applies` 对 `sm_count != 104` 直接 return false(`routing.cuh:944`),
   且 batches 上限为 2。C600U 上 b1/b6 由我们自己的 fp32 split 服务
   (work target `sm_count*5/2` = 70)。
2. **单内核收尾 + 核内取值**(DG `gather_topk_values`)。省一次启动和
   `coarse12_cols` 的 topk×4B 往返;带宽主导的旗舰格上预期小,未实测。
3. **浪尾 chunk 数模型**(`select_chunk_count`,kMinChunkCount 3 / kMax 6 /
   kMinElementsPerChunk 4096)—— 对应我们 fp32 split 大 batch 分支对非 104 AP
   硬编码 return 2(`routing.cuh:576-579`)。DG 的规则在 28 AP 上会选 4–6 chunk,
   欠填更多;这是策略参考,不是预测的收益。
4. `topk_single`(fp16 圆整 key>>6,1024 桶,1024 线程)未移植,但它也是两遍整行读
   + 逐元素原子,pass-1 没有节省。
5. `alignas(128)` 热共享标量(仅 topk_single)、向量化 trivial 填充(官方网格不打),
   均无关。

**边界性负结论:DG 没有任何降低 pass-1 逐元素共享原子发射的机制** —— 这正是旗舰格
的疑似主成本。DG 对慢行走的唯一答案是按 chunk 拆行(即第 1 条)。

**一个待探针裁决的矛盾**:相位探针文档把 bf16 直方图行走上限(780–880 GB/s)套到
coarse12 pass-1;而记忆(`c600u-optimization-state`)记 fp32 行走(4 原子/16B)约
1.4 TB/s ≈ 墙、"不构成约束"。两条不可能都对;`20261021_coarse12_phase/` 的相位拆分
是裁决者。反解 5.57 ms / 4.29 GB ≈ 771 GB/s 只是两遍平均,分不开账。

## 3. 对照官方 CUDA DeepSelect:五个 mandated 机制全不可移植

官方一遍 dataflow(随机块序扫描 → 运行阈值过滤 → k+B2 压缩)的五个核心机制逐一过过:
mask+`__ffs` 放置、float-add-as-int、bf16x2 census/pivot/quota、随机序+运行阈值+压缩、
threadblock cluster —— **全部服务于一遍 dataflow 本身,没有一个能移植到我们的两遍
radix**。唯一已转移的原则是"把原子挪出元素路径",已经以 block-max 直方图落地
(`095224c`)。两个"需测量"项(sink-slot 直方图、整桶早退)落在非瓶颈阶段。
一遍原型 v1/v3 的实测否决见 `20261020_onepass/`(但其"19K 并列"的机制解释是错的,
见 §6 —— 否决在别的理由上仍然成立)。

## 4. 对照 NPU/Ascend DeepSelect:硬件原语,无可移植

Ascend 版的算法骨架与我们相同(直方图 → 阈值 → 收集),但所有快组件都是硬件的:
`asc_cumulative_histogram_bin0/1` + `asc_loadalign_deintlv`(**硬件**累计直方图)、
`asc_squeeze_and_storeunalign`(**硬件**流压缩)、`asc_gather`、`asc_eq(v,v)` 免费
NaN 计数、16 位分裂索引(候选内低 16 位、块内高 16 位)、内容播种置换 hash、UB 内存
规划与刻意别名。**没有一样可移植**;其教训("直方图按硬件速率跑")正是我们 block-hist
用软件逼近的东西。

## 5. 对照 CUB/mcCUB:块级原语无一可用

`BlockHistogramAtomic` 与我们的 pass-1 **逐字节同构**(就是它);
`BlockHistogramSort`(默认)4096 桶要 ≥32 KB;`DeviceHistogram` 私有化上限 256 桶、
之后退到**全局**计数器;`cub::BlockSelect` 不存在;`BlockRadixRank` 要 36,864 B 计数器;
`BlockScan/WarpScan/WarpReduce` 都是 `__shfl_*_sync` 包装(**71 指令** vs 手写
`__builtin_mxc_bsm_bpermute` 蝶形 **44**,同一条 `sm_bperm_b32`,差值全是包装层的
`__lane_id()` + 边界算术 —— 我们的热路径已经是原生形态,采用 CUB 版是回退)。
唯一的机制想法是 RLE(`IS_RLE_COMPRESS`),但它的前提是输入有序/成簇
(CUB 内部是先排序再压缩,4096 桶 ≥32 KB);官方分布相邻两元素同 12 位桶实测
**1.4%**、8 元素组 **7.62 个不同桶**(`20261021_blockhist` §1,含同族的寄存器
预聚合 427 vs 678 GB/s 否决),可合并的原子 ≤5% 而每元素先付一次比较+分支 ——
且 block-hist 之后原子已不在元素路径上,fp32 侧本就非原子受限(6.9 vs ~14 G/s/AP)。
**没有目标可作用。**

## 6. 勘误:k-th 值的并列组是 24–110,不是 ~19,000

`20261020_onepass/README.md` 的最终裁决与 `C600U-algorithm-choice.zh.md` §2.4 都说
"k-th 值处并列 ~19K 元素"。**该数是误读**:19,416 = 23,462 − 4,046 是高于某个
**12 位桶下限**(值 2.0,横跨多个桶)的总人口,不是并列组。本目录
`sim_tie_bf16.py`(numpy,bf16 RNE 截断,官方 randn)给出精确并列组:

| 形状 | 并列组中位 / 最大 | count(≥kth) 中位 |
| --- | --- | ---: |
| bf16 V1048576 k512 | **29 / 36** | 532 |
| bf16 V1048576 k1024 | **53 / 65** | 1053 |
| bf16 V262144 k1024 | 49 / 54 | 1051 |
| bf16 V131072 k512 | 24 / 30 | 519 |
| bf16 V131072 k2048 | 83 / 110 | — |
| bf16 V129280 k512 | 24 / 33 | — |
| fp32 全部形状 | **1 / 2** | — |

一遍原型自己的计数(532 vs 490)就隐含并列组 = 42,与模拟一致。

**什么变了**:bf16 排除一遍的理由从"候选集必然 20–40×k 的结构性不可能"退化为
**行走速率算术** —— 过滤行走 ~930 GB/s 比 ADJ4 后的摘要行走(~1002–1034 GB/s)
**慢**,所以两遍仍然赢。结论方向不变,但论证强度降了一档,且依赖实测速率而不再
依赖分布性质。**fp32 则完全没有并列问题**(k-th 并列组 = 1),采样阈值一遍在
fp32 上是开放的 —— 即 §7。

## 7. fp32 采样阈值一遍(LiteTopK 路线;归属见下)

**算法**(= LiteTopK 的 sample-filter-select,arXiv 2607.11976;DeepSelect issue #13
要求归属,GLM-5.2 prefill 1.2×,vLLM PR #48726 / SGLang PR #32094 已用):
采样一段连续前缀(V/16),建直方图,取其第 m 大有序 key T(裕量 m ≈ 1.4k·s/V,
k<1024 用 1.6k);**一遍**整行行走把 {key > T} 收进 4096 项 arena(24 KB:
idx32[4096] + key16[4096] sidecar);smem 内精化(12 位直方图 → 子桶;仅对罕见的
key_hi 并列组回读低位);欠收(count<k)或溢出(>4096)回退现有 coarse12 两遍。
收尾走不变的契约半。

**可行性(本目录 `sim_sample_np.py`,官方分布,模拟的 12 位桶人口 1380 中位 vs
设备实测 1336/1403/1464 —— 分布已验证)**:

旗舰 `(4096,131072,2048)`,256 行:

| 采样 | 裕量 | E[count] | sd | min | max | P(<k) | P(>cap) |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| V/8 | 1.40k (m=358) | 2863.7 | 143.6 (5.0%) | 2517 | 3260 | 0 | 0 |
| V/16 | 1.40k (m=179) | 2863.5 | 217.1 (7.6%) | 2347 | 3540 | 0 | 0 |
| V/32 | 1.40k (m=90) | 2897.5 | 299.4 (10.3%) | 2184 | 3940 | 0 | 0 |

k=512 格:s=V/8 1.40k → min 534,P(<k)=0;s=V/16 需 **1.60k**(1.40k 有 1.56–6.25%
欠收);s=V/32 在 k=512 上欠收 6–25%,弃。其他 k2048 格(V107520/V66551/b256)
在 s=V/16 1.40k 下全部 P(<k)=0、P(>cap)=0。

**成本模型**(旗舰,现 5,562.8 µs;单遍流量 2.147 GB):

| 收集行走速率 | 采样 | 一遍行走 | 精化 | 合计 | 加速 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 772 GB/s(=现两遍均速,下界) | 0.17 ms | 2.78 ms | ~0.2 ms | **3.15 ms** | 1.77× |
| 1200 GB/s | 0.17 | 1.79 | 0.2 | **2.16 ms** | 2.58× |
| 1400 GB/s | 0.17 | 1.53 | 0.2 | **1.90 ms** | 2.93× |

网格影响:三个大 fp32 格合计 −14.0…−14.6 ms ≈ **全网格 −6%…−15%**(对 133 ms
的 ADJ4 后网格约 −10.5…−11%)。区间来自未知量:fp32 行走是 MLP 受限(两遍都是
772 GB/s 所指)还是收集已接近墙。772 GB/s 时逐元素原子仅 6.9 G/s/AP,对 ~14 G/s/AP
的天花板**不是原子受限**,所以占用/MLP(640 线程;2 vs 3 CTA/SM 在飞字节 41→62 KB)
是首要嫌疑 —— 探针、驱动回答的占用、线程宽度扫描排在算法改动**之前**,且两者
可复合(先修 MLP,采样路线的一遍行走直接受益)。

**风险与回退**:欠收/溢出都回退现有两遍(已模拟 P≈0);采样段是连续前缀,
对有序输入有偏 —— 官方/生产是 randn 分布,且欠收回退保底,但值得在文档里记一笔。

## 8. 杠杆排序(离线判断,设备验证顺序见 §9)

1. **相位探针 + 占用 + 线程宽度**(`20261021_coarse12_phase/`,已备好):裁决
   47%-of-墙的归因(MLP vs 原子),决定采样路线的预期收益取区间的哪一端。
2. **fp32 采样阈值一遍**(§7):1.8–2.9× 于三个大 fp32 格,全网格 −6…−15%。
3. **DG chunks 内核结构的 b≤2 移植**(§2.1):C500 实测 0.58×,但 C600U 上
   b1/b6 合计仅占 fp32 的 0.9%,且需要解除 `f32_chunks_applies` 的 sm_count==104
   限制 —— 价值小、路由改动大。
4. **fp32 split 的浪尾 chunk 模型**(§2.3):策略参考,非预测收益。
5. **单内核收尾**(§2.2):预期小。
6. **bf16:无。** NaN 税、hist1a/b、collect、list 全部在实测下界。

## 9. 上机顺序(pod 可用时)

1. 干净树 `./develop.sh` → `CUDA_VISIBLE_DEVICES=1 ./run_bench.sh --set-baseline`
   (恢复 ADJ4 后基线;基线目录必须有 `run_header.txt`)→ 提交 `perf_data/` +
   重绘 PNG。
2. 复制树、`patch_coarse12_phase.py`、第二次完整构建、跑相位探针(构建期间
   设备 0 开 CUDA-graph 保活)。
3. `maca_kernel_doctor` 驱动回答占用 + 线程宽度扫描(640 → 候选宽度)。
4. fp32 过滤+暂存微基准(预设阈值的一遍行走)—— 采样路线的关键未知量。
5. 以上任一指向 MLP/占用,先修再回头评估 §7 的区间端点。

## 10. 证伪清单

- 采样路线欠收:构造 count(key > T) < k 的行(退化分布、重尾),必须走回退且答案
  仍满足契约。
- 采样路线溢出:count > 4096,同上。
- 连续前缀偏差:有序/半有序输入上的欠收率。
- 相位探针若显示 pass-2(collect)也远慢于墙,则 §7 的区间下端(1.77×)才是诚实的
  预期;若 collect 接近墙,采样路线收益主要在上端。
- bf16 一遍的重估条件不变:生产数据被证并列稀疏(不是现在的 randn)。
