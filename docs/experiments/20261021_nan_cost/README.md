# 折叠进 pass 1 的 NaN 扫描,在 in-situ 下的价格(2026-10-21)

设备:MetaX C600-U(28 AP,family 1600,MACA 3.8.1.3,device 1),产物
`281cc660`(ADJ4,HEAD `14d66b8` + 本日记录)。官方形状(`indices_type=int32`、
`return_value=False`、`abort_when_nan_found=False`)。

## 0. 为什么量它

契约的 NaN 扫描折叠在 pass 1 的行走里(`hist_add_bf16_wide<kNan,…>`):
每个 32-bit 字一次 SWAR,`z |= (w | 0x80008000) - 0x7F817F81`,bit 15/31 为 1
当且仅当该半字是 NaN 位型(65,536 个半字模式上验证过)。隔离微基准里它值
**17.4%**(1295.6 → 1070.7 GB/s,ADJ4 文档)。问题是这个数在核内是否成立。

## 1. 方法:不用重新编译

`check_nan` 在 row 核里是**运行期 bool**,不是模板参数
(`contract.cuh:626`:`fold_nan = params.check_nan && !kPreSelected`),所以
同一个产物既能跑"扫描"也能跑"不扫描",交替计时就把时钟和温度放在两边。
每格 3 轮 × 每轮 15 次,取中位;输入 `randn`→bf16,无 NaN。

| 格 | 扫描开 | 扫描关 | 差值 |
| --- | ---: | ---: | ---: |
| b4096 V1048576 k512 | 11.092 ms | 9.525 ms | **+16.45%** |
| b4096 V1048576 k1024 | 12.578 | 11.089 | **+13.42%** |
| b 512 V1048576 k512 | 1.636 | 1.461 | +11.96% |
| b4096 V 262144 k512 | 4.278 | 3.903 | +9.60% |
| b4096 V 131072 k512(块直方图臂之下) | 3.179 | 2.974 | +6.89% |

隔离微基准的 17.4% 在旗舰格上成立(**16.45%**),而且这是契约成本:
`check_nan=True` 是默认,官方网格、正式调用都付它。

## 2. 它已经在下限,别重写

把这个 SWAR 写成"更省指令"的形式——`(w | 0x80008000) - 0x7F817F81` 直接累加,
最后再 `& 0x80008000`——**一个指令都省不下来**:两种写法经 `cucc -aop -S
-maca-device-only` 编出来的设备指令数相同(各 20 条/16 次迭代),因为 LLVM 本来
就会把 `(a&M)|(b&M)` 归约成 `(a|b)&M`。SASS 里每个字是 `or_b32` + `add_u32`
(+ 三输入 `or3_b32` 归并),即 **每字 2 条 ALU、每元素 1 条**,这就是地板。

另一条看似可行的路——用块级极值代替逐元素测试(NaN ⟺ key ≥ 0xFF81 或
key ≤ 0x007E,所以块的 max/min 就够)——也不便宜:max 树已经在算,但 min
每元素要一次比较+选择,与现在的每元素一条 ALU 打平,还要多一棵 3 步 min 树
和一张新表。**结论:不要动这个测试。**

真正能省掉它的只有"不扫每个元素",而那会打破契约:负 NaN 的 key 在
`0x0000..0x007E`(最小端),它所在的块**不会**被块直方图的列表保留,所以
hist1b / collect 只走保留块的行走覆盖不到它。

## 3. 对下一步的意义

旗舰格的相位(blockhist §9)是 hist1a 73%、hist1b 8%、list 7%、collect 11%。
hist1a in-situ 跑 ~1002 GB/s,其中约 16% 是这次量到的 NaN 税;把税去掉它才
~1195 GB/s(隔离无 NaN 是 1295.6)。所以"hist1a 离墙还差多少"这个问题要先把
这 16% 扣掉再问——**walk 本身的余量约 16%(1002→1195),不是 35%。**
