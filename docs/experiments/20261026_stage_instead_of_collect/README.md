设备:MetaX C600-U(28 AP,family 1600,MACA 3.0.1436.20261017,
torch 2.10.0+metax20261017.1120),设备 1。

产物收据(`ab_snapshot.py` 子进程打印的、它**实际加载**的 `.so` md5 前 12 位):

| 臂 | md5 | 说明 |
| --- | --- | --- |
| base | `3bfbcc31cdb2` | `/root/ds_base`,HEAD `70591ab` 的 xcore1600 产物 |
| staged | `883fcf249b74` | 本改动,即最终交付的产物(8000 例 sample gate 与 122 格性能网格跑的就是它) |

## 0. 结论

1. **在一个够密的块直方图行上,计数那一趟顺带暂存候选,第三遍读整行就没有了。**
   扫掉的是 `collect`(在 `b4096 V131072 k512` 上占该格的 27.4%,见
   `docs/experiments/20261025_row_walk/`),`b4096 V131072 k512` 因此
   **2880.1 → 2653.0 µs(−7.9%,372.8 → 404.7 GB/s)**。
2. **收益随行长单调衰减,这与被删掉的那一趟的份额一致**:
   V=131072 是 −7.9%,V=262144 −6.7%,V=524288 −4.1%,V=1048576 −2.2%
   —— 行越长,pass 1 的 walk 越占主导(73.3%),而 list 上的两趟越短。
3. **同一个 `topk` 下 k 越大收益越大**:`b4096 V262144 k1024` **−7.7%**,
   因为闸门是密度(`topk <= length/256`),k 越大窗口越大、collect 越贵。
4. **"把直方图挪到 arena 上"这个变体是否证的**:它去掉 walk 里的每元素共享
   原子,但要在第二趟按索引回读 arena,7/8 个分组都更慢(见 §3)。
5. **不在闸门内的短行没有回归**:53 个非 staged 格的比值中位数 1.0055,
   p10/p90 为 0.975/1.029,且同一格内既有变快也有变慢的(如 `k512 V1024`
   同时有 0.968 与 1.039)—— 这是 A/B 的噪声底,不是代码路径(那条路径的
   SASS 没变,MT 寄存器也没变,见 §4)。

## 1. 机制

块直方图臂拿到的是**块**的切点:`#blocks(max >= cut) >= topk`,于是
`#elements(>= cut) >= topk`,于是元素阈值 `T >= cut`。所以切点保住的块里,
每一份能进窗口的元素都被那一趟读过 —— 既然读到了,就顺手写进 arena
(`s_input_flat`,即块直方图自己那 16 KB,扫描之后早已死掉),只数它0的高字节
(256 bin,静态 `s_histogram`)。

两个事实让它精确,而不是近似:

- **元素阈值在块切点之上**,所以窗口里的元素**全部**在 arena 里 ——
  闸门 `num_staged <= SMEM_INPUT_SIZE` 就是这件事的检查,失败就退回原来的
  计数走查(那条路径一行没改)。
- **扫描只读它落点及其之上的计数**,而对这些字节,暂存的计数是全行计数:
  落点 bin 一定 `>= cut`,被 `bin < cut` 提前返回的元素都严格低于落点 bin。

落点的 16 个子 bin 不在 walk 里数:那是 `narrow()` 的事,它在 arena 上把
落点字节的成员再走一遍(数量是候选数,不是行长)。

于是这个臂的数据流从四遍读变成三遍:

| | 改前 | 改后 |
| --- | --- | --- |
| pass 1 | 整行 walk → 块 max 摘要 | 同 |
| pass 2 | list walk → 4096 bin 元素直方图 | list walk → 高字节直方图 **+ 暂存** |
| pass 3 | list walk → 收集进 arena + 16 bin 直方图 | *(没有了)* |
| refine | arena 上的 16 bin 直方图 + emit | 同 |

## 3. 被否证的变体:把高字节直方图挪到 arena 上

既然 arena 里已经有全部候选,直觉上应该"walk 只暂存、事后再在 arena 上数",
这样 walk 里每元素就只剩一个位置原子和一次存储,比改前那趟 list walk
(每元素一个 4096 bin 共享原子)还便宜。

实测相反。同一批格,`--rounds 2`,与 §2 同一条 base:

| 组 | walk 带原子 | 直方图挪到 arena |
| --- | ---: | ---: |
| k512 V131072 | 0.9102 | 0.9285 |
| k512 V262144 | 0.9383 | 0.9503 |
| k512 V524288 | 0.9672 | 0.9737 |
| k512 V1048576 | 0.9845 | 0.9885 |
| k1024 V262144 | 0.9294 | 0.9611 |
| k1024 V524288 | 0.9745 | 1.0042 |
| k1024 V1048576 | 0.9824 | 1.0011 |
| k2048 V1048576 | 0.9258 | 0.9492 |

8 个分组里 7 个更慢,`k1024 V524288` 上收益整个消失。原因是被挪走的那一趟
不是免费的:`s_input_flat[i]` 是**索引**,事后计数要拿它回行里取原值,
那是一次按索引的、跨步的全局读;而"顺带数"时那个 `key` 已经在寄存器里。
省下的一个共享原子换回一次全局读,不划算。

(该变体已回退,不在本树的提交里。两次运行的非闸门格中位数分别是 1.0045 与
1.0211 —— 两次会话之间有约 1.7% 的系统性漂移,所以跨会话比较只看同一次运行内
的相对次序,这一点正是它给出的结论。)

## 4. 资源

`mxcc --resource-usage`,同一组实例化文件,两臂各编一次:

| 实例化 | base MT/ST | staged MT/ST | 静态 smem |
| --- | --- | --- | --- |
| `bf16 i32 block_512 si1 rv0 sv0 pre0` | 64 / 60 | 64 / 64 | 4936 → 4948 B |
| `bf16 i32 block_1024 si1 rv0 sv0 pre0` | 62 / 60 | 62 / 64 | 4936 → 4948 B |
| `bf16 i32 block_1024 si0 rv0 sv0 pre0` | 60 / 60 | 60 / 64 | 4936 → 4948 B |
| `bf16 i32 block_512 si0 rv0 sv0 pre0` | 62 / 60 | 62 / 64 | 4936 → 4948 B |

**MT 寄存器一格没动**,ST 从 60 涨到 64,静态共享内存 +12 B(`s_nstage` 一个
`uint32_t`,加上对齐)。所以占用率不变:BLOCK 1024 仍然是每 AP 1 个 CTA,
BLOCK 512 仍然是 2 个。这也是 §2 里非闸门格没有回归的解释 —— 那条路径的
指令流和寄存器都没变,看到的 ±2.5% 是噪声。

## 5. 门禁

产物 `883fcf249b74`,设备 1:

| 门 | 结果 |
| --- | --- |
| `tests/contract_test.py --backend maca_c` | **74 / 74** |
| `tests/contract_test.py --backend torch` | **71 / 71** |
| `tools/sample_gate.py --sample 8000 --seed 20261024` | **8000 / 8000**,0 fail / 0 crash / 0 skip,645 s(12.4 例/秒) |
| `stage_probe.py`(本目录,定向) | **72 / 72** |
| `tests/test.py --perf-only -nc --backend maca_c` | **122 / 122** |

`stage_probe.py` 是为此改动写的:官方 8000 例的抽样上限是 2^26 元素,
闸门内的行(b4096 起)基本都在上限之外,所以它自己画一张网格 ——
9 个形状 × 4 种分布 × 2 种索引类型。四种分布各有分工:

- `normal`:官方分布的形状(正态取整到 bf16);
- `ties`:只有 8 个不同取值,阈值 bin 极度拥挤;
- `equal`:整行同值 —— 每个元素都 `>= cut`,`num_staged = V`,
  **故意让 arena 溢出**,走的正是那条退回计数走查的路径;
- `dense`:后半行是一片等于 0.5 的平台,恰好横跨切点。

检查的是合同本身(索引在界内、唯一、`value == input[index]`),外加一条比
合同更强的**值多重集**断言:`sorted(selected_values) == sorted(topk_values)`。
用值而不是索引,平局就不会让它含糊。

## 6. 架构边界

改动全部在 `csrc/maca_kernels/common/radix_row_bf16.cuh`,`common/` 是三个
family 共编的,所以 xcore1000 / xcore1500 的产物**同样变了**,本记录只在
xcore1600 上测过,另外两个 family 未测(也没有可用的 C500/C600-A 板子在场)。
实例化表、模板参数集合、`setup.py` 的源列表都没动:产物里
`topk_kernel_radix` 60 个、`__device_stub__` 87 个、`__tvm_ffi_*` 2 个,与改前一致。
