# 第二趟到底跑多快 —— skim 的速率实测（2026-10-10）

**为什么量这个。** `docs/experiments/20261009_c500_dsa_decode/README.md` §9.4 给的
1.74×（整网格 −29%）是**两个实测量相乘**得到的：相位占比（§9.3 内核时间戳）× 保留比例
（`probe_block_skip.py`）。乘之前还差一个假设——"skim 过的那趟每字节与整趟同速"。
§9.6 第 3 条把它点名成"预测里的上界假设……**这是下一步第一个该量的数**"。
本节就是那个数。

## 协议

- **数据**：官方生成器的分布（`lib.NormalFloatDistribution`，即 `randn`），按
  `lib.generate_testcase` 的样子按 1024 B 行对齐后切片，写盘成 `.data`（行）、
  `.summary`（每 64 元素块的最大 12 位 bin，uint16）、`.t`（每行的 12 位阈值 T，
  取第 (k+1) 大的 bin）——`gen_data.py`。T 正是内核自己收窄会落到的那个 bin，
  所以"跳过 max < T 的块"与内核今天访问的集合**逐元素相同**。
- **被测的循环**是生产 collect 循环本体（`radix_core.cuh:1389-1433` 的对齐臂），
  抠出来单独编译：同样的 `idx = tx*8; idx += BLOCK*8` uint4 走法、同样的
  `output[atomicAdd(&s_counter,1)]` 发射、同样的 `bin == T` 进 arena + 16-bin
  细直方图（`skim_walk.cu`）。不在循环里的（折叠、收窄、refine）都不在读数里 ——
  本节量的是**那一趟的速率**，不是整核。
- **每档臂都在同一进程、同一份数据、同一占用率下与"不跳的整趟"配对**；计时区间外
  每次 128 MB 的 `cudaMemsetAsync` 冲 L2（`run_sweep.sh`，`iters=10`）。
- 臂：`unroll=1`（测试在循环里，plain）、`unroll=4`（plain，每次四块在飞）、
  `unroll=9`（list+gather，列表在**共享内存**、上限 2048）、`unroll=8`
  （list+gather，列表在**显存**）。

## 结果（`skim_walk_raw.txt`，device 2）

`skim/full` 是同一数据集内"跳过臂 / 不跳整趟"的比值；括号里是绝对 µs。

| V | 行数 | 保留块 | 整趟 µs | plain | plain unroll4 | list+gather 共享 | **list+gather 显存** |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1048576 | 1024 | 3.73% | 1818.7 | 0.447 | 0.439 | 0.138 (256.6) | **0.142** (264.0) |
| 524288 | 2048 | 8.48% | 1850.1 | 0.675 | 0.672 | 0.227 (420.1) | **0.223** (423.1) |
| 262144 | 1024 | 17.78% | 568.7 | 0.834 | 0.834 | 0.298 (170.2) | **0.312** (180.4) |
| 131072 | 4096 | 33.45% | 1159.8 | 0.982 | 0.989 | 0.477 (553.7) | **0.508** (591.1) |
| 65536 | 4096 | 55.25% | 721.9 | 0.951 | — | 0.650 (471.1) | **0.705** (508.7) |

（"共享"与"显存"两列是**不同批次**的读数：V=1M/128K 那两行来自同一进程的配对
（`skim_walk_raw.txt` 第一段），512K/256K/64K 的显存版是另起的进程。逐对比较时
看同一段的数：显存版贵 **+2.9% / −1.8% / +4.7% / +6.5% / +8.5%**（按该行的
`skim/full` 比）—— 512K 那一对是噪声级，其余单调变贵，行越短越贵。）

三条对照：

| 对照 | 读数 |
|---|---|
| 只扫摘要、一行不读（`summary_kernel`） | 63.5 µs（V=1M，1024 行）= 整趟的 **3.5%**；V=131072 时 56.7/1159.8 = 4.9%，V=65536 时 55.7/721.9 = 7.7% |
| **不跳的对照**：`keep_every=0`（每块都留）走 plain | 比整趟贵 **13.9%**（V=1M）、**1.5%**（V=262144）——这是"循环里多一个测试 + 多读一遍摘要"的价钱，也就是这条杠杆的**税** |
| 合成密度（V=1M，plain，`keep_every`）：25% → 1.036、6.25% → 0.987、1.56% → 0.794 | plain 的收益只在密度 ≲2% 时才出现；list+gather 在 17.8% 的实测密度上还有 0.298 |

**短行的单独一条**：V=65536 那一档的整趟本身只有 **730–744 GB/s**（墙的 45%）——
行短（每行 1024 个块）且每轮 L2 冲掉之后，整趟已经不在墙上了。那一档的 0.705 是
"相对一个不在墙上的整趟"的比值，所以把它套进预测时要按同一格的相位占比用，
不能读成"这一格省了 29.5% 的时间"。

## 读到什么

1. **§9.4 的"同速"假设是错的，而且错约 10×。** plain skim 在保留 3.73% 的块时
   还要 0.447 趟——它没有"少读就等比例变快"。机制上是每次跳过的判断与那一行 128 B
   的取数串在同一条延迟链上（生产循环是运行期行长，编译器不展开，每线程只有一个
   摘要在飞），把一个 `unroll=4` 的臂放上去也只从 0.447 动到 0.439。
2. **这条杠杆的形状是 list+gather，不是"带判断的循环"。** 先把保留的块压成一张
   清单（pass A 只读摘要），再对着清单纯取数（pass B 无判断、多块在飞）。显存版
   清单：**0.142 / 0.223 / 0.312 / 0.508 / 0.705**（V=1M/512K/256K/128K/64K），
   即 **7.0× / 4.5× / 3.2× / 2.0× / 1.42×** 于整趟。
3. **它有一条地板**：3.5–7.7% 的整趟（只扫摘要的时间），也就是说这条杠杆把第二趟
   从 100% 压到约 **14–51% + 4–8%**，而不是压到 0。
4. **清单放共享内存还是显存**：显存版贵 **+0.4%…+5.5%**（按整趟计；见上表注）。
   这笔钱买的是"没有容量上限、不占共享内存、不动占用率"——生产行核在 2 CTA/SM 上
   只剩约 9 KB 余量，而清单在 k=512 的实测峰值就有 807 项（4 KB 装得下，但 k≥1024
   装不下），所以**生产取显存版**：一个 shape 无关的代码路径，没有"超限回退"这条
   第二条路要走，而 smem 版省下的那 0.4–5.5% 要用一条只在容量内才正确的路去换。
5. **CTA 宽 1024 比 512 好**（gather 臂：0.147/0.243/0.351/0.603 对
   0.142/0.227/0.298/0.477）。摘要的**元素粒度保持 64**（= 一条 128 B 线 = 8 个
   连续 lane 的 uint4），§9.6 第 4 条说的"块宽另开一轮"仍待办。
6. **保留块数**（k=512，官方数据）：

   | V | 每行平均 | 每行最大 | p99 |
   |---:|---:|---:|---:|
   | 1048576 | 611.9 | 700 | 668.8 |
   | 524288 | 694.9 | 781 | 753.0 |
   | 262144 | 728.2 | **807** | 785.3 |
   | 131072 | 685.1 | 762 | 732.1 |

   候选数是个常数（约 600–800/行），所以行长翻倍、保留比例减半 —— 与 §9.4 的
   `probe_block_skip.py` 独立一致。

## 对 §9.4 预测的修正

`predict_grid.py` 用实测比值（显存版）+ §9.3 的相位占比重算（只动 k=512 且
V≥65536 的格；pass 1 按多写一份摘要计 1.6% 字节）：

**整网格 108.21 → 93.55 ms（−13.5%）**，34/147 格被移动。逐格：×1.85（V=1M）、
×1.67（512K）、×1.51（256K）、×1.29（128K）、×1.15（64K）。

这与 §9.4 的 −29% 相比砍掉一半多，差额全部来自"第二趟不是同速"这一条：
§9.4 假设第二趟以整趟同速读它要读的那部分（0.037 的字节比例），实测 list+gather
读到 0.142——即便最优形状，第二趟也不是"按字节等比例变快"，它有一条 3.5–7.7% 的
摘要地板和 0.14 量级的剩余代价。

仍然是**预测**：k=1024/2048 的格一个没测（那里阈值桶更宽、保留比例更高，收益更小
但方向不变），pass 1 多写摘要的代价是模型（1.6% 字节，未实测），生产整合的开销
（清单分配、pass A 的扫描、三处消费者改写）也都还没计。

## 落地的形状（本节的结论，实施另起一笔）

`radix_topk_row_bf16_b`（`radix_core.cuh:1275`）的四处改动，其余调用点（chunked
stage1/stage2）传空指针、逐字节不变：

1. **pass 1 多写一份摘要**：同一个 `idx = tx*8; idx += BLOCK*8` 走法（地址逐字节
   不变，只有循环条件改成按 8-lane 组统一的 `(idx & ~63) < vec_len`，这样最后那个
   不完整的组里 8 个 lane 一起进出、组内 shuffle 的掩码才有定义），每个 lane 取自己
   8 个元素的最大 key，组内 3 步 shuffle 归约，`(tx & 7) == 0` 的 lane 落一个
   `uint16`。SWAR 那两个 half 的 key 本来就在 `kp` 里（`kp & 0xFFFF` / `kp >> 16`），
   所以只多 2 个 `max`/字。代价 = 行字节的 1.6%。
2. **收窄之后、collect 之前建清单**（pass A）：`for (b = tx; b < nb; b += BLOCK)
   if (summary[b] >= T)` 就地 `atomicAdd(&s_nlist, 1)` 追进**显存**清单。T 就是
   12 位阈值 `s_high_threshold_bin_id`，与 collect 用的同一个。
3. **三个消费者都改走清单**（它们的集合与"max ≥ T 的块"逐个相同，跳过是保答案的）：
   collect 主走法、`remain_topk == 0` 的发射走法、以及 arena 溢出的整行重扫。
   走法：`for (j = (tx>>3); j < nlist; j += BLOCK/8)`，`base = list[j] << 6`，
   内层仍是 8 个连续 lane 各取一个 `uint4`。不完整行（`length % 8 != 0` 或指针
   未对齐）不建摘要、原路走今天的两条循环。
4. **开关按行长**：`length` 够长才建摘要（本节的四档实测从 V=131072 起是 2.0× 以上，
   V=65536 也有 1.42×；更短的行按 §9.4 的密度表收益趋 0 而税照付）。k 只影响收益
   大小，不影响正确性——清单在显存里没有容量上限，这也是选显存版而不是 smem 版的
   唯一理由（smem 版在 k=512 的实测峰值 807 项上要留容量判断和回退）。

## 可执行件

| 文件 | 是什么 |
|---|---|
| `gen_data.py` | 按官方生成器的分布造行，写 `.data` / `.summary` / `.t`（**数据不入库**，`/tmp/skim_data`） |
| `skim_walk.cu` | 被测量的四个臂（plain / plain-unroll4 / list+gather-smem / list+gather-gmem）与两条对照（摘要扫描、整趟），生产 collect 循环的逐字副本 |
