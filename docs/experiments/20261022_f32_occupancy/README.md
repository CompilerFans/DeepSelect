# fp32 行走为什么慢:占用率调查(2026-10-22,pod 32741,C600-U 28 AP,MACA 20261017)

状态:**已落地**(`kThreads` 640 → 512,见 §3)。问题:coarse12 两遍行走在核 ~780-880 GB/s(官方 5.618 ms
旗舰格 × 相位份额 43.3%/49% 折算),同形状复刻微基准 1226-1310 GB/s ——
~40% 的差距归因为何。

## 1. doctor + 驱动回答的占用(已测)

`maca_kernel_doctor`(编译 TU,`--resource-usage`)读数:

| 构建 | 寄存器 | 栈帧 | 静态 smem |
| --- | ---: | ---: | ---: |
| `topk_coarse12_kernel<640>` | 51 MT / 76 ST | 0 | 1308 B |
| `topk_coarse12_kernel<512>`(落地构建) | **32 MT / 46 ST** | 0 | 1308 B |

512 的寄存器反而更低(32 < 51)。注意 doctor 的纯 Python 占用模型
(`lib/occupancy.py`)按 **64 KiB/AP** 算,对 512 × 17,692 B 给出 75%(= 3 CTA)
—— 那是 C500 的答案;本 pod 的 C600U 每 AP 是 128 KiB(torch
`shared_memory_per_multiprocessor = 131072`,`max_threads_per_multi_processor =
2048`,`regs_per_multiprocessor = 131072`),所以占用**只认驱动**。

驱动回答(`cudaOccupancyMaxActiveBlocksPerMultiprocessor`,直接问真核 —
`/tmp/occ512b.cu` include `topk_coarse12.cuh` 实例化 `<512>`,与先前的
`/tmp/occ_c12.cu`(`<640>`)同一仪器):

| 构建 | 动态 smem = 16 KB(生产) | 动态 smem = 0(对照) |
| --- | ---: | ---: |
| `coarse12<640>` | **3 CTA/SM**(1920 线程) | **3 CTA/SM** |
| `coarse12<512>` | **4 CTA/SM**(2048 线程) | **4 CTA/SM** |

**上限是 2048 线程/AP 的天花板,不是 smem,也不是寄存器**:640×3 = 1920,
4 个 CTA 需要 2560 > 2048;寄存器 51 MT × 640 × 4 = 130,560 ≤ 131,072 本来够
4 个。smem(1308 + 16384)× 7 ≈ 124 KB 也够 7 个 —— 线程数是唯一瓶颈。
**512 线程 = 4 CTA = 2048 线程满填**(驱动读数),且在飞字节 30 → 32 KB(+7%),
复基准同形状 512 vs 640:纯读 +10.6%、逐元素原子 +6.4%、过滤+暂存 +6.5%。

在核 walk 已带 OUT=2(`topk_coarse12.cuh` 的 `ARCH_REGS_PER_AP >= 131072`
门,xcore1600 满足),所以差距不在在飞 float4 数。

## 2. 线程宽度在树扫描(一行改动,`kThreads` 符号化)

`topk_coarse12.cuh:67` 的 `kThreads` 是唯一拼写处(声明、显式实例化、
`__launch_bounds__`、`<<<B, kThreads>>>` 同步,`74e3fbb`)。512 构建冒烟
(in-tree,官方形状,pod 32741):

| 格 | 640(基线 CSV,pod 30752) | 512(本 pod) | 变化 |
| --- | ---: | ---: | ---: |
| b4096 V131072 k2048 | 5.618 ms | **5.334** | −5.1%* |
| b4096 V129280 k512 | 5.330 | **4.378** | −17.9%* |
| b4096 V107520 k2048 | 4.704 | **4.441** | −5.6%* |
| b256 V131072 k2048 | — | 0.424 | — |

*跨 pod 读数,仅作先导 —— 其中 −17.9% 那一格没有复现(同 pod A/B 是 −4.3%),
是跨 pod/跨 toolkit 的噪声。判定只看 §3 的同 pod 交替 A/B。

## 3. A/B 与门禁

同 pod、同 device 轮换 A/B(`ab_targeted.py`,本目录):两臂 `t640`
(md5 `ccf5631f`)与 `t512`(md5 `5958dcea`),3 轮交替,每臂每轮 9 次取中位,
官方调用形状(`indices_type=int32, return_value=False,
abort_when_nan_found=False`,device 1)。比值 = t512 / t640,< 1 是 512 更快:

| 格 | t640 | t512 | 比值 | t640 三轮 (µs) | t512 三轮 (µs) |
| --- | ---: | ---: | ---: | --- | --- |
| f32 b4096 V131072 k2048 | 5743.1 µs / 373.9 GB/s | **5425.4 µs / 395.8 GB/s** | **0.9447×** | 5731 / 5771 / 5743 | 5415 / 5427 / 5425 |
| f32 b4096 V129280 k512 | 4662.7 / 454.3 | **4464.1 / 474.5** | **0.9574×** | 4657 / 4705 / 4663 | 4458 / 4477 / 4464 |
| f32 b4096 V107520 k2048 | 4829.6 / 364.8 | **4528.7 / 389.0** | **0.9377×** | 4830 / 4858 / 4820 | 4525 / 4553 / 4529 |
| f32 b256 V131072 k2048 | 538.9 / 249.1 | **518.8 / 258.7** | **0.9626×** | 532 / 540 / 539 | 518 / 519 / 525 |

| bf16 b4096 V1048576 k512(对照) | 11480.8 / 748.2 | 11467.8 / 749.1 | 0.9989× | 11481 / 11514 / 11469 | 11468 / 11468 / 11470 |
| bf16 b4096 V262144 k1024(对照) | 5571.2 / 385.5 | 5559.1 / 386.3 | 0.9978× | 5571 / 5609 / 5566 | 5565 / 5559 / 5557 |

GB/s 是算子自身的逻辑流量(`B·V·4` 或 `B·V·2`,单次读),与 `perf_data` 的
`bandwidth(GB/s)` 同义,不是核内纯读墙。三轮都同向,且两个对照(bf16)
比值 0.998 —— 512 的收益全部落在 coarse12 服务的 fp32 格上,bf16 路由不经过
这个核,所以不动。

**判定:瓶颈是 2048 线程/AP 天花板,不是 smem、不是寄存器。** kThreads=640
时 3 CTA/SM = 1920 线程,离 2048 差 128;4 个 CTA 需要 2560。smem
(1308 + 16384 = 17692 B)能放 7 个,寄存器(51 MT)按 4 个 CTA 算
51×640×4 = 130,560 ≤ 131,072 也够 —— 驱动读数(§1)两个对照都停在 3。
512 线程 = 4 CTA = 2048 整(驱动对真核 `<512>` 直接答 4),在飞字节 30 → 32 KB(+7%),复基准同形状
纯读 +10.6%、逐元素原子 +6.4%、过滤+暂存 +6.5%;在算子里是 3.7-6.2%
(五个 fp32 格),差值被算子的其余相位稀释。

**仍未到墙,这次只关掉了占用这一项。** 两遍行走本身在同形状复基准是
1226-1310 GB/s,核内按相位份额折算是 780-880 GB/s;512 之后核内约 820-925,
与墙(本 pod 1650 GB/s 量级,见 C600U 记忆)和复基准都还有距离。剩余差距在
相位结构 —— pass1 43.3% / narrow 2.4% / collect 48.6% / arena 5.6%
(640 构建的份额),两遍之间的串行段和空洞 —— 下一杠杆应从那里找,不是继续
加 CTA(4 已是天花板)。

门禁:512 构建(`/tmp/t512`,md5 `5958dcea`)上
`tests/test.py --backend maca_c --sample 342 -rf`,491 例 = 342 抽样正确性 +
147 官方网格 + 2 selector:**pass 486 / check_fail 0 / crash 0 /
unsupported 0 / skip 5**,5 个 skip 全是 `b4096` × `V≈0.4-1.0M` 的
`torch.cuda.OutOfMemoryError`(进程本身占着 ~45 GB,单卡 72 GB),是环境,
不是答案。

落地:`csrc/maca_kernels/common/topk_coarse12.cuh` 的 `kThreads` 640 → 512
(唯一拼写处,声明/显式实例化/`__launch_bounds__`/launch 同步),注释随之
更新;`csrc/maca_kernels/common/routing.cuh` 里"640 threads against 512"的
差异描述改为"块宽同为 512"。改动在 `common/`,编进三个 family 的产物;
测量只在 C600U(device 1)上做,C500/C600 未测。
