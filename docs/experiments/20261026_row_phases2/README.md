# 行 dataflow 的相位表(暂存走查之后):走查每行恒定 65 cycles/块,固定开销占 28–35% 却不决定墙钟(2026-10-26)

设备:MetaX C600-U(28 AP,family 1600,MACA 3.0.1436.20261017,
torch 2.10.0+metax20261017.1120),设备 1。被测源码是 pod 上的 `3b3b3b2`
(即 `walk_kept_blocks` 落到 `#pragma unroll 1` 之后的树)。

本目录两个文件:`phase_patch2.py` 把 `clock64()` 相位计时器插进
`radix_row_bf16.cuh` 的**副本**(每个锚点都断言唯一),`phaseprobe2.cu` 用
`cucc -O3 -std=c++20 --offload-arch=xcore1600 -DDEEP_SELECT_IS_BUILD_ON_MACA
-DDEEP_SELECT_ARCH=1600 -DDS_PHASE_TIMERS -I<副本根>` 编译成独立程序:

```bash
./phaseprobe2 <V> [k] [rows] [row.bin]
python3 phase_patch2.py csrc/maca_kernels/common/radix_row_bf16.cuh
```

它直接调用生产 body `radix_topk_row_bf16_b<512u, true, true>`(C600-U 在
batch ≥ 256 的官方长行格上 `radix_block_for` 选的就是 512),一行一 CTA,
1120 行,一行正态数据复制满,`clock64()` 差分记在每道屏障上。

**上一张相位表(`docs/experiments/20261025_row_walk/` §2)早于暂存走查
(`bd8c3db`)和 arena 打包(`100cc9b`),collect 那一相已经不存在了。** 这张是现
dataflow 的。

## 0. 结论

1. **保留块走查是行里最大的常数项,也是唯一与 V 无关的整块:每行恒 65
   cycles/块。** V=131072 时 683 块 → 45.4k cycles(36.2%),V=65536 时 542 块
   → 35.7k(39.2%)。两次的每字节速率一致到 0.5%(1.93 / 1.94 B/cycle/CTA),
   是 pass 1 的 **34%** —— **密度不是变量**(33% 与 53% 的保留率同价),
   所以这不是"取回粒度"的问题,是每块一次的取回代价。
2. **每行的固定开销(scans + 精化/发射 + 块表建 list)是 28–35%**:
   V=131072 时 35.4k/125.5k,V=65536 时 31.4k/91.1k。它的绝对 cycles 两种 V
   几乎相同 —— 短行格子的带宽就是被这块吃掉的。
3. **窄化(thread 0 的 16 次子桶串行链)是固定开销里最大的一件:4,851 cycles
   (3.9–5.4%),而它后面的屏障只有 1,988。** 它后面的屏障不是代价,取回串行才是:
   `break` 让每次共享读都等上一次比较的结果。把十六次读一次发出去,链确实从
   4,851 掉到 3,363(**−31%**),但**整行 cycles 与整算子都不动**
   (整行 +0.2%,121 格配对 A/B 中位 **1.0008**)。原因见第 4 条,改动因此**没有
   落地**。
4. **相位表的占比不是优先级列表 —— 4 CTA/AP 下只有搬字节的相位算数。**
   一行里碰 DRAM 的只有 pass 1(262 KB)和保留块走查(87 KB),约 90k cycles;
   一个 AP 上 4 个 CTA 就是 360k cycles 的内存工作挤进 125k cycles 的窗口,
   **超订 2.9 倍**。所以某个 CTA 的串行/共享/屏障相位被另外三个 CTA 的取回
   盖住了。这条把全部历史读数也解释干净了:动字节的改动 1–11%,动指令形状的
   改动 ~0.1%。
5. **三个"让第二阶段读得更快"的形状全输给现在的 list 走查**(§6):连续 + 标量
   body 85.4k、连续 + ADJ4 96.4k、list + 宽变换门 48.4k,对生产的 45.4k
   (V=131072)。list 读的字节只有整行的三成到五成,散列 1.9 B/cycle 对连续
   5.9 B/cycle 的 3 倍劣势被"少读三分之二"抵掉还有余 —— **这一档密度上
   list 走查已是这个设计空间的最优解,一次过(dataflow 级)也不是方向**。
6. **两件事被算术否证,不必再花一次测量**:把块切点抬高再按 `num_staged ≥ topk`
   回退(§4);以及"走查受 MLP 限制"(unroll 4 在它该服务的格子上 +3.3%,
   `20261026_unroll_width`),与 §3 的每块恒定代价一致 —— 加在途请求不改变
   每块一次的取回代价。
7. **图上最弱的那一列(`vocab = 16K`)走的是计数臂,瓶颈是第二趟整行 collect
   (41%)**,而且这一档内存根本没饱和(pass 1 每元素一个原子 + collect 两趟全行,
   43k cycles 里只有 8.5k 是 AP 的字节需求)。给它加宽门也输(18,045 → 18,995),
   是"加 body 更贵"的第三次。**这一档只剩"一次过"可走**:采样定切点 + 一趟连续
   暂存,按实测单价估 V=16384 是 **1.68×**、V=4096 **1.74×**;那是新增一条
   dataflow,本记录没有做(§7)。
5. **旧的每行换算口径是错的**:`20261025_row_walk` §2 写的是"打印值 × 28 / 1120",
   按驱动给出的占用率应是 **× 4 CTA/AP × 28 AP = 112 并发**,即每行 CTA 时间
   = `墙钟 / (行数/112)`。按新口径,整核在 V=131072 是 **70–71 µs/行 CTA**、
   1.76 GHz,与生产格 `b4096 V131072 k512` 的 2399 µs 对齐(2399/4096×112 =
   65.6 µs,探针高 6–9%,是探针只有 1120 行、wave 填充略差)。

## 1. 方法上的一件事:探针必须先爬频,否则墙钟差 3.5 倍

第一版探针(1 次预热 + 10 次计时)在 V=131072 报 2.32 ms,`whole` 读
113k cycles → 反推时钟 0.49 GHz;同一天另一次跑报 0.698 ms(1.62 GHz)。
**AP 空闲时在低频,几百毫秒的持续负载才爬到 1.76 GHz**,而整核一次只有
~0.7 ms,十次加起来不够爬频。

现在探针先跑 **300 次**再计时,`best` 与 `last` 一起打印,时钟由
`whole_cycles / 每行 CTA 墙钟` 反推打印出来,每次都在 1.74–1.78 GHz。

**cycle 数与时钟无关,所以相位占比本来就可信;但低时钟会把等待内存的相位
放大(同样的内存延迟在低频下折成更多 cycles)**,所以爬频对占比也是必要的,
不只是对墙钟。

占用率不是手算的:`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 对
`rowk` 与 `radix_smem_plan(512,false,true).total_bytes = 18,432 B` 直接回答
**4 CTA/AP**,112 并发。

`kcycles/行` 一列是 `cycles/1e3`,**不是微秒**:探针不知道时钟,时间要由
`whole / 1.76e3` 换算。

| 相位 | V=131072 k512 | % | V=65536 k512 | % |
| --- | ---: | ---: | ---: | ---: |
| pass 1(ADJ4 摘要走查 + NaN 票) | 44,469 | 35.4 | 23,726 | 26.0 |
| scan #1:折桶 4,096→256 | 3,189 | 2.5 | 3,155 | 3.5 |
| scan #1 + #2:256 宽 cumsum(两次) | 4,543 | 3.6 | 4,570 | 5.0 |
| narrow 的串行子桶链(两次) | **4,851** | **3.9** | **4,954** | **5.4** |
| narrow 的屏障(两次) | 1,988 | 1.6 | 1,596 | 1.8 |
| scan #2 的 arena 落桶 | 2,027 | 1.6 | 1,838 | 2.0 |
| 建保留块 list | 5,457 | 4.3 | 3,780 | 4.1 |
| **保留块走查(暂存)** | **45,365** | **36.2** | **35,719** | **39.2** |
| 精化 + 发射(含精化自己那次 cumsum) | 13,324 | 10.6 | 11,537 | 12.7 |
| 合计 | 125,471 | 100 | 91,129 | 100 |

两件与旧表不同、值得记下来的事:

- **collect 那一相没了,它变成了走查的一部分**:暂存走查边走边写 arena,
  所以"第二次走 list"和"收集"合成一次取回(`bd8c3db`)。
- **scan #2 现在是"arena 落桶 + cumsum + narrow"**,不再是"整行细直方图":
  arena 里已经带着 12-bit bin(`100cc9b`),这两个 loop 读的是共享内存,不是行。

## 3. 保留块走查:每块 65 cycles,与 V 和密度无关

| V | nlist | 字节 | cycles | cycles/块 | B/cycle/CTA | 占 pass 1 速率 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 131072 | 683 | 87.4 KB | 45,365 | **66.4** | 1.93 | 33% |
| 65536 | 542 | 69.4 KB | 35,719 | **65.9** | 1.94 | 35% |
| 131072(前一轮) | 683 | 87.4 KB | 44,253 | 64.8 | — | — |
| 65536(前一轮) | 542 | 69.4 KB | 35,786 | 66.0 | — | — |

`num_staged` 是 845 / 781,`use_list` 与 `staged` 都是 1120/1120 —— 也就是说
这一档两个 V 都走暂存臂,没有一格掉进计数回退。

**密度差 1.6 倍(542/1024 = 53% 对 683/2048 = 33%),每块代价不变。**
所以代价跟着"块"走,不跟着"行里剩下多少字节"走,也不跟着 DRAM 的取回粒度走 ——
如果是粒度问题,53% 密度应该比 33% 便宜。每块的代价是 8 lane 各一次 `uint4`
(`walk_kept_blocks`)、8 个元素的 key 变换与切点比较、以及被暂存的那 1.9% 的
两个共享原子。

`unroll 4` 在同一格上 +3.3%(`20261026_unroll_width` §2)与这条一致:每块
一次取回的代价与在途请求数无关,多展开只买到代码体积。

## 4. 被算术否证的两个方向

**抬高块切点 + `num_staged ≥ topk` 精确回退。** 现在 nlist 比 topk 多
1.33 倍(683 对 512),看上去有 25% 可省;回退判据也是精确的(暂存集里
若已有 ≥ topk 个元素,`k` 大元素必在其中)。但**回退要整趟重走**,所以设
切点按 `f·topk` 块来选时,期望代价是 `f·683 + p·683`,而必须 `p < 1-f`
才不亏;元素/块之比只有 1.24,`f = 0.9` 留给 `num_staged` 的余量只有 11%,
按行的分布,`p` 远大于 0.1。**这条不成立,不必测。**

**把 list 走查摊平成"遍历整行 + 查 block_max"。** 在 33% 密度上,整行
262 KB 按 pass 1 的 5.9 B/cycle 要 44k cycles,与现在的 45k 持平;在 53% 密度
上整行 128 KB 要 22k,确实比 35.7k 快 1.6 倍 —— 但这条形状已经在
`20261025_row_walk` §0 被否证过(90 MT,每 AP 掉到 1 个 CTA,整体 1.54× 慢),
它的代价不在字节上,在寄存器上。密度 53% 这一档要不要单独一条 arm,取决于
能不能写出一条不涨寄存器的摊平走查,而不是取决于这次的表。

## 5. 窄化:一次"把串行链拉直"的实验,和它给出的否证

`narrow` 是 thread 0 的一段:先读 `s_histogram[high+1]`,再从第 15 个子桶往下
走,`above + c > want` 就停。加两个计时器把它和它后面的屏障分开:

| | 两次调用合计 | 占整行 |
| --- | ---: | ---: |
| 跨点测试 + 串行子桶链 | 4,851(V=131072)/ 4,954(V=65536) | 3.9% / 5.4% |
| 尾屏障 | 1,988 / 1,596 | 1.6% / 1.8% |

十六次共享读配一次依赖比较,所以每一次读都要等上一次的结果。把十六个计数
**一次读完**、再跑同一条跨点规则的算术(`break` 换成 `hit` 谓词,`above` 在命中
后不再累加),语义一字不改,读就一次发出去 —— 跨点规则本身
(`above + c > want`,对窗口本身而不是对余量)没有动,它是这个文件里两次记过的
静默错答源。产物 `ca2b32d562e2`(18,300,312 B),对照臂 `16200ce50a27`
(18,394,520 B)。

**结果:链确实变短了,整行却一 cycles 没少,算子一格没动。**

| 读数 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 窄化的串行链(两次,`clock64`) | 4,851 | **3,363**(−31%) |
| 整行(`whole`,同一探针) | 125,471 | 125,726(**+0.2%**) |
| 整算子 A/B(121 格,3 轮配对) | — | **中位 1.0008**,`row` 路 1.0021,`split` 路 0.9875 |

(`tools/ab_snapshot.py --arm base=/root/ab_base --arm narrow=/root/ab_narrow`,
147 格、3 轮、每轮每臂 10 次,两个臂同一时段交替,子进程各自打印了它加载的
`.so` md5。工具把子进程的 `CUDA_VISIBLE_DEVICES` 设成它的 `--device`(默认 0),
所以这一轮跑在设备 0 上 —— 那里有 0.5 s 一次的心跳负载(16 MB 的 `mul` 加
`sync`,占空约 0.1%),两个臂同样承受,配对读数不受影响。`split` 那 16 格根本
不含这段代码,它们的 1.25% 是产物布局噪声 —— 产物小了 94,208 B。)

**为什么 1,488 cycles/行 不见了:4 个 CTA/AP 把内存管道超订了。** 一行里真正
碰 DRAM 的只有 pass 1(262 KB,5.9 B/cycle/CTA)和保留块走查(87 KB,
1.9 B/cycle/CTA),合计约 90k cycles;一个 AP 上同时有 4 个 CTA,于是
4 × 90k = 360k cycles 的内存工作要挤进一个 125k cycles 的窗口 —— **超订 2.9 倍**。
某个 CTA 在串行相位里不发请求时,另外三个正好在发,内存管道并不空闲,所以
这段串行时间被吸收掉了。这条对相位表的读法是决定性的:

> **相位表给出的 cycles 占比不是优先级列表。** 只有真正搬字节的相位
> (pass 1、保留块走查)是行的时间;共享内存、原子、串行链、屏障在 4 CTA/AP
> 下都是"免费"的,因为它们不占内存管道。

这也解释了这条路径上所有改动的大小:动**字节**的(暂存走查 `bd8c3db`、
arena 打包 `100cc9b`、密度下限 `6d6298e`、块表批读 `31d52fd`)都在 1–11%;
动**指令/串行/代码形状**的(`unroll` 宽度 `3b3b3b2` 是产物体积效应,
本节的窄化是纯零)都只在 0.1% 量级。

**因此这一版没有落地**:它是中性的,而中性改动不进树(多出来的 16 个计数
寄存器也没换来任何东西)。这段是本记录的主要产出 —— 它把后面所有的优化方向
重新指向"字节数与取回效率",而不是 cycles。

## 6. 三个"读得更快"的形状,全输给现在的 list 走查

第 4 条说行的时间只由字节和取回效率决定,于是自然的下一步是"让第二阶段读得更快"。
三个形状都在**同一个探针**上量了(同一份 body、同一 1120 行、同一 `clock64()`
口径),切点由探针填进 `ds_probe_cut`(1.15 × topk 大元素的 12-bit bin,所以
暂存集必是答案的超集,下游仍然精确):

| 臂 | 补丁 | V=131072 走查 cycles | V=65536 走查 cycles |
| --- | --- | ---: | ---: |
| 生产:list 走查(`walk_kept_blocks`) | — | **45,365** | **35,719** |
| 连续走查,标量逐元素 body | `onepass_patch.py` | 85,398 | 50,029 |
| 连续走查,ADJ4 + 宽变换 + 每 lane 门 | `adj4_patch.py` | 96,365 * | 57,118 * |
| list 走查 + 宽变换每 lane 门 | (第四臂,见下) | 48,404 | 38,558 |

\* ADJ4 那一版把整核也拖慢了(同一版的 pass 1 从 44,469 涨到 69,668 cycles,
寄存器/代码布局),所以 96k 不是这条走查的干净单价;但它比 list 走查多一倍,
结论不依赖那点污染。

- **连续 + 标量 body(85.4k)是"一次读完整个行"的价钱**:它读 262 KB,拿到的
  却是 3.1 B/cycle —— pass 1 的 5.9 是靠 ADJ4 四个 load 在途 + SWAR 宽度换来的,
  逐元素标量 body 只有一次 load 在途。
- **连续 + ADJ4(96.4k)更差**:它把 pass 1 的活重做了一遍,而在真的一次过
  dataflow 里这段要**取代** pass 1,不是加在它后面 —— 用它的单价算,
  一次过的整行 = 96k + 常数 30k + 采样扫描 12k > 现在的 125k。**一次过不是
  这条路的方向**,除非那条走查能在带暂存的前提下仍跑出 5.9 B/cycle,而这里
  两次尝试(B2/B3)都没做到。
- **list 走查 + 宽变换每 lane 门(48.4k)也输 3k**:每个 8 元向量先算 SWAR 最大
  key 再决定要不要走标量路,听上去免费(候选只占 0.45%),实际是给 100% 的向量
  加了 16 条 SWAR 算术,而散列取回的下限不在算术上 —— 与 unroll 4 同一条结论
  (`20261026_unroll_width`)。产物 `bf6da4734fa3`(+57,344 B),**未落地**。

**三个都输,原因是同一个:list 走查读的字节只有整行的三成到五成**(V=131072
33%、V=65536 53%),而连续走查要读满。散列取回 1.9 B/cycle 对连续 5.9 B/cycle
的 3 倍劣势,正好被"少读三分之二"抵掉还有余。**在这一档密度上,现在的
list 走查已经是这个设计空间里的最优解**;再要往下走,得换算法(一次过要能在
带暂存的前提下跑满 5.9 B/cycle),不是换走查的形状。

## 7. 短行那一档:图上最弱的 16K 列走的是计数臂,而它是两趟全行

README 里的 bf16 图按 batch × vocab 画 18 格,最弱的一列是 `vocab = 16K`(b4096 165
GB/s、b512 150、b6 11)。那一列落在块直方图闸门(V ≥ 128·k = 65536)之下,走的是
**计数臂**:pass 1 每元素一个共享原子建 4,096 桶直方图,pass 2 再整行走一遍 collect。

**探针必须先按生产的口径关掉块表**:`kSkipMinVocab`(65536)与
`kSkipMinRowPerSlot·k` 之下宿主根本不分配 `block_max`/`block_list`,而探针原来
无条件传表,量到的是生产不做的那份摘要。关掉之后(V=16384 k512,一行 43,417 cycles):

| 相位 | cycles | % |
| --- | ---: | ---: |
| pass 1(元素直方图,每元素一个原子) | 10,574 | 24.4 |
| **collect(整行第二趟)** | **~18,000** | **41** |
| 折桶 3,181 + cumsum 2,219 + narrow 2,120(两次扫描) | 7,520 | 17.3 |
| 细直方图 + 精化 + 发射 | ~7,000 | 16.1 |
| 建 list(闸门之下已无用) | 220 | 0.5 |

V=4096 k512 同形:pass 1 3,672(15.9%)、collect ~5,400(23%)、扫描 4.5k、其余 ~9k,
整行 23,151 cycles。

**这一档内存根本没饱和**:一个 AP 上 4 个 CTA × 每行 32 KB × 两趟 = 256 KB 的需求,
按 31 B/cycle 只要 8.5k cycles,而行是 43k —— 所以第 4 条"非取数相位免费"在
**长行**成立,在短行不成立:这里时间花在每元素的活上,不在字节上。

**给 collect 加宽门(每 lane 先算 SWAR 最大 key,再决定要不要走标量路)也是输**:
collect 18,045 → 18,995,整行 46,674 → 49,764(V=16384;V=4096 同向)。
这是同一条结论的第三次:**在这条路径上加 body,寄存器与调度付的价总比省下的多**。

**这一档真正剩下的路只有一次过**:切点先由**采样**给出(抽 1/8–1/16 行建直方图,
按 1.15·k 的秩取 bin),然后整行**一趟连续**走,把 ≥ 切点的元素暂存进 arena,再走
已经存在的暂存臂下游(arena 子桶 → cumsum → narrow → 精化/发射);`num_staged < topk`
就回退到今天的计数臂。按测过的单价算(连续暂存走查 2.6 B/cycle = 32 KB 花 12.6k
cycles),V=16384 的整行会是 ~26k cycles 对今天的 43k(**1.68×**),V=4096 ~13k 对 23k
(1.74×)。这是**新增一条 dataflow**,不是调一条循环,风险是寄存器(摊平走查 90 MT
的前例)与回退路径的正确性;本记录到此为止,没有做。

## 8. 一次过路由:做出来了,在它服务的每一格上都更慢,回退

按 §7 的设计实现了一版(采样定切点 → 一趟连续暂存 → 复用暂存臂的扫描与发射 →
`num_staged` 不够就回退到计数臂),门限是 `!block_hist && 对齐 && length ≥ 4096 &&
2·topk ≤ arena`。产物 `defe4c7b43ffd`(+1.7 MB)之后又有三版修正,最终 **117/117 通过但
在它服务的 48 格里全部更慢**,回退,不进树。

**三个在实现里踩到、值得记下来的坑:**

1. **连续走查必须止于 `list_end`,不能到 `vec_len`。** 尾部循环从 `list_end` 起,
   两者之间(行 8 对齐但不 64 对齐时,最多 7 个块)会被**暂存两次**,arena 里同一个
   index 出现两遍,发射时同一格写两次 —— 表现是 harness 的 `unique index` 检查失败,
   且**只在 b6 那几格**出现,因为那里走 chunked split,而 split 的 stage 2 传给行核的
   `length` 是**分块长度**,不保证 64 对齐。行核自己的 list 走查之所以没事,是因为它
   只覆盖整块。
2. **采样的切点必须是 12 位,不能是字节。** 正态行顶部一个高字节里能装几千个元素,
   按字节切的暂存集直接溢出 arena(4,096),于是**每一行都回退** —— 既付了采样又付了
   计数臂,整格 2.1× 慢。切点要在样本自己的 4,096 桶里对该字节再做一次 `narrow`。
3. **采样直方图要用 4,096 桶而不是 256 桶**:正态分布把质量压在几个桶上,256 桶时
   这些原子在少数地址上串行。

**为什么做完还是不划算:`clock64` 相位表给了答案。**

| V=16384 | 计数臂 | 一次过 |
| --- | ---: | ---: |
| 第一趟(计数臂:元素直方图 / 一次过:采样 + 暂存走查) | 10,574 | **28,009** |
| 第二趟(collect) | 18,000 | 0 |
| 合计 | 28,574 | 28,009 |

采样按 1/8 行取样,代价约 **7 cycles/采样元素** —— 正态分布的众数桶让共享原子串行,
于是 1/8 的样本要 ~15k cycles,正好抵掉它省下的那一趟。整行 46.9k 对 43.4k,格子
1.20–1.27× 慢(这还是在 12 位切点、基本不回退之后;更早的版本 2.1× 慢)。

**没试的那一档**:1/32 采样(~3.6k cycles)理论上把该格压到 ~32k 对 43.4k = 1.35×,
代价是秩估计的噪声大三倍、回退率上升(每次回退白付一整趟),而且产物已经 +1.7 MB,
按 `20261026_table_batch` 记过的规矩,那笔税由 105 个不受益的格子分摊。**本记录停在
这里,不再往这条路上投入**;要重开的话,从"免原子的采样"开始(样本先排序或按块最大值
取序),而不是把采样比例调小。

## 9. 未测与边界

- 只测了 `k = 512`、V = 65536 / 131072 两个 short-row 重点格;`k = 1024`、
  V ≥ 262144、以及 fp32 行都未测。
- 全部在 `csrc/maca_kernels/common/` 的副本上做,不改生产树;探针是独立程序,
  不经 torch、不经本树构建系统。
- 相位边界都是 `__syncthreads()`,屏障会吸收上一相位尾部仍在途的内存延迟,
  所以"某相位的 cycles"含一部分前一相位的尾巴。这一点对 narrow 的拆分不适用
  (它前面和后面各自就是屏障,且环路本身在 thread 0 上是纯串行的)。
