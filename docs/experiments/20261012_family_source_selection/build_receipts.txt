D. the .so md5s differ -- MEASURED, and it is the LINK that is nondeterministic
--------------------------------------------------------------------------------

  The md5s are not equal (9ca8450c.. -> f60f7549.. on xcore1000).  That is not
  a signal about the change, and the reason is sharper than 'builds are
  nondeterministic'.  Split it by stage:

  D.1  THE COMPILE IS DETERMINISTIC.  The build's own xcore1000 cucc command,
       run four times (two with the -o retargeted, two verbatim):
         md5 of the produced maca_topk.o = c7b9b7b307e0dff86d6f7be030b994cb
         6614560 B, all four runs, cmp -l empty between them.

  D.2  THE LINK IS NOT.  The build's own xcore1000 gnu command, run twice on
       that same object, into two different filenames:
         link 1 -> md5 1081e6741aba6f9bd9a43dfccd8d0c35  6464392 B
         link 2 -> md5 043eb2f535decd5415a9f0c395396def  6464392 B
       cmp -l between them: 6 bytes, offsets 0x623a06..0x623a0b, ONE cluster.
       The text around those offsets reads:
           ...ay_entry | ds_link_probe-ac125e.cpp | __FRAME_END__...
       i.e. the whole difference is inside a generated intermediate filename.

  D.3  THE STRING IS MINTED AT LINK TIME, with a per-invocation random suffix.
       In one single build's three artifacts:
         deep_select_maca_xcore1000.so    maca_topk-d1037b.cpp
         deep_select_maca_xcore1500.so    maca_topk-b7550c.cpp
         deep_select_maca_xcore1600.so    maca_topk-221bd9.cpp
       -- three different suffixes from ONE build, so it is per link call,
       not per build or per family.  And in the compile-stage object:
         strings -a maca_topk.o | grep -E 'maca_topk-[0-9a-f]{6}\.cpp'  ->  empty
         strings -a maca_topk.o | grep -E '\.cpp'                      ->  empty
       The compile emits no such name at all, which is why it is deterministic.

       The stem is the OBJECT the link was handed, not the source: the link of
       build/temp.../maca_topk.o produces 'maca_topk-<hex>.cpp', and the control
       run above, which linked /tmp/ds_link_probe.o, produced
       'ds_link_probe-ac125e.cpp'.  So the rule is cucc's: its link-stage
       intermediate is named <basename of the input .o>-<6 hex>.cpp, and the
       6 hex is minted per invocation.

  D.4  SO: the receipt for 'this build change changed nothing' is the
       byte-identical command lines (B) plus the identical artifact SIZES
       and the identical symbol counts (C) -- never the md5.  Comparing the
       COMPILED OBJECT is a stronger receipt than comparing the linked .so,
       because it removes the one nondeterministic input.

  This is the same 6-byte/one-filename-string shape the repository recorded
  before (CLAUDE.md Build section: 0909cc25.. -> 4b29550a.., 6 bytes at
  0x3a2af8..0x3a2afd in '...maca_topk-02b752.cpp\0__FRAME_END__...').  What
  this measurement adds is WHICH STAGE: it is the link, and a compile-only
  comparison is therefore stable.

F. one object path, three compiles -- why the families cannot share a stale .o
--------------------------------------------------------------------------------

  A reader looking at the build log will notice the thing that looks wrong:
  all three per-family Extensions write the SAME object file,

    build/temp.linux-x86_64-cpython-310/csrc/maca_kernels/xcore1000/maca_topk.o

  -- the `xcore1000` there is the *source's* directory, not a per-family
  artifact directory.  So the worry is fair: could family 1500 link family
  1000's object?

  No, and this is checkable in the same log rather than argued.  Every run
  above prints THREE separate `[1/1] cucc ...` compile lines, one per family,
  distinguished by their flags:

    [1/1] cucc ... -offload-arch=xcore1000 -DDEEP_SELECT_ARCH=1000 ... -o .../maca_topk.o
    [1/1] cucc ... -offload-arch=xcore1500 -DDEEP_SELECT_ARCH=1500 ... -o .../maca_topk.o
    [1/1] cucc ... -offload-arch=xcore1600 -DDEEP_SELECT_ARCH=1600 ... -o .../maca_topk.o

  The compile line is part of the target's identity as far as ninja is
  concerned, so a changed `-offload-arch` / `-DDEEP_SELECT_ARCH` re-runs the
  compile into that shared path; the object is never silently reused across
  families.  The three `.so`s carrying three different device images (and two
  different sizes) is the same fact from the other end.

  Verified independently of the build by the run that produced this file:
    grep -oE '\-o \S+/maca_topk\.o ' build_{before,after}.log | sort -u
      -> one path
    grep -oE '\-offload-arch=xcore[0-9]+' build_{before,after}.log | sort -u
      -> xcore1000 xcore1500 xcore1600
