# bf16 保留块列表的构建:向量化加载,不是压缩(2026-10-21)

设备:MetaX C600-U(28 AP,family 1600,MACA 3.8.1.3,device 1)。目标是块直方图
臂 pass 1 之后的**列表构建**相位:把 `row_block_max` 里达到块阈值的块号压进
`row_block_list`。

## 0. 目标相位

`docs/experiments/20261021_blockhist/` §9 的相位表:b4096 V1048576 上
list = **52,584 周期/CTA(k512 时 7%)/ 52,256(k1024)**。生产循环是

```cpp
for (uint32_t b = tx; b < nb; b += BLOCK_SIZE) {
    if (block_max[b] < cut) continue;
    const uint32_t pos = atomicAdd(&s_nlist, 1u);
    if (pos < list_cap) block_list[pos] = b;
}
```

V=1M 时每行 **16,384 次 uint16 标量加载**(每 lane 每次迭代一个),加上
V/k=1024 密度下约 **1,000 个保留块 → 1,000 次共享原子**。

## 1. 微基准(`walk10.cu`,本目录)

独立核,真实表格形状:4096 行 × 16,384 块(uint16 表 134 MB),`CUT=3840`
在 0..4095 上约 6.25% 保留(≈ V/k=1024 的块保留率),`CAP = nb - nb/4`。
每个臂打印驱动占用的答案、三轮最好、以及 `s_nlist` 的每行均值(收据——压缩
写错会在这里露出来)。BLOCK 1024 与 512 各跑一遍。

| 臂 | 做什么 | BLOCK 1024 | BLOCK 512 |
| --- | --- | ---: | ---: |
| A | 生产形态:标量 uint16 + 每保留块一次原子 | 0.452 ms | 0.419 ms |
| A2 | 同上,`const uint16_t* __restrict__` | 0.460 | 0.421 |
| B | 标量加载 + 波内 ballot 压缩(每波一次原子) | 0.660 | 0.611 |
| **C** | **uint4 加载(每线程 8 块)+ 每线程一次原子** | **0.271** | **0.239** |
| D | uint4 + 6 步 bpermute lane 前缀 | 0.445 | 0.450 |
| — | 每行保留块数(正确答案 1038) | A/A2/B/C 1038 | **D 835** |

四点:

1. **别名不是成本**:A2 == A。
2. **压缩比原子更贵**:B 慢 46%/46%。ballot + `__popcll` 是每元素一次,而原子
   只落在 6.25% 的元素上——与 `docs/C500-radix-profile.zh.md` §5 的"成本是
   原子发射而不是冲突"一致。
3. **向量加载才是杠杆**:C 快 **1.67×(1024)/ 1.75×(512)**。一个 uint4 带 8 个
   块最大值,一次原子保留整个向量的保留数。
4. **D 是错的**:它 ballot 的谓词是 `cnt != 0`,`__popcll(m)` 数的是"有保留的
   lane 数",而预留的应是 `sum(cnt)`;每行 835 vs 1038 就是少掉的那部分。
   D 也比 C 慢,所以没有修正后重测的价值——前缀和在这里本来就不是瓶颈。

注意事项:微基准的 `block_max` 表是冷的(134 MB,DRAM);in-situ 时同一 CTA
刚写过自己那一行的 32 KB,读大概率命中 L2,所以**整格里的收益可能小于 1.7×**。
真 budget 是 §0 的 52k 周期。

## 2. 内核改动

`csrc/maca_kernels/common/radix_row_bf16.cuh` 的 `summary_wanted` 分支:
`nb % 8 == 0` 且该行 `block_max` 16 B 对齐时走 uint4 臂,否则保留原标量循环
(行表的行距是 `blocks_per_row * 2` 字节,奇数行距会让某些行不对齐)。uint4 臂
用 8 位 mask + `__popc` 计数,`atomicAdd(&s_nlist, cnt)` 一次预留,写回仍受
`list_cap` 限制;`nlist` 照旧统计**每一个**保留块(`use_list` 的判据不变)。
列表内的顺序变了,但下游 `walk_kept_blocks` 只遍历,不依赖顺序。

## 3. 核内 A/B:不落地

官方形状(`indices_type=int32`、`return_value=False`、`abort_when_nan_found=False`),
`tools/ab_snapshot.py` 配对、3 个交替轮次、device 1。旧臂 = ADJ4 产物
`281cc660`(`/tmp/arm_adj4`),新臂 = 本节改动 `4abc8ca2`:

| 路由 | n | 中位(new/old) | 范围 |
| --- | ---: | ---: | --- |
| c12 | 10 | 1.0008 | 1.000–1.002 |
| row | 95 | **1.0033** | 0.986–1.066 |
| split | 16 | 0.9961 | 0.981–1.007 |
| 全部 | 121 | **1.0019** | 0.981–1.066 |

改动瞄准的格(V≥512K、row 路由)确实快了一点,但只有 **0.2–0.7%**:旗舰
b4096-V1048576-k512 10918.7 → 10892.1 us(0.9976×)、b4096-V1M-k1024
0.9970×、b512-V1M-k512 0.9926×。对照 §0 的 7% 相位预算,回报约 **0.25%**;
微基准的 1.67× 没有转移过来。

原因两条,都与微基准的成立条件有关:

1. **in-situ 时表是 L2 热的**:同一个 CTA 刚把自己那一行的 32 KB 块最大值写进
   `row_block_max`,紧接着就遍历它;`walk10.cu` 读的是冷的 134 MB 表,那是
   DRAM 读。1.67× 是冷数据下"减少 load 在飞的数量"的收益。
2. **向量臂每个 uint4 多做工作**(8 次比较 + mask + `__popc` + 8 路展开写),
   只省下 7 次 load。load 一旦不再是瓶颈,多出来的指令就是净成本。

最差的格是 b=6、V=1024–16384 的 row 格:**+5.1…+6.6%**,但这些格只有
10–18 us,绝对量 +0.5…1.0 us,是 §2 那个"更重的函数体编进每个 bf16+int32
实例"的代码生成成本(`kSkip` 由索引类型决定),在最小的格上量得出来,在
格子总量上是噪声。

正确性(新产物上):bf16 官方网格 **117/117**(先查后计时),外加契约自测
12 个直接形状 + 12 个奇数 vocab/带窗形状(标量回退唯一可达的路径),全过。

**结论:不落地。**标量循环保持原样;`list_build.patch` 存放改动本体以备复现。
这条记录的价值是把"冷 DRAM 微基准不描述 in-situ 相位"钉下来——§0 的 7%
不是 load 发射预算,下一个动 collect/hist1b 的微基准要先把表热起来再下结论。
