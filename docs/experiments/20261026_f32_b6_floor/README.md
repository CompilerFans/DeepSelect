# fp32 图里最短的那根柱(b6 / v129280):三条路、四个 chunk 数都落在同一个地板上(2026-10-26)

设备:MetaX C600-U(28 AP,family 1600,MACA 20261017.1436),设备 1,
源码 `d9704cb`,产物 `8a4c3501970c`。数据取自同一天的记录
`perf_data/MetaX_C600-U/20261026_052535`(该记录在另一台同型号 pod 上取,
源码 `73f8fcb`,与本提交只差文档)。

## 0. 结论

1. **这一格是"只有 6 行"的地板,不是字节地板。** b6-v129280-k512 fp32 在记录里是
   71.7 µs kernel / **43.3 GB/s**,而同一个 vocab 上 b256/b512/b768/b4096 是
   390/432/450/**476 GB/s** —— 20 倍的差距全部来自行数。
2. **三条路、四个 chunk 数,内核时间都落在 55–69 µs,默认已经是最好的那个。**

   | 臂 | 内核合计 | stage1 | stage2 | 合约 | 
   | --- | ---: | ---: | ---: | ---: |
   | split(默认,8 chunk) | **55.1** | 34.1 | 14.9 | 4.7 |
   | `DEEP_SELECT_F32_CHUNKS=16` | 55.9 | 31.6 | 18.0 | 4.9 |
   | `DEEP_SELECT_F32_CHUNKS=32` | 69.2 | 38.7 | 24.1 | 4.9 |
   | `DEEP_SELECT_F32_COARSE12=1` | 58.9 | coarse12 53.5 | — | 4.1 |

   (`nan_abort_kernel` 另有 1.3–1.5 µs;记录里的 71.7 µs 是这些内核加上发射间隙。)
3. **看单价就明白没有调参空间**:stage1 搬 3.1 MB 用 34.1 µs = 91 GB/s,是读墙的
   6%;而 bf16 的 b6-v131072 格走行核、只有一半的字节,同样是 **34 µs** ——
   所以这不是字节成本,是"一个 CTA 走一条短行"的固定链。
4. **因此没有落地任何改动**:要赢这一格只能把 stage1/stage2/合约合成一条新
   dataflow(一次发射、每行更多 CTA),而同类改动的上一次尝试在 bf16 上刚刚输掉
   (`docs/experiments/20261026_row_phases2/` §8)。这一条记录在案,不做。

## 1. 这一格走的是哪条路

fp32 的路由顺序是 `coarse12 → split → row`。C600U 上 coarse12 的门是
`batches * topk >= kF32Coarse12C600UWideProduct`,b6 的乘积是 3,072,够不着;
于是走 split(`f32_chunked_chunks` = 8),三个内核:stage1 直方图、stage2 归并、
行核的合约半。b256 起乘积过线,走 coarse12 的单个行核,才有 390 GB/s。

## 2. 为什么换路线也不动

`DEEP_SELECT_F32_COARSE12=1` 把 b6 强行送进 coarse12:6 个 CTA、一行一个,
53.5 µs —— 比 split 的 34.1 + 14.9 还差一点。`DEEP_SELECT_F32_CHUNKS` 从 8 加到
16/32 只把 stage1 从 34.1 压到 31.6(再多就反弹到 38.7),而 stage2 因为候选变多
从 14.9 涨到 18.0/24.1,合计反而更差。**两个旋钮都已在最优点或之外。**

## 3. 边界

- 只测了这一格(v129280、k512、bf16 不涉及);b1 那一档同理(记录里 b1 的
  fp32 格是 45–111 µs,同样受发射与行数支配,见 `20261022_f32_pass2_skip/`)。
- 全部用运行期旋钮测量,不改源码、不重建;`topk` 输出经 `lib.generate_testcase`
  与官方 perf 网格同一份数据。
