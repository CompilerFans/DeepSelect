# 行内核的带宽去哪儿了：走查相位拆分、两个被否证的形状、一次不转移的微基准(2026-10-25)

设备:MetaX C600-U(28 AP,family 1600,MACA 3.0.1436.20261017,
torch 2.10.0+metax20261017.1120),设备 1。

产物收据(全部为 `ab_snapshot.py` 子进程打印的、它实际加载的 `.so` 的 md5 前 12 位):

| 臂 | md5 | 说明 |
| --- | --- | --- |
| base | `6ca00ada6973` | 本树 HEAD `120ebee` 的 xcore1600 产物,所有 A/B 的参照臂 |
| e1 | `ba7aa0f73191` | NaN 票改成 key 区间 min 跟踪 |
| pack | `4207a39cccce` | 四个 2 B block_max 存储合成一个 `uint2` |

探针与补丁源码都在本目录。`walkprobe.cu` 是隔离 walk 的相位拆分,`walkocc.cu` 是同一条
body 在 BLOCK 1024/512 × 自然占用/钉死一 CTA 下的扫描(占用数由
`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 直接打印,不手算),`phaseprobe.cu` +
`phase_patch.py` 是真实行 dataflow 的分相位计时(`clock64()` 差分;`repl` 核把第 0 行
复制成 1120 行,Box–Muller 正态数据经手写 round-to-nearest-even 转 bf16),
`walk_patch.py` 生成摊平的 `walk_kept_blocks` 对照臂,`clk.cu` 是时钟标定。
前三者都是独立程序,不经 torch、不经本树的构建系统,全部用
`cucc -O3 -std=c++20 --offload-arch=xcore1600` 构建。两次整算子 A/B 的原始输出在
`ab_e1_raw.txt` 与 `ab_pack_raw.txt`(每轮开头的 `lib=` 是 `ab_snapshot.py` 子进程
**实际加载**的 `.so` md5 前 12 位)。

## 0. 结论

1. **pass 1 的 walk 本身已经是这台机器的 65%,而它离读墙的 35% 差在两条指令类上,
   不在流式读取上**:纯读 1417.7 GB/s(墙的 91.8%),加上 key 变换与块内 max 之后
   1532.0(99.2%,ALU 免费),加上组内 max 树与 block_max 存储掉到 1229.1(79.6%),
   再加上每块一次共享直方图原子掉到 **1007.9(65.2%)**。
2. **在核里,walk 跑到隔离形态的 88%**:b4096 k512 bf16 的四列 `V` 拟出一条直线
   `t_row = 11.6 µs + 8.23 µs × (V / 131072)`,斜率折合 891 GB/s 聚合带宽,截距是
   每行的固定成本。k1024 是 `18.2 µs + 8.77 µs × (V / 131072)`(837 GB/s)。
3. **短行被固定成本统治**,这是"重点 shape 推带宽"在这条路径上的真实分布:
   `b4096 V131072 k512`(758 GB/s 那格旁边最短的一格)每行 19.8 µs,其中 11.6 µs
   与行长无关;真实 dataflow 的相位表把这块点名了 —— 该格 `collect` 27.4%、
   `pass 2 hist` 14.3%、`scan #1` 8.4%、`refine/emit` 6.0%,walk 只有 34.1%。
4. **两个"显然更快"的形状都是否证**:把 `walk_kept_blocks` 摊平(不再走 list)
   在 131072 格上 **1.54× 慢**(90 MT → 每 AP 一个 CTA);把 NaN 票换成 key 区间
   min 跟踪在 121 格上 **0.9992×**(行路径 0.9945×)。
5. **隔离微基准的 +4.4% 没有转移到核里**:打包 `block_max` 存储在隔离 walk 上是
   3.275 → 3.136 ms(V=1048576 k512),在整算子 121 格上是 **0.9991×**。
   该改动已回退,不在本树的提交里。

## 1. 隔离 walk 的相位拆分

生产摘要 walk 的形状(ADJ4、BLOCK 1024、一行一 CTA、每线程每轮四个 `uint4`),每一级
只加一件真实 body 里的东西,所以**相邻两级之差就是那一件的价钱**。1120 行 × 1048576
元素 bf16 = 2.35 GB,数字是一次读行的时间。

| stage | 加了什么 | ms | GB/s | 占 1545 读墙 |
| --- | --- | ---: | ---: | ---: |
| s0 | 只读,四个 `uint4`,XOR 累加 | 1.657 | 1417.7 | 91.8% |
| s1 | + 有序 key 变换与块内 max(纯整数) | 1.533 | 1532.0 | 99.2% |
| s2 | + 8 lane 组内 max 树(`mov_shfl`×3)与 `block_max` 存储 | 1.911 | 1229.1 | 79.6% |
| s3 | + 每块四个 12-bit 共享直方图原子(lane 0) = **生产 body** | 2.330 | 1007.9 | 65.2% |
| s4 | s3 + 下一轮四个 load 提前发射(8 个 `uint4` 在途) | 2.253 | 1042.5 | 67.5% |

两件事值得记下来:

- **s1 比 s0 快**。key 变换并不免费,但 s0 的 XOR 累加链给四个 load 加了一条它不需要的
  依赖;这不是"key 变换负成本",而是 s0 这个对照臂自己不够纯。用它只回答一个问题:
  ALU 不是瓶颈。
- **s3 → s4 只有 +3.4%**。说明 4 个在途 load 已经够盖住延迟,MLP 不是这里的杠杆。
  35% 的缺口在 s2(−20%)和 s3(−18%)上,也就是组内 max 树 + 存储,和共享原子。

## 2. 真实 dataflow 的相位拆分

`phaseprobe` 把生产行核的每一相用 `clock64()` 切出来,一行一 CTA,1120 行。
**注意单位**:探针打印的 `us/row` 是把总时间除以行数,没有乘 28 个 AP 的并发;
真正的每行墙钟是 `打印值 × 28 / 1120`。V=1048576 时整行约 82 µs,V=131072 时约 25.5 µs,
与 CSV 的 77.5 / 19.8 µs 对得上(探针的行数更少,wave 填充略差)。

| 相位 | V=1048576 k512 | V=131072 k512 |
| --- | ---: | ---: |
| 0 清直方图 | 2.4% | 1.6% |
| 1 pass 1 walk | **73.3%** | 34.1% |
| 2 scan #1 | 2.2% | 8.4% |
| 3 建保留块 list | 6.3% | 3.9% |
| 4 pass 2 hist(走 list) | 4.2% | 14.3% |
| 5 scan #2 | 1.2% | 4.3% |
| 6 collect(再走一次 list) | 8.0% | **27.4%** |
| 7 整核 | 100.0% | 100.0% |
| refine/emit(7 − 0..6) | 2.3% | 6.0% |

长行的 73% 是 walk,和隔离探针的结论一致;短行反过来,`collect` 与 pass 2 两次走
list 加起来 41.7%,walk 只剩三分之一。**这两次走 list 读的都是同一批保留块**
(约 `topk` 个 64 元素块),V 越小占比越大,因为它们的成本由 `topk` 定而不是由 `V` 定。

## 3. 每行成本的拟合

从 `perf_data/MetaX_C600-U/20261024_062159/deepselect_perf.csv` 的 `maca_c` 列取
`b4096`、bf16、int32 的四列 `V`(131072 / 262144 / 524288 / 1048576),把 µs 换成
每行墙钟(`t × 28 / 4096`),对 `V / 131072` 做最小二乘:

| k | 截距(每行固定成本) | 斜率(每 131072 元素) | 斜率折合聚合带宽 |
| --- | ---: | ---: | ---: |
| 512 | 11.6 µs | 8.23 µs | 891 GB/s |
| 1024 | 18.2 µs | 8.77 µs | 837 GB/s |

- 斜率就是 pass 1 的 walk(再加上两次 list 走查里随 V 增长的那一小部分),
  891 GB/s 是隔离生产 body 的 1007.9 的 **88%** —— 剩下的 12% 是行的尾部残块和
  collect 走 list 的流量。
- 截距随 `topk` 长大,和"它由 `topk` 定"的读法一致:arena 更大、保留块更多、
  refine 的成员更多。
- 全部 `V` 下的有效带宽:131072 → 374 GB/s,262144 → 523,524288 → 661,
  1048576 → 759。行长每翻一倍,增幅 **+40% → +26% → +15%**,逐段收窄:
  固定项被摊薄,而斜率本身只有 891 GB/s(§0),所以再长的行也到不了读墙。

## 4. 否证 1:摊平的 `walk_kept_blocks` 慢 1.54 倍

把 list 走查摊平成"测试 + 直接取数"(每个 64 元素块先判断块最大值是否过阈值,
过了就地读),V=131072 k512,三轮交替:

| 臂 | 整核 | collect |
| --- | ---: | ---: |
| 走 list(现航) | 1.020–1.029 ms | 25.46 µs/row |
| 摊平 | 1.570–1.573 ms | 22.44–22.49 µs/row |

摊平臂的 **collect 反而更快**(22.4 对 25.5),整核却慢 1.54 倍 —— 90 MT 寄存器,
每 AP 一个 CTA,pass 1 的 walk 被拖垮。这与 `docs/experiments/20261010_skim_rate/`
在 16-bit 行上的结论同形:测试和取数挂在同一条延迟链上,跳过块省下的流量被
发散的 issue 吃回去。**这条形状不再尝试。**

## 5. 否证 2:NaN 票改成 key 区间 min 跟踪,121 格 0.9992×

宽 walk 里的 NaN 票原本是 5 条 SWAR 指令(逐元素判指数全 1 且尾数非零);
E1 把它换成"跟踪 key 的 min",一次变换后 `min` 一个词即可。汇编门通过
(每 64 元素 64 条 `min`,base 为 0),40 项精确性探针全过。整算子 A/B
(2 臂 × 3 轮 × 10 iter):

| 路径 | n | 中位 | 范围 |
| --- | ---: | ---: | --- |
| c12 | 10 | 1.0025× | [0.997, 1.005] |
| row | 95 | 0.9945× | [0.977, 1.026] |
| split | 16 | 1.0020× | [0.994, 1.011] |
| **全部** | **121** | **0.9992×** | [0.977, 1.026] |

减去 follower 的读数完全一致(全部 0.9994×)。**中性,不落地** —— 它换掉的是
walk 里 5 条指令,而 s1 已经证明 walk 的 ALU 不是瓶颈。

## 6. 否证 3:打包 block_max 存储,隔离 +4.4%、在核 0.9991×

`summary_walk` 的 ADJ4 分支每轮写四个相邻块的 16-bit 最大值。把它们写成一次
`uint2`(要求块索引是 4 的倍数,且表的行距取整到 4 的倍数,`contract.cuh` 与
`maca_topk.cu` 的尺寸必须同时改)。隔离 walk:

| 形状 | 四存 | 打包 | 比值 |
| --- | ---: | ---: | ---: |
| V=1048576 k512 | 3.275 ms | 3.136 ms | 0.958 |
| V=131072 k2048 | 1.630 ms | 1.622 ms | 0.995 |

整算子 A/B(2 臂 × 3 轮 × 10 iter,147 格中 121 格有读数):

| 路径 | n | 中位 | 范围 |
| --- | ---: | ---: | --- |
| c12 | 10 | 1.0010× | [0.999, 1.005] |
| row | 95 | 0.9985× | [0.956, 1.018] |
| split | 16 | 0.9990× | [0.994, 1.002] |
| **全部** | **121** | **0.9991×** | [0.956, 1.018] |

减去 follower 的读数一致(0.9991×)。**隔离的 4.4% 没有转移**:s2 那一级的 20%
缺口不是被存储指令数定住的,四个 2 B 存储和一条 8 B 存储在这条 walk 上等价 ——
真正贵的是组内 max 树本身和它给调度带来的形状。**已回退**:一个跨两个文件的
行距不变式,没有整算子量级的收益,不值得留在树里。这是
"受控微基准不转移到核里"在本仓库的第三次记录,前两次在
`docs/C500-to-parity-plan.zh.md` §12–§15。

## 7. 下一步的落点

按上面的分布,"推高带宽"在这条路径上只有三个地方还站着:

1. **walk 的组内 max 树 + 每块原子(s2/s3 的 35%)**。已经试过的两条路(去掉原子、
   换 tree 宽度)都在 `docs/experiments/20261021_adjacent_walk/` 与
   `docs/experiments/20261021_mov_shfl_tree/` 里;还没试过的是"把块直方图从共享
   原子挪进寄存器再合并",这是 `CLAUDE.md` 记下的 lever 形状。
2. **短行的固定成本(11.6 µs/行)**。它的主体是两次 list 走查(collect 27.4% +
   pass 2 14.3%)。合并不了 —— pass 2 要给阈值的双重计数,collect 要写 arena ——
   但两次走的是**同一批块**,可以一次读进来、两次用。
3. **`scan #1` 的 8.4%**:`fold 4096 → 256` 只有 256 个线程在工作,1024 线程的块在
   这一段空转四分之三。
