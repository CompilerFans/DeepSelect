# 逼近 deep_gemm：两个可分离的杠杆，和一份按杠杆排序的方案

前置事实见 `docs/C500-vs-deepgemm.zh.md` §2：官方轴 36 格里 maca_c 只赢 6 格
（全是 `L ≤ 4096`），`L ≥ 16384` 全域落后 2.4–2.9×，最差 `b6-v524288-k512` 落后 10×。

> **⚠ 本节初版把方向写反了（2026-09-14 更正）。** 初版的对比表第三列是
> **时间比**（`maca_c / deep_gemm`），`2.97x` 意思是**慢 2.97 倍**。初版把它当
> 加速比读，于是"长行更快"整段结论颠倒。初版的数字没错，解读错。
> 更正经 `f0bc4e3`，正确结论见该文 §2。

## 1. 先算两个数，再谈怎么优化

`docs/C500-radix-profile.zh.md` 给出的本形状可达读速率是 **1,149.8 GB/s**
（128 MiB 张量实测），记为 `W1`。内核每行读**两趟**。

于是每个格子有两个独立的量：

- **`ours / floor2`** —— 我们的两趟离"以墙速跑完两趟"有多远。这是**我们自己的效率**。
- **`floor2 / dg`** —— 即使两趟跑到满墙速，能不能追平 deep_gemm。**> 1 就追不平**，
  与实现质量无关，是趟数的算术。

| cell | ours µs | 两趟下界 | **ours/floor2** | dg µs | **floor2/dg** | 该格要什么 |
|---|---|---|---|---|---|---|
| `b4096-v1024-k512` | 235.7 | 29.2 | 8.08× | 324.5 | 0.09× | 修自己（上界富余 8×） |
| `b4096-v4096-k512` | 502.0 | 116.7 | 4.30× | 214.2 | 0.54× | 修自己 |
| `b4096-v16384-k512` | 1308.2 | 466.9 | 2.80× | 440.0 | **1.06×** | 两趟**刚够不到** |
| `b4096-v65536-k512` | 4426.9 | 1867.7 | 2.37× | 1521.8 | **1.23×** | 减少趟数 |
| `b4096-v262144-k512` | 15298.1 | 7470.8 | 2.05× | 5497.8 | **1.36×** | 减少趟数 |
| `b512-v262144-k512` | 2175.6 | 933.9 | 2.33× | 718.1 | **1.30×** | 减少趟数 |
| `b6-v524288-k512` | 1070.6 | 21.9 | **48.9×** | 106.0 | 0.21× | **并行度**（不是趟数！） |

**这张表就是方案的全部依据。** 两个结论之前没被算出来过：

1. **`L ≥ 16384` 的大 batch 格，两趟算术上就追不平**（`floor2/dg > 1`）。
   即使把两趟推到满墙速也还差 6%–36%。**减少趟数是唯一出路**，不是优化。
2. **`b6-v524288-k512` 差 49×，与趟数无关** —— 6 行铺在 104 个 AP 上，
   下界只有 21.9 µs，我们跑了 1070.6。这是纯并行度问题，**最便宜的一块**。

## 2. 借鉴清单：三条来源分别给了什么

### 2.1 上游 DeepSelect 文档（`docs/DeepSelect-deep-dive.{md,zh.md}`）

它的**保证**是"每个元素只从全局内存读一次"，工作集 `O(k+B+B2)` 放共享内存。
流程：随机序扫大小为 `B` 的块 → 按运行阈值 `T` 过滤 → 候选缓冲超 `k+B2` 时压缩
并更新 `T`。**这正是 deep_gemm 的 `topk_coarse12` 在做的事**，也是它比我们快的
根本原因。我们要借鉴的是这条**结构性保证**，不是它的某个技巧。

### 2.2 `dsa_topk`

我们的 `radix_core.cuh` 就是从它的 `csrc/radix_topk.cuh` 移植的
（provenance banner 记了 commit）。**要借鉴的是它更新的那份**：
`opt/radix_topk.cuh`（1208 行，比移植来源 1949 行短）里 `kSMEM = 16 KiB`
（对 MACA），与我们的 arena/histogram 别名同向。它的 chunked split/merge
（`launch_topk_f16_chunked`、`recommend_topk_f16_chunks`）**正是 §3.1 要的东西**——
我们移植了它的 chunked 骨架，但只编译了 bf16 的 merge 分支。

### 2.3 `deep_gemm/kernels/fp32_topk.cu`

**唯一能让"两趟变一趟"的具体实现范本**，且是 fp32（正好是我们最短的那块）。
它的 `topk_coarse12_impl`：

- 第一趟算 12 位粗直方图；
- 定位阈值桶后，**同一趟遍历里**就把 `bin > wide_threshold` 的元素直接写进
  `output[atomicAdd(&counter,1)]`，并把 `bin == wide_threshold` 的成员索引
  存进 `candidate_indices[]` **同时**累细直方图；
- 然后**只在候选（约 150 个/行）上做 refine**，不再走整行；
- 只有 `num_input[0] > kCoarse12CandidateCapacity`（桶溢出、极罕见）才回退到
  整行重扫，而且回退路径也把索引暂存在原地，重扫只重读不放索引。

**它与我们的差别是关键的**：我们的 pass 2 无条件重走整行；它只在溢出时重走。
非溢出路径下它**每个元素只读一次**。

## 3. 方案（按"收益/成本"排序，四条独立）

### 条目 1（最便宜，先做）：fp32 的 chunked split —— 直接吃掉 `b6-*` 与 `b256-*`

**证据**：`b6-v524288-k512` 差 **48.9× 于其自身下界**，`b6-v262144` 差 7.79×。
这两个格 `floor2/dg = 0.21`、`0.28`，**两趟也远够**。问题纯粹是 6 行的 CTA 数
喂不满 104 个 AP。

**现状**：split 已存在且**门槛已经覆盖这些格** —— `chunked_bf16_applies`
（`maca_topk.cu:611`）是 `batches <= 64 && vocab_size >= 262144 && topk ∈ {512,1024}`，
`kChunkedChunks = 16`。实测收益记在 `:592-596`：`B=6/L=1M 2.03 → 0.18 ms`。
**但只有 bf16 的 merge 分支被编译**（`launch_typed_chunked` 里的
`radix_topk_row_bf16_k` / `_b` 特化），`radix_select_row` 对 float 走
`radix_topk_row_f32`，**没有 fp32 的 split 入口**。

**要做**：给 fp32 增加 split/merge 分支（stage1 用现成的 fp32 行核按 chunk 选
`topk` 个候选；stage2 在 `chunks × topk` 个候选上跑一次行核），沿用同一套
`ChunkedWorkspace` 与门槛。**这是复用已有机器，不是新算法。**

**风险**：`s_num_input[0]` 的双重身份陷阱（`C500-radix-profile.zh.md` §5.1）在
merge 路径同样存在 —— 它是 split 的候选计数，必须保证"计数"与"实际暂存数"相等，
否则越界。**先看 §5.1 那节的结论再动手。**

**预期**：`b6-*` 从落后 4.5–10× 变为领先；`b256-*` 的 3.5× 落差大部分消失。

#### 动手前的实测：split 的算术收益有多大，以及它现在被什么吃掉

三个测量（`/tmp/dsab/chunk_probe.py`、`ws_cost.py`、`decompose.py`，
`CUDA_VISIBLE_DEVICES=2`，C500），都是**内核时间**：

| cell / dtype | 走的路径 | 内核时间 | 说明 |
|---|---|---|---|
| `b6-v262144` bf16 | **split** | **96.6 µs** | nan_scan 20.0 + stage1 40.9 + stage2 29.5 + merge 5.3 |
| `b6-v262144` fp32 | 行核 | **563.8 µs** | `chunked_bf16_applies` 对 fp32 不成立（`topk_launch:728` 门 `value_dtype == 1`） |
| `b6-v524288` bf16 | **split** | **100.5 µs** | |
| `b6-v524288` fp32 | 行核 | **1073.2 µs** | |

**dtype 换算系数**：`b6-v65536`（在 262144 门槛之下，两条路都走行核）
bf16 **53.7 µs** / fp32 **144.7 µs** ⇒ **k = 2.69**。

所以 fp32 若接上 split，算术收益是 **563.8 / (96.6 × 2.69) = 2.17×**、
**1073.2 / (100.5 × 2.69) = 3.97×** —— 即 `b6-v262144` 564 → 260 µs、
`b6-v524288` 1073 → 270 µs。**达不到"领先"**（deep_gemm 在这两格是 72.5 / 106.0 µs），
但能消掉 3–4×。

**split 现在被什么吃掉：不是设备的活，是每次调用 270 µs 的 host 时间。**
`deep_select.topk` 每次调用都 `cudaMalloc`/`cudaMemcpy`/`cudaFree` 长度表，
再 `cudaMalloc` 12 MB 候选 workspace，末尾 `cudaFree`（`maca_topk.cu:900-922`）。
分解（`decompose.py`，host 用 `perf_counter` 且在设备空闲时测）：

| cell | host（设备空闲） | device | e2e（设备空闲调用）| 谁在决定 |
|---|---|---|---|---|
| `b6-v262144` bf16 | **268.2 µs** | 96.6 µs | 264.4 µs | **host** |
| `b6-v524288` bf16 | **272.6 µs** | 100.5 µs | 266.2 µs | **host** |
| `b512-v262144` bf16 | 87.3 µs | 821.8 µs | 907.7 µs | device |

即 `e2e ≈ max(host, device)` —— 完全重叠，且小 batch 长行这块
**host 是 2.8× 于设备**。raw MACA 对照（`malloc_cost.cu`：12 MB 的
`cudaMalloc`+`cudaFree` 一对，空闲 runtime）只有 **36 µs/iter**，所以 268 µs 里
约 230 µs 在别处 —— 已定位到 `torch.empty` 分配输出 + FFI 边界 + 六次 launch。

**这条改变条目 1 的做法**：只加 fp32 分支，收益是 2.17×/3.97×（内核），
而 e2e 会停在 ~270 µs 的 host 地板上。**先做 host 侧**：把 workspace 与长度表
改成**按最大尺寸分配一次、跨调用复用**（按 `(batches, topk)` 缓存），
再叠 fp32 分支。两者都收敛到同一个 e2e 目标，且 host 侧的改动不碰内核、
不碰 `s_num_input[0]`、没有 lane 宽度风险。

（`ws_cost.py` 早先给出的 "+170 µs host overhead" 是 `e2e − Σkernel` 的**减法**，
那在 host/device 重叠时不是分解 —— 已由 `decompose.py` 的直接测量取代，
上述 268/96.6 那对才是结论。`malloc_cost.cu` 的 `mcMalloc 5382 µs` 也是 torch
profiler 对 malloc 的**斜向**计时（1 次/iter 摊进 10 次迭代），不是单次成本。）

### 条目 2（结构性，主战场）：把 pass 2 改成"只在溢出时重走"

**证据**：`L ≥ 16384` 的大 batch 格 `floor2/dg = 1.06–1.36`，**两趟追不平**。

**做法**：把 deep_gemm `topk_coarse12_impl` 的形态搬进
`radix_topk_row_f32`（fp32 先行，它是短板；bf16 视条目 3 的结论再定）：
pass 1 定位阈值桶后，**同一趟**把补集直接写输出、把阈值桶成员索引暂存进 arena
并累细直方图；随后只在 arena 里 refine。整行重扫**只在溢出时**发生。
这正是上游文档的 scan/filter/compact，也正是 `overflow` 那条罕见边的用法。

**风险**：这正是我们的 pass 2 现在**不做**的事（它无条件重走）。改动的核心是
把"细直方图 + 暂存"前移到 pass 1 的同一趟遍历里，需要保证 arena 与粗直方图的
别名时序仍然正确（那是 `radix_core.cuh` 里最微妙的一处约束）。

### 条目 3：`L ≤ 4096` 的短行格 —— 修自己，上界有 4–8× 富余

**证据**：`b4096-v1024` `ours/floor2 = 8.08×`、`b4096-v4096 = 4.30×`，而
`floor2/dg` 只有 0.09/0.54 ⇒ **两趟绰绰有余，是我们自己没跑满**。

**做法**：先量，再动。这三个短行格没有 profile（§3 的归因只在
`b4096-v16384-k512` 上做过）。量法用现成流程：profile 文档 §1 的增量消融 +
§5.3 的原子计数法，套在 `b4096-v1024-k512` 上。**在拿到归因之前不写任何代码**——
上一轮块宽 A/B 已经证明这个区间"看起来很明显的优化"（换 1024 线程）方向是反的。

### 条目 4（不做）：块宽 / `needs_long_row_bf16` 门槛 / 寄存器直方图

三条都已有实测否证，别再试：
- 块宽与 `L`/`B` 门槛：账本 §6（1024 线程在 `L < 60000` 慢 10–22%）。
- 寄存器直方图：profile §5.3，收益上限 **~1 µs**。
- 合并原子减冲突：profile §5.1/§5.2，`P4` +38 µs 更慢；且 F1 聚合越界。

## 4. 一条必须写清的前提

**maca_c 在不同格上需要的优化是相反的**：`b6-*` 要**更多并行**（split），
`b4096-v16384+` 要**更少趟数**（单趟形态）。任何"一个改动全局受益"的期待都不成立
—— §1 的两个数列已经把它们分开了。所以方案按格分派，而不是找一个统一大改。

**且条目 1 与条目 2 都有溢出哨兵风险**（`s_num_input[0]`），这是本内核最容易
踩且不报错的地方。两条都做之前先读 profile §5.1。
