# maca_c 的向量化现状，与 `backend="deep_gemm"` 的对等对比

测量日 2026-09-14，C500，`CUDA_VISIBLE_DEVICES=2`（该设备当时无进程）。
口径：`tests/lib.py` 造例（`NormalFloatDistribution`），种子 11，
`return_value=False`，`indices_type=int32`。

---

## 1. 数据加载的向量化现状：**分路径，且 fp32 路径完全没有向量化**

`radix_topk_row_bf16_b` 的装载点是**按对齐分档**的
（`csrc/xcore1000/radix_core.cuh:1031`）：

```c
const bool input_aligned = (length & 7u) == 0 && bf16x8_is_aligned(input);
```

| 路径 | 触发条件 | 装载宽度 | 说明 |
|---|---|---|---|
| bf16 对齐 | 行长是 8 的倍数 **且** 行首 16 B 对齐 | **128 位**，每线程 `uint4` 搬 8 个 bf16（`hist_add_bf16_wide`，`:228`） | `input` 满足 `INPUT_STRIDE_ALIGNMENT_REQUIREMENT`(1024 B) ⇒ 行首天然 16 B 对齐，所以只看行长 |
| bf16 非对齐 / 尾块 | 行长非 8 的倍数时**整行**退回 | 标量 `ldg_u16`（每次 2 B） | 有意为之：混合向量+尾块在 1024 线程块上实测有间歇性竞争（`:1029` 的注释） |
| **fp32（全部）** | — | **标量 `ldg_b32`（每次 4 B），无任何向量装载** | 见下 |

**fp32 路径的向量化是"有实现、无调用"。** `hist_add_f32`（`:132`）是
`float4` 的向量直方图助手，但它在 fp32 行内核里**没有生效**：

- `radix_topk_row_f32`（`:465`，**生产 fp32 行**）通篇没有 `float4`/`uint4`——
  我数过：该函数体里向量类型的出现次数是 **0**。
- 唯一调用 `hist_add_f32` 的是 `:497`，属于 `radix_topk_row_f32_rescan`
  （**溢出重扫**那条边），不是主路径。

所以 **fp32 的常态是每元素一次 4 B 标量装载**。对 `topk <= 512` 的 fp32 调用，
`api.cu` 里的 `topk_select_fp32` 走的是 xcore1600 那套（另一份代码）；
但 `:465` 这条是 fp32 的**降级/重扫**路径，它是标量的。

**这说明什么**：内核的两趟已经跑到单趟可达速率的 80%/89%
（`docs/C500-radix-profile.zh.md` §3），那个"可达速率"是在**当前指令数**下测的。
向量化减少的是**发射的装载指令数**，而 §3 的结论是内核绑在"读之外还要做的事"
（原子发射 + 屏障），不是绑在装载发射上。所以 **fp32 向量化不是一条已被证明
有收益的方向**——它是"看起来该做但没人量过"，要动先量。

## 2. 与 `backend="deep_gemm"` 的对等对比

`deep_gemm` 后端是**严格子集**：只吃 float32、`topk <= 2048`、无序
（`deep_select/interface.py:316/320/324`，不能服务的一律 `UnsupportedByBackend`）。
所以可比格**只有 fp32 且 topk ≤ 2048** 的那些；bf16 与 `topk > 2048` 根本不可比
（它拒答，拿 bf16 去比就是比另一个算子）。

| cell（fp32） | maca_c µs | deep_gemm µs | ratio | 答案一致 |
|---|---|---|---|---|
| `b4096-v1024-k512` | 235.1 | **318.0** | **0.74x** | 是 |
| `b4096-v16384-k512` | 1309.6 | **439.0** | **2.98x** | 是 |
| `b4096-v65536-k512` | 4431.3 | 1518.3 | 2.92x | 是 |
| `b512-v262144-k512` | 2179.5 | 716.4 | 3.04x | 是 |
| `b4096-v16384-k2048` | 1448.5 | 526.5 | 2.75x | 是 |

**答案一致**：`torch.equal(排序后的索引)`，五格全部逐元素相同。

> **⚠ 本节初版把方向写反了（2026-09-14 更正）。**
> 初版写的是"长行 maca_c 快 2.75–3.04×、短行慢 26%"。**反了。** 上表第三列的
> `maca_c / deep_gemm` 是**时间比**：`2.97x` 意味着 maca_c 花的时间是对方的
> 2.97 倍，即**慢 2.97×**，不是快。初版把它当加速比读了，于是整段结论颠倒。
> 发现方式是下面 §2 的 36 例全量重测：36 格里 33 格 maca_c 更慢，与初版说的
> "长行更快"不可能同时成立。**更正后的结论见 §2。** 下表数值本身没错，错的是
> 对它们的解读。

### 结论（更正后）：**没有"完全大于等于"，而且差距比初版写的大得多**

- **`L = 1024` 的三格 maca_c 是赢的**（`b512-v1024` 1.11×、`b768-v1024` 1.12×、
  `b4096-v1024` **1.38×**）—— 这是全表唯一赢的地方。
- **其余各格 maca_c 慢 2.7–10×。** 长行尤其悬殊：`b6-v524288-k512` 慢 **10×**
  （1070.6 vs 106.0 µs）。deep_gemm 的 `topk_coarse12` 单行核一 CTA 一行、
  数据只读一遍，而 maca_c 读两趟。

### 诚实边界（三条）

1. **上面每个数都是 `e2e_time`**，即 profiler 里所有 kernel 的时间跨度，不是纯
   kernel 时间；两侧都夹带非内核开销。**但方向性结论不依赖这一点** —— 33/36 的
   差距远大于任何 e2e 口径偏差。
2. **本表全部是 fp32。** bf16 是 DeepSelect 的主场景，而 `deep_gemm` 后端不吃
   bf16，所以"我们与它的 bf16 对等场景"不存在 —— 没有可比对象。
3. **单种子（seed 11）**。差距量级（≥2.7× 与 10×）远大于抖动，但若要出对外材料
   应重复到三种子。

### 一条待查的 `SETS-DIFFER`

`b4096-v65536-k512` 上 maca_c 与 deep_gemm 选出的**集合不同**。maca_c 侧的契约
自检（下标范围、唯一性、`min(selected) ≥ max(unselected)`）是 **ok**，所以
maca_c 自洽。已知 deep_gemm 后端有分块截断漏洞（宿主仓以 strict xfail 记录
`deep_gemm/tests/test_indexer_topk_selector.py::test_selector_candidate_overflow`），
**很可能是它截断** —— 但**本轮没有证实**，因此**不得**当作 maca_c 正确性的证据，
也不得当作 deep_gemm 的已知缺陷来引用。待单独定位。

### 修复前必读：为什么这个差距不可能靠"调参"抹平

`L = 1024` 的三格 maca_c 领先，`L ≥ 16384` 全域落后 —— 分界不在参数，在
**算法形态**：deep_gemm 的 `topk_coarse12` 与上游 DeepSelect 都是"每个元素只读
一遍"，maca_c 的行核读两趟。两趟读在长行上就是 2× 的 DRAM 代价，
`docs/C500-radix-profile.zh.md` §3 已实测两趟分别是单趟可达速率的 80%/89% ——
**没有靠调度把这 2× 消化掉的余地**。所以逼近持平的路径是减少趟数
（`radix_topk_row_bf16_k` 那套更轻的数据流，或改造成上游的 scan/filter/compact），
不是再调块宽/门槛（那条已由账本 §6 证否）。
